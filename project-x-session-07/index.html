🧩 EKS add-ons: shared cluster services

  • An add-on is extra software that extends the cluster. It is a native EKS feature: AWS console → your cluster → Add-ons → "Get more add-ons" (about 23 from AWS, plus community and marketplace ones like Datadog).
  • How one gets installed: Terraform aws_eks_addon → calls the EKS API → EKS creates the Kubernetes objects (for example the coredns Deployment) → the pods run on your workers. AWS manages the install.
Add-onWhat it does
CoreDNSDNS for Service names inside the cluster. Practically required
VPC CNIGives every pod an IP address from the VPC subnets
kube-proxyRoutes Service traffic to pods. Required for networking
Pod Identity AgentLets pods get AWS credentials (assume IAM roles)
Metrics ServerCPU and memory numbers for kubectl top and the HPA (Containers Session 12)
EBS CSI driverLets pods use EBS volumes (PVCs from Containers Session 13)
CloudWatch ObservabilityShips container and node logs and metrics to CloudWatch
  • Also in the catalog but not in our build: the EFS CSI driver (shared file storage), GuardDuty (security), and more.
  • In our code: terraform/modules/eks-cluster/addons.tf. Two aws_eks_addon resources, each with for_each: first vpc-cni, kube-proxy, eks-pod-identity-agent; then coredns, metrics-server, aws-ebs-csi-driver and amazon-cloudwatch-observability.
  • Nothing is pre-selected in Terraform. The console picks the basic add-ons for you. Our code sets bootstrap_self_managed_addons = false, so every add-on has to be declared. Leave them out and the cluster still gets created, but it doesn't work properly.
  • Cost: there is no fee per add-on. You pay for what it uses: CloudWatch logs (not cheap, so retention is set to 2 weeks in the Terraform), EBS volumes, and a little CPU and memory on your nodes.
  • The CloudWatch add-on made four log groups: /aws/containerinsights/<cluster>/application, dataplane, host, performance. The application logs are the same lines kubectl logs shows.
  • Before EKS add-ons existed, teams installed all of this themselves with Helm.
  • 📝 Metrics Server and kube-state-metrics are different things (see Corrections).

⛵ Helm: why teams use it

  • Helm is a command-line tool like kubectl, called the Kubernetes package manager. It uses the same kubeconfig and talks to the same API server. Install: brew install helm.
  • Why: scale. It is the same reason we use Terraform instead of clicking: variables, reuse, and one set of files for dev, staging and prod.
  • Helm only creates Kubernetes objects (Deployments, Services, StatefulSets, DaemonSets…). It can't create a cluster, an EC2 or an S3 bucket. That is Terraform's job.
Terraform ideaHelm idea
.tfvars valuesa values file
resource code with var.nametemplates with {{ .Values.name }}
terraform applyhelm upgrade --install
a public module with hundreds of inputsa public chart with a 2,000-line values file
  • A release is one installed copy of a chart, with a name you choose. Helm manages everything in it as one unit: helm uninstall removes all of it, whether that is 1 pod or 50 objects.
  • How teams use it:
    • Platform software from public charts: Karpenter, External Secrets Operator (Containers Session 11), Grafana, OpenTelemetry Collector.
    • Mostly their own apps, with one values file per environment. Our investment app gets its own chart later.
    • Later, Argo CD runs the Helm upgrades automatically. It sits on top of Helm, it doesn't replace it.
  • 81% of organizations in the 2025 CNCF survey reported using Helm in production. Helm tasks also appear in the CKA and CKAD exams. The instructor's point: if you say you work with Kubernetes, an interviewer expects Helm, the same way Terraform implies modules.
  • 📝 Helm is its own CNCF project, not part of Kubernetes itself (see Corrections).

📦 Inside a chart: Chart.yaml, values and templates

Class example: class/07/live-helm/ in the infra repo. The same nginx pod, once as plain YAML and once as a chart.

nginx-pod-chart/ ├── Chart.yaml # required: the chart's name and version (its ID card) ├── dev-values.yaml # the variables, one file per environment ├── staging-values.yaml ├── prod-values.yaml └── templates/ └── pod.yaml # normal Kubernetes YAML with placeholders

The values file (dev-values.yaml):

podName: nginx

container:
  name: nginx
  port: 80

image:
  repository: nginx
  tag: "1.14.2"

The template (templates/pod.yaml):

apiVersion: v1
kind: Pod
metadata:
  name: {{ .Values.podName }}
spec:
  containers:
  - name: {{ .Values.container.name }}
    image: "{{ .Values.image.repository }}:{{ .Values.image.tag }}"
    ports:
    - containerPort: {{ .Values.container.port }}
  • Helm fills the placeholders with the values and sends normal YAML to the cluster.
  • Everything in templates/ is read automatically. You never name a template file in the command. You only choose the values.
  • Chart.yaml doesn't connect to the templates. It only describes the chart. The version matters when you share the chart with others.
  • Values live outside templates/. One values file feeds every template in the chart. One chart = one set of templates.
  • The default file name is values.yaml, and Helm picks it up by itself. The class chart has no default, so you must pass one with -f.
  • Different environments = different values files, same templates.
  • Real-life chart: Grafana. Its templates/ folder holds a Deployment, ConfigMaps, HPA, Ingress, NetworkPolicy, Secret, Service, Role and RoleBinding, ServiceAccount, StatefulSet and more. Its values.yaml is about 2,000 lines. You never edit those templates. You supply your own values.
  • 💡 Don't mix the two up: Grafana is a dashboard product. Helm is just one way to install it. Grafana comes back in the monitoring classes.

  • Scaling the Helm way: change replicaCount in the values file, then run helm upgrade again. Don't edit the live object.
  • Remote charts: helm repo add then helm install (Grafana), or an oci:// address (Karpenter).
  • A Helm install failed? After Helm sends the YAML it is ordinary Kubernetes. Go back to get → describe → logs (Containers Session 06).
  • kubectl rollout undo brings back the previous pod template of one workload. helm rollback covers the Deployment, the ConfigMap, the Service and anything else the release changed.
  • 💡 A new release name doesn't rename the pod. The class values hard-code podName: nginx, so a second release in the same namespace clashes. Installing a chart twice only works when the templates use the release name, like {{ .Release.Name }} in the class service-chart.

🪚 Karpenter: what it is and why there is a system node

  • Karpenter is an autoscaler for nodes. It runs as a pod in the cluster, watches for pods that can't be scheduled, and launches EC2 workers that fit them. (Containers Session 12: the HPA adds pods, Karpenter adds nodes.)
  • Our design (Session 05): a managed node group called system (1 node in dev) runs the system pods, including Karpenter. Application pods go on workers that Karpenter launches.
EKS managed node groupKarpenter
What it isA feature of the AWS EKS serviceSoftware running as a pod in your cluster
Defined inTerraform: aws_eks_node_group and aws_launch_templateKubernetes YAML: NodePool and EC2NodeClass
Change instance typesTerraform or the EKS consolekubectl edit nodepool general, or re-apply the YAML
Used here forSystem pods (CoreDNS, Karpenter…)Application pods
  • vs an Auto Scaling group (Scale Session 09): ASG settings live in the EC2 console and an AWS service does the scaling. Karpenter lives in your cluster and reads YAML objects.
  • vs Cluster Autoscaler: the older Kubernetes autoscaler that scales node groups. Most AWS teams now choose Karpenter, and Karpenter's docs include a "migrating from Cluster Autoscaler" guide. For your résumé: Karpenter.
  • Why Karpenter gets resource requests: if Karpenter can't run, nobody launches new nodes, and everything waiting stays stuck. Requests reserve its CPU and memory (Containers Session 11).
  • High availability: the chart starts 2 Karpenter pods with pod anti-affinity, meaning "never both on the same node". With one system node, the second pod stays Pending. That is expected in dev. In production run at least 2 system nodes.
  • 📝 Karpenter is open-source software that AWS built. It is not a managed AWS service (see Corrections).

🔧 Installing Karpenter by hand (3 steps)

1

AWS prerequisites. IAM role, instance profile and permissions. Already created by Terraform in the eks root (Session 05: terraform apply makes the prerequisites only).

2

The controller, with Helm. The instructor followed the Karpenter "Getting Started" docs instead of running the PR's install.sh. The script works, but it is hard to read (jq and long pipelines). He asked Claude to check each doc setting against our Terraform. What changed from the doc command:

  • Removed settings.interruptionQueue: our Terraform never created an SQS queue.
  • CPU request 1 → 250m, memory request 1Gi → 512Mi. Limits stayed.
  • Added a nodeSelector so Karpenter itself runs on the system node.
  • Namespace kube-system. The zonal shift setting stays false.
export KARPENTER_NAMESPACE="kube-system"
export KARPENTER_VERSION="<latest release>"
export CLUSTER_NAME="<your-cluster-name>"

helm registry logout public.ecr.aws    # fine if it says you were not logged in

helm upgrade --install karpenter oci://public.ecr.aws/karpenter/karpenter \
  --version "${KARPENTER_VERSION}" \
  --namespace "${KARPENTER_NAMESPACE}" --create-namespace \
  --set "settings.clusterName=${CLUSTER_NAME}" \
  --set controller.resources.requests.cpu=250m \
  --set controller.resources.requests.memory=512Mi \
  --set controller.resources.limits.cpu=1 \
  --set controller.resources.limits.memory=1Gi \
  --set-string 'nodeSelector.projectx\.io/node-role=system' \
  --wait

kubectl -n kube-system get pods        # karpenter: 1 Running, 1 Pending (anti-affinity)
  • This is the shape of the class command. The instructor shared his exact one in the class chat.
  • Every --set changes a value of the Karpenter chart without downloading the chart and editing its values file.
  • 💡 Pasting export lines that carry # comments into the terminal gave errors. Remove the comments before pasting.
3

Tell Karpenter what to build. Two objects in one file. The doc sample doesn't work as written: it points at a node role and tags our Terraform doesn't create. Fill in three values from terraform output in the eks root (the platform output): the Karpenter instance profile, the two private subnet IDs, and the security group ID.

ObjectAnswersMain fields
EC2NodeClassHow to build a workerAMI (Amazon Linux 2023, pinned), subnets, security group, instance profile

apiVersion: karpenter.k8s.aws/v1
kind: EC2NodeClass
metadata:
  name: general
spec:
  instanceProfile: REPLACE_WITH_YOUR_KARPENTER_INSTANCE_PROFILE   # IAM identity for new workers
  amiSelectorTerms:
    - alias: al2023@v20261031                 # pinned Amazon Linux 2023 image
  subnetSelectorTerms:                        # your two private EKS subnets
    - id: REPLACE_WITH_YOUR_PRIVATE_EKS_SUBNET_ID_1
    - id: REPLACE_WITH_YOUR_PRIVATE_EKS_SUBNET_ID_2
  securityGroupSelectorTerms:
    - id: REPLACE_WITH_YOUR_EKS_SECURITY_GROUP_ID
  associatePublicIPAddress: false             # workers stay private
---
apiVersion: karpenter.sh/v1
kind: NodePool
metadata:
  name: general
spec:
  template:
    spec:
      nodeClassRef:
        group: karpenter.k8s.aws
        kind: EC2NodeClass
        name: general
      requirements:
        - key: karpenter.sh/capacity-type
          operator: In
          values: ["spot"]                    # Spot, because this is dev
        - key: node.kubernetes.io/instance-type
          operator: In
          values: ["t3.medium", "m5.large"]
      expireAfter: 720h                       # replace workers every 30 days
  limits:
    cpu: "8"                                  # never more than 8 vCPUs in total
  disruption:
    consolidationPolicy: WhenEmpty            # only remove empty workers
    consolidateAfter: 1m
kubectl apply -f karpenter-node-settings.yaml
kubectl get ec2nodeclass,nodepool
kubectl edit nodepool general          # change instance types later

🏷️ nodeSelector and the first Karpenter worker

nodeSelector is a field in the pod spec. The pod may only run on a node that carries that label.

kubectl get nodes --show-labels
# one label per line, easier to read
kubectl get nodes --show-labels | tail -1 | awk '{print $6}' | tr ',' '\n'
# or show just the two labels we care about
kubectl get nodes -L projectx.io/node-role,karpenter.sh/nodepool

The system node carries projectx.io/node-role=system. Workers launched by Karpenter carry karpenter.sh/nodepool=general.

The test:

kubectl apply -f - <<'EOF'
apiVersion: v1
kind: Pod
metadata:
  name: demo
spec:
  nodeSelector:
    karpenter.sh/nodepool: general
  containers:
  - name: demo
    image: busybox
    command: ["sleep", "3600"]
EOF

kubectl get pods -o wide
kubectl get nodeclaims                        # Karpenter's record of each worker it launched
kubectl -n kube-system logs <karpenter-pod>   # launch decisions and errors
pod Pending (no node has the label) → Karpenter sees it → new EC2 within seconds, tagged karpenter.sh/nodepool: general → pod Running (log: launched a t3.medium in us-east-1a)
  • kubectl apply -f - <<'EOF' applies YAML typed inline, without saving a file.
  • A ready-made version of this test is class/07/capacity-check.yaml.
  • A pod with no selector (kubectl run testpod --image=nginx) landed on the system node. Nothing stops it yet. The stronger fix comes later: taints and tolerations, so only system pods may run there.
  • More than one NodePool makes sense only with a real reason, for example general plus a GPU pool for machine-learning workloads. Not just to separate frontend from backend.
  • Project rule from now on: every app Deployment carries the selector below. The class app/deployment.yaml already has it.
spec:
  nodeSelector:
    karpenter.sh/nodepool: general

🧪 The test that stayed Pending (not solved in class)

  • A pod with a big CPU request (1500m, later 1800m) stayed Pending and Karpenter launched nothing. kubectl describe pod said, roughly, that no instance type has enough resources.
  • The first explanation in class was "no nodeSelector, so Karpenter ignores it". With the selector added and the big request, it was still Pending. The instructor left it open.
  • The class README is more careful than the lecture: whether a selector is needed depends on the nodes and NodePools you have, and the cause of this Pending pod was not established. Karpenter looks at any pod the scheduler can't place and launches a node when a NodePool can satisfy it.
  • The written class notes guess the 8-vCPU limit. That doesn't fit: only one 2-vCPU Karpenter worker was running, so 2 of 8 were used.
  • Most likely cause (my reading, not confirmed in class): both allowed types, t3.medium and m5.large, have only 2 vCPUs. Part of that is reserved for the system, and every node also runs DaemonSet pods (VPC CNI, kube-proxy, the CloudWatch agent…). A 1500–1800m request doesn't fit in what is left on either type, which matches the "no instance type has enough resources" message.

How to check next time:

kubectl describe pod <pod>                    # Events: the scheduler's reason
kubectl -n kube-system logs <karpenter-pod>   # Karpenter's reason
kubectl get nodepool general -o yaml          # limits and allowed instance types

Then try a smaller request, or add a 4-vCPU type to the NodePool.

Golden rule: install with Helm, look with kubectl. And when a pod is Pending, read its events and the Karpenter logs before you change anything: Karpenter only builds what a NodePool allows.

Self-test

Check yourself

Answer each question out loud first, then open the answer. Score yourself out of 10.

1. A pod in the web namespace calls http://trading-api.trading:8080 and it works. You paste the same URL into your laptop's browser and it fails. Who answered the name inside the cluster, and why can't your laptop use it?

Show answer

CoreDNS answered it, and CoreDNS only serves pods inside that cluster. trading-api.trading is short for trading-api.trading.svc.cluster.local. That name exists only in the cluster's own DNS. Your laptop asks public DNS, where Route 53 keeps public records, and nobody there knows the name. Even with the IP in hand, a ClusterIP is only reachable from inside the cluster.

  • To reach it from outside you need a kubectl port-forward, or an Ingress / load balancer with a Route 53 record in front.
  • Analogy: CoreDNS is the office extension list. Route 53 is the public phone book.

2. CoreDNS is an EKS add-on in our cluster. Karpenter was installed with Helm. Both end up as pods on the system node. What is different about who installs and upgrades each? And which forgotten add-on makes kubectl top nodes fail?

Show answer

An EKS add-on is installed by AWS through the EKS API. A Helm release is installed by you, straight into the Kubernetes API.

  • Add-on: Terraform aws_eks_addon → EKS API → EKS creates the objects (the coredns Deployment) and tracks the version.
  • Helm: you pick the chart version and the values, and you run the upgrade.
  • kubectl top and the HPA need Metrics Server. Without it nothing collects CPU and memory numbers.
  • In our Terraform nothing is pre-selected (bootstrap_self_managed_addons = false), so a forgotten add-on is simply missing.

3. An interviewer asks: "What is the difference between helm install, helm upgrade --install and helm template? Which one belongs in a deploy pipeline, and why?"

Show answer

helm upgrade --install belongs in the pipeline, because it is safe to run again and again.

  • helm install works the first time only, like kubectl create. The second run fails because the release already exists.
  • helm upgrade --install installs if the release is missing and updates it if it is there, like kubectl apply. That is idempotent (Scale Session 21): same command, same end state.
  • helm template only renders the final YAML on your machine. Nothing reaches the cluster. Good for reviewing what a change would send.

4. A chart has Chart.yaml, dev-values.yaml, prod-values.yaml and a templates/ folder with a Deployment and a Service. There is no values.yaml. A teammate runs helm upgrade --install shop ./chart. What goes wrong, and how did Helm decide which template files to use?

Show answer

The placeholders have nothing to fill them, because no values file was given. Helm only loads a file by itself when it is named exactly values.yaml. Here the command needs -f dev-values.yaml. Without it Helm stops with a template error, or renders empty fields that the API server rejects.

  • Helm did not "decide" on templates at all: everything in templates/ is rendered, every time. The values are the only thing you choose.
  • Two fixes: pass -f, or add a values.yaml with safe defaults and keep the per-environment files for overrides.

5. Friday release: one helm upgrade changed a Deployment's image, a ConfigMap and a Service port. The app breaks. Compare fixing it with kubectl rollout undo versus helm rollback.

Show answer

kubectl rollout undo fixes one workload. helm rollback takes the whole release back.

  • kubectl rollout undo deployment/shop brings back the Deployment's previous pod template. The ConfigMap and the Service port stay new, so you get old pods with new config. It may still be broken.
  • Helm saves every upgrade as a revision of the release. helm rollback shop returns all three objects to the previous revision in one step.
  • After either one, check with kubectl: get pods, describe, logs.

6. Prod is down. A teammate fixes it with helm upgrade --install shop ./chart -f prod-values.yaml --set image.tag=1.4.1. It works and everyone goes home. What is the risk at the next normal deploy?

Show answer

The fix lives only in that one command, not in Git. --set overrides a value without touching the file, so prod-values.yaml still names the broken tag. The next deploy that uses the file puts the broken version back.

  • Same idea as Terraform drift: reality and code disagree, and the code wins on the next run.
  • Use --set for a quick test or an emergency. Then write the value into the values file and commit it.

7. After installing Karpenter on a dev cluster with one system node you see one Karpenter pod 1/1 Running and a second one 0/1 Pending. Is the install broken? What would you change for production?

Show answer

Not broken. That is pod anti-affinity doing its job. The Karpenter chart runs 2 replicas and forbids both on the same node, because one node failure would take out both. With one system node, the second pod has no allowed place and stays Pending. kubectl describe pod says the node "didn't match pod anti-affinity rules".

  • Dev: one running controller is enough.
  • Production: at least 2 system nodes, so each Karpenter pod gets its own node.

8. Karpenter launches nodes. So why does our design still keep an EKS managed node group? And what happens if Karpenter has no resource requests and the system node fills up with other pods?

Show answer

Karpenter is a pod, and a pod needs a node before it can create nodes. On a brand-new cluster there are zero nodes. The managed node group (built by Terraform, run by AWS) provides the first one, where CoreDNS and Karpenter can start.

  • If Karpenter gets squeezed out or can't be scheduled, nobody adds capacity. New pods stay Pending, and it looks like "the app is broken" when the real problem is the autoscaler.
  • Requests reserve CPU and memory for it, so the scheduler always keeps its seat.
  • The nodeSelector for projectx.io/node-role=system pins it to the steady on-demand system node, not to a worker that Karpenter itself may remove.

9. You run kubectl run test --image=nginx with no nodeSelector, and it starts on the system node. Why there? Name two ways to keep app pods off system nodes, and say which one is stronger.

Show answer

The scheduler puts a pod on any node that has room and no rule against it. The system node has room and no taint, so the pod lands there.

  • Way 1: nodeSelector on the pod. karpenter.sh/nodepool: general on every app Deployment. It works, but only if everybody remembers to add it.
  • Way 2: taint the system nodes and give only system pods a toleration. Now the node itself refuses everything else.
  • Taints are stronger because the rule is enforced on the node, not hoped for in each manifest. Our project uses way 1 for now. Taints and tolerations come later.

10. NodePool general allows t3.medium and m5.large, Spot only, with limits.cpu: "8". One t3.medium is running. A new pod with the right nodeSelector and a CPU request of 1800m stays Pending, and Karpenter launches nothing. How do you diagnose it? Is the 8-vCPU limit the reason? Which object would you edit?

Show answer

Read the reasons first, then do the math: the request doesn't fit on any instance type the NodePool allows.

kubectl describe pod <pod>                    # Events: the scheduler's reason
kubectl -n kube-system logs <karpenter-pod>   # Karpenter's reason
kubectl get nodepool general -o yaml          # limits and allowed types
  • The limit is not it. One t3.medium uses 2 of the 8 vCPUs.
  • Both allowed types have only 2 vCPUs. Part is reserved for the system, and every node runs DaemonSet pods (VPC CNI, kube-proxy, the CloudWatch agent…). Less than 1800m is left, even on an empty node. That matches the message "no instance type has enough resources".
  • Fix it in the NodePool (it decides what to launch): add a 4-vCPU type, or lower the pod's request. The EC2NodeClass (how to build a worker: AMI, subnets, security group, instance profile) is not involved.
  • This is the likely explanation for the test that stayed Pending in class. It was not confirmed there.
