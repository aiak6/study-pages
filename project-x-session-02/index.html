Compare

ECS vs EKS: another flavor of orchestration

  • Container orchestration = a system that manages containers at scale across many hosts. Kubernetes is the most popular one, not the only one.
  • EKS = Kubernetes software + AWS-run infra. ECS = AWS's own software, built from scratch, + AWS-run infra. ECS only runs on AWS.
Kubernetes / EKSECS
ClusterCluster
Pod specTask definition
PodTask
Deployment (+ Service)ECS service (keeps the desired count, hooks into the ALB target group)
kubectlAWS CLI / console / CloudFormation
  • ECS Fargate = serverless ECS (same idea as Lambda in Scale Session 18): you don't provision nodes, you just launch tasks and pay per compute they use. Regular ECS runs on EC2s you control (often an Auto Scaling group), which feels closer to EKS.

Nadia's current setup

users → ALB → ECS Fargate task (Flask app) → RDS Postgres around it: VPC + security groups, ECR for the image, Secrets Manager for DB creds, CloudWatch for logs & metrics
Kubernetes was one flavor. With AI you can work in a tool you've never touched: ask it to "explain ECS to me as a Kubernetes person".
Decision

Convincing Nadia: why move ECS → EKS?

  • Nadia's choice isn't bad. Setups are rarely "bad"; needs change over time. That's why we have to convince her, with reasons.

For Kubernetes / EKS

  • Huge ecosystem: tools, controllers, community support
  • Not locked to AWS: easier to move to GCP (say, with startup credits), Azure or on-prem
  • More control over servers (with EC2 nodes): spot or reserved instances to cut cost, GPU or high-memory instance types
  • Experience: "I've run big Kubernetes clusters (400 nodes) and I'm more confident there" is a valid reason too

For ECS

  • CloudWatch logs and metrics work out of the box, because both are AWS-made. Kubernetes needs extra setup for that.
  • In a big company the call might be made by an engineering manager, not you. Here, we're the decision makers.
Before you use a reason, check it's actually true. A classmate said ECS locks you into paid AWS subscriptions. Marcel pointed out Fargate has no subscription; it's pay-per-use.
Why

Situation & task: every action needs a why

  • Assignments trained us to start from the action ("create an ASG"). Real work never starts there, because every action costs time and money.
  • STAR for interview answers: Situation → Task → Action → Result. Never open with the action.

Example: Amazon Prime Video's monitoring service

StepWhat happened
SituationVideo/audio defect monitoring ran serverless on Step Functions, swapping video frames through S3
TaskCosts were high and it couldn't monitor enough streams

  • As the platform engineer there you'd have built the ECS, ASGs and EC2s, maybe with special instance types (GPU) or tuned system settings.

Refresher

PRs & branches

  • PR (pull request) = a request to merge changes from one branch into another. GitLab and Bitbucket call it an MR (merge request).
edit file → commit to new branch adjust-alarm (not main) → open PR adjust-alarm → main → merge → delete branch
  • The new branch has all of main's commits plus yours. Opening a PR changes nothing yet; only merging does.
  • He could merge his own PR only because that repo had no branch protection. With protection on, someone else has to approve. (Same as Class 32.)
Now we work in a team, even if it's AI agents, so never commit straight to main.
AI

Context engineering: how AI finds "dev"

  • Prompt engineering = asking the question well. Context engineering = handing AI the folder, the handbook and the notes before it answers. A great prompt can't help if AI doesn't have the facts.

"Where is dev?" Give it context from

  1. Repositories (infra, platform, app)
  2. Docs: Confluence, Notion, Google Docs, SharePoint, reached through MCP connectors (a later class)
  3. Communications: Slack, onboarding emails
  4. Or just ask a coworker (Nadia)
  • Agentic AI loves file systems. Clone the repo locally instead of pasting a link: it's faster, and it doesn't have to re-clone or go through the GitHub CLI every time.
mkdir ~/312-students && cd ~/312-students   # a dedicated folder, NOT your home folder
git clone git@github.com:<org>/<infra-repo>.git
git clone git@github.com:<org>/<app-repo>.git
# launch Claude Code / Codex from here (both repos) or from one repo
  • Why not ~? The agent can reach the folder you launch it from and everything under it. Launching from home exposes all your files.
  • The agent still sees global things like ~/.aws/config and its memory. Marcel's infra README had leaked his account ID and AWS profile name, so he had a sub-agent scrub all the repos and open PRs.
  • Where Claude Code / Codex live: the Code tab in the Claude desktop app (Codex tab in the ChatGPT app), the terminal CLI (claude, codex), or the web Code tab, which runs on the vendor's cloud instead of your machine.
  • Worktrees are coming in a later class.
Ticket

Deploying PR #1 to dev, end to end

  • The ask (Slack, #platform): Jordan (QA) → us: "Can you deploy PR #1 to dev today?" He didn't link the repo. The proper move is to ask, or check the linked ticket. There's only one app repo, so we found it.
  • The change (ticket PX-001): the page shows cash and shares but not the trades behind them. Add a recent trades list (latest 10). The developer wrote it, QA tested it (integration + regression tests pass), and the PR was still a draft.
  • Translate it: PR = a code change. Dev = the dev environment (a separate account/stage from staging and prod). So: get this code running in dev.

Look at what's running. AWS CLI → one task (≈ one pod), and its image tag.

the dev page now shows a recent-trades list under cash and shares.

Same loop as Kubernetes, different tool

Kubernetes: build image v2 → push to ECR → change image in Deployment → rolling update ECS here: build image v2 → push to ECR → CloudFormation change set updates the ECS service
  • Order chosen: deploy first, then merge after Jordan accepts. No CI/CD yet, so merging deploys nothing; it just keeps the change in main.
  • Rollback: the old image is still in ECR. The proper way back is to revert the CloudFormation change. A direct aws ecs update-service also works, but then CloudFormation no longer matches what's running (drift, like Scale Session 02).
  • Small correction: Marcel said "kubelet would change the container image". More precisely, the Deployment controller creates a new ReplicaSet with v2 pods, and the kubelet on each node pulls and starts them (Containers Session 06).
  • "How can I approve AI's steps in a system I don't know?" Lower the risk: ask it to explain, have a second model review it, and start in dev, where changes are cheap to undo. Humans make mistakes too, so good orgs already have guardrails: separate environments, limited access, multi-person approval for prod.
  • Deploying isn't most of the job. It's one of many request types.
Cost

AI subscriptions, usage limits & token cost

  • Subscription (Pro/Max, ChatGPT Plus/Pro) vs usage-based API billing (pay per token). Subscription is roughly 20–40x cheaper: ~$100/month can be ~$3,000 worth of API tokens.
  • Companies over ~150 users can't buy Team plans; they move to Enterprise, which is usage-based. Some give employees about $2,000/month of tokens.
  • So at work, model choice is a cost decision. A simple lookup like "where is dev?" → Sonnet, not the biggest model.
  • Chat isn't free either. Every message uses tokens from the same limit.
  • Reading the meters: Claude shows how much you've used; ChatGPT/Codex shows how much you have left. 80% in Claude ≈ 20% left; 80% in ChatGPT = 80% left.
  • Burned through Codex limits fast? Start a new Codex session and ask it to go through your usage history and say what used the most tokens.
  • Recap: get personal ChatGPT Plus (~$20); run both this month for extra credits. GPT works faster but makes slightly more mistakes than Claude.

Self-test

Quiz: check yourself

Answer each out loud first, then open the answer. Score yourself out of 10.

1. Jordan from QA posts in #platform: "Can you deploy PR #1 to dev today?" Translate that into plain words. What's the first question you need answered?

Show answer

"Get this code change running in the dev environment." A PR is a code change waiting to be merged; dev is one of several environments (dev, staging, prod), usually its own account. Before deploying anything you need to know which repo the PR is in and where dev lives (account, region, cluster/service). If the request is missing that, ask, or check the linked ticket.

2. Your company runs on ECS and you only know Kubernetes. Map these to ECS: Pod, pod spec, Deployment, kubectl.

Show answer

Pod → task. Pod spec → task definition. Deployment (+ Service) → ECS service. kubectl → AWS CLI / console / CloudFormation. The ideas match (run containers, keep N replicas, sit behind a load balancer) but it's AWS's own software, not Kubernetes, and it only runs on AWS. Fastest way in: ask AI to "explain this ECS setup to me as a Kubernetes person".

3. ECS on EC2 vs ECS Fargate. What changes for you, and how do you pay?

Show answer

With ECS on EC2 you run the servers; with Fargate you don't. On EC2 you pick instance types, run an Auto Scaling group and pay for the instances whether they're busy or not (spot/reserved can cut that). On Fargate (serverless, like Lambda) you only launch tasks and pay for the compute the containers use. Less to manage, less control over the hardware.

4. Interview question: "Why would you move a working app from ECS Fargate to EKS?" Give a balanced answer.

Show answer

Lead with the situation, give real reasons, and admit what you lose. For EKS: a huge ecosystem of tools and controllers, no lock-in (easier to move to GCP, Azure or on-prem), more control over nodes (spot/reserved, GPU or memory-heavy types), and a team with more Kubernetes experience. Against: ECS gets CloudWatch logs and metrics out of the box, while Kubernetes needs extra monitoring setup, and you take on more operations. Never say the old setup was "bad"; needs changed. And check each claim is true (Fargate has no subscription, for example).

5. You tell an interviewer: "I deployed an Auto Scaling group." Why is that weak? Rewrite it in STAR form.

Show answer

It starts with the action, so nobody knows why it mattered. Every real action costs time and money, so start with the need. Situation: the app ran on one EC2 and went down whenever it failed. Task: keep it up through instance failures and traffic spikes. Action: built a launch template + ASG behind an ALB with health checks. Result: a killed instance was replaced in ~X minutes and users saw no downtime. (Prime Video version: high cost and limited throughput → moved to ECS on EC2 → 90%+ cheaper.)

6. You paste a GitHub link into Claude Code and ask, "Where is our dev environment?" Why is cloning better, and which folder do you launch from?

Show answer

Agentic AI works best on the file system. With a link it has to go through the internet or re-clone every time. Locally it reads the README, Terraform/CloudFormation and docs instantly. Clone into a dedicated folder (~/312-students/) and launch from there or from the repo. Not from ~, because the agent can reach everything under the folder you start it in.

7. Prompt engineering vs context engineering. Why can't a better prompt find your dev account? Name three places that context can come from.

Show answer

A prompt only shapes the question; context supplies the facts. No model knows your company's account IDs, however well you ask. Give it the facts: repos (infra README, IaC), docs (Confluence, Notion, Google Docs, SharePoint, through MCP connectors), communications (Slack, onboarding emails). Or ask a coworker.

8. Marcel deployed PR #1 to dev before merging it. In a repo with no CI/CD, what does merging do? What would change once CI/CD exists?

Show answer

Without CI/CD, merging just moves the code into main; nothing gets deployed. The deploy was done by hand (build image → push to ECR → CloudFormation updates the ECS service), so testing in dev first and merging after QA accepts is safe. You still merge so the change isn't lost from main. With CI/CD, a merge (or a push to certain branches) triggers the pipeline to build and deploy automatically, so merge order matters a lot more.

9. The new version breaks dev. The app was deployed with CloudFormation. Do you run aws ecs update-service back to the old image or revert the CloudFormation change? Why?

Show answer

Revert through CloudFormation, the tool that owns the resource. The old image is still in ECR either way. update-service is faster, but then CloudFormation's template says v2 while v1 is running: drift, the same problem as clicking in the console behind Terraform's back. The next CloudFormation deploy could quietly put the broken version back. In a real emergency you might do the fast fix first, then bring the code in line right away.

10. Your company gives each engineer an API token budget. You need a quick lookup ("which README mentions dev?"). Which model do you pick, and why does this matter more at work than at home?

Show answer

Use a smaller, cheaper model (e.g. Sonnet) for simple lookups; save the biggest one for hard reasoning. At home a flat subscription hides the cost, and it's roughly 20–40x cheaper per token anyway. Companies over ~150 users are on usage-based enterprise billing, so every token is real money against a budget (some give ~$2,000/month). Choosing the right model is part of being an AI-fluent engineer.
