Concepts

The main ideas, from zero

Why a Secret file can't go into Git

  • A Secret stores values in base64. That's encoding, not encryption: base64 -d turns it back into the password (Session 09).
  • Git is where the whole team shares YAML, so a committed Secret is a password for anyone with the repo.
  • .gitignore keeps it out, but then nobody else on the team has it. Mo's example: you're off sick, the Secret gets deleted, and your teammate can't recreate it.
The fix: keep the password in AWS Secrets Manager, and commit only its address.

The External Secrets Operator: a controller that copies the password in

  • Operator / controller: a program in the cluster that watches objects and makes things match, like the Deployment controller (unit 2).
  • It is open source and not part of Kubernetes. A new EKS cluster doesn't have it; the team installs it with Helm (a package installer for Kubernetes). It runs in its own namespace, external-secrets.
  • It adds a new kind of object, the ExternalSecret, which says which AWS secret to copy and which Kubernetes Secret to write.
ExternalSecret (your ns, in Git: only a PATH) ↓ names SecretStore aws-secrets-manager (AWS region + which ServiceAccount to sign in as) ↓ uses ServiceAccount secrets-reader → IAM role (may read ONLY /26a/<your-ns>/) ↓ operator signs in to AWS as that role AWS Secrets Manager /26a/<your-ns>/investment-app (DB_PASSWORD, FINNHUB_KEY) ↓ operator writes normal Secret investment-app-secret (your ns; re-read from AWS every 1h) ↓ copied once, when the container starts pod env vars DB_PASSWORD, FINNHUB_KEY

The ExternalSecret holds the path, not the password, so it is safe to push. Reading the value still needs AWS permission on that path, or access to your namespace.

The ExternalSecret file, line by line

apiVersion: external-secrets.io/v1
kind: ExternalSecret
metadata:
  name: investment-app-secret
spec:
  secretStoreRef:
    name: aws-secrets-manager            # the SecretStore already in your namespace
  refreshInterval: 1h                    # read AWS again every hour
  target:
    name: investment-app-secret          # the Secret to write: night 1's name, so Deployments don't change
  dataFrom:
  - extract:
      key: /26a/<namespace>/investment-app   # the path in Secrets Manager; both keys are copied
  • STATUS SecretSynced, READY True means it worked. SecretSyncedError always means the operator could not read the secret; describe says why.
  • Can a teammate still see the value? Only if they have your namespace (they read the copied Secret, or exec into the pod) or AWS permission on the path.

Rotation: a running pod keeps the value it started with

10:00 password changed in Secrets Manager ("rotated") ≤11:00 operator re-reads (refreshInterval 1h) → updates the Secret running containers: still the OLD value (env copied at start) kubectl rollout restart deploy/investment-app → new pods read the NEW value
After a Secret or ConfigMap changes, replace the pods that use it. Same rule as Session 09's TICKER change.

Least privilege, made visible: asking for a classmate's password

  • Change the key to a classmate's path and apply. Kubernetes accepts the object, because the file itself is allowed. AWS refuses the read.
  • Read the error as four facts: who (the IAM role behind secrets-reader), what (GetSecretValue), where (the classmate's path), answer (no policy allows it).
  • Mo: it took him 5–6 months at his company to get Secrets Manager access. New hires get least privilege, and more is granted per ticket.

Unit 5: request, actual use, limit are three different numbers

  • A pod runs on a node (an EC2 instance) with fixed CPU and memory, shared with other pods, from any namespace. A namespace is not a machine.
  • Without limits, one busy (or DDoS'd, or buggy) pod can use the CPU and memory the others need.
NumberWho uses itMeaning
RequestThe scheduler, at placement"Put me on a node with at least this much free." Reserves scheduling room. Doesn't consume CPU and doesn't cap use.
LimitThe node, while it runsThe most the container may use. Must be ≥ the request.
Actual usekubectl topWhat it uses right now. Can be below or above the request, never above the limit.
UnitRuleExample
CPU: millicores m1000m = 1 core250m = a quarter core → four such pods fit on one core
Memory: Mi / Gi1024Mi = 1Gi (mebibytes, gibibytes)512Mi = half a GiB
m is only for CPU, never memory. Mi is not "milli".

Placement: the request must fit on one node

  • Each node offers its allocatable capacity: what's left after it reserves some for itself (kubelet, containerd, kube-proxy).
  • The scheduler adds up the requests already on each node and places the pod only where its request still fits.
  • Node A and B each have 400m free, the pod requests 600m → it fits on neither. The scheduler can't split one pod across two nodes. It stays Pending until a bigger or new node exists.

Execution: at the limit, CPU waits and memory ends the container

CPU limit reachedMemory limit exceeded
What happensThrottling. Extra work waits; the container keeps running, slowerOOMKilled (out of memory). The container is killed
ThenLatency for usersThe kubelet restarts the container in the same pod. The pod isn't replaced, and its RAM is freed
You'll seeSlow answers. Prove it with throttling metrics + response times; slow alone proves nothingRESTARTS goes up; describe: Last State: Terminated, Reason: OOMKilled
Users of a 3-pod ServiceSlower answers from that podErrors only while every pod is restarting
  • Mo's cashier analogy: one cashier, ten customers at once. Nobody is thrown out; the last one just waits a long time. That's throttling.
  • If the app needs that memory every time, it is killed again and again. A climbing RESTARTS count means read the logs and describe.
CPU over the limit gets slow. Memory over the limit gets killed and restarted.

Choosing the numbers: measure, then set, then adjust

measure → kubectl top at startup, normal traffic, peaks (one top = a snapshot) set → requests from what you saw; CPU limit for OK response time; memory limit above the highest use (+ some headroom) test → watch for throttling, OOMKilled, Pending; change when load changes
  • The developer usually knows roughly what their app needs. Mo's comparison: a PS5 game listing the space it needs.
  • Headroom: peak was 2 CPU over a week, so set 2.5.
  • Billing: you pay for the EC2 node either way. Good requests let you fit more pods per node.
  • resources: goes on each container, inside the Deployment's spec.template.spec.containers, so every replacement pod gets it.

Pending: the event says why a pod has no node

Reason in describeMeans
Not enough capacityNo node has enough free CPU or memory for the requests
Placement ruleNo node matches the pod's node requirements
Node unavailableA fitting node isn't Ready yet, e.g. one the autoscaler just started
  • PodScheduled: False + FailedScheduling = no node assigned. A pod can also be Pending after it has a node, while its image downloads.

Emphasis

What the instructor stressed

  • Never push a password to Git. Push the address (the ExternalSecret), keep the value in AWS.
  • Least privilege everywhere: per-namespace IAM roles, the read-only Claude Code from Session 10. AI agents can delete things if permissions allow it.
  • Operators are real work. Mo runs External Secrets at his job. When an app breaks over an expired secret, check describe, then the operator logs, then the secret in AWS.
  • "This red AccessDenied you'll see a lot from now on." Read it calmly as who / what / where / answer.
  • Memory → OOMKilled, CPU → throttling. Remember both. You'll read them in describe and logs at work.
  • Double-check the command you typed before deciding the cluster is broken. He mistyped top live.
  • To create any object (e.g. a ServiceAccount), search the Kubernetes docs for its YAML.

Check yourself

1. You push externalsecret-investment-app.yaml to a public repo. A stranger reads it. What can they do with it?

Show answer

Learn the path, nothing else. The file holds /26a/<ns>/investment-app, not the value. Reading it needs AWS GetSecretValue on that path, or access to your namespace.

If this one was shaky, reread "The External Secrets Operator" chain.

2. Two nodes have 400m CPU free each. Your new pod requests 600m. What do you see, and why?

Show answer

Quiz

Full self-test (10)

Answer out loud first, then open the answer. Score yourself out of 10.

1. A teammate says: "Our Secret is base64, so it's encrypted, and it's fine to commit." What do you answer, and what actually protects the value?

Show answer

base64 is encoding, not encryption. base64 -d reverses it in one command. EKS does encrypt etcd on disk with KMS, but the API server decrypts for anyone allowed to read the Secret. What protects it is who may read it (RBAC) and keeping the file out of Git.

2. Why not just put secret-investment-app.yaml in .gitignore and keep it on your laptop?

Show answer

Then the password lives only with you. Git is how the team shares the YAML. If you're off and the Secret is deleted, nobody can recreate it. Secrets Manager keeps the value where a teammate with permission can read it, and Git keeps only the path (the ExternalSecret).

3. Walk the chain from kubectl apply -f externalsecret-investment-app.yaml to DB_PASSWORD inside the app. Name every object.

Show answer

ExternalSecret → SecretStore → ServiceAccount → IAM role → Secrets Manager → Secret → pod env. The operator reads your ExternalSecret, which names the SecretStore aws-secrets-manager (region + which ServiceAccount). secrets-reader is linked to an IAM role that may read only /26a/<ns>/. The operator reads the AWS secret, writes the normal Secret investment-app-secret, and the kubelet copies it into env vars when the container starts.

4. The password is rotated in Secrets Manager at 10:00. refreshInterval is 1h. At 11:15 the app still uses the old password. Why, and what's the fix?

Show answer

The Secret was updated; the running containers weren't. Within the hour the operator rewrote the Secret, but env vars are copied once, at container start. kubectl rollout restart deploy/postgres deploy/investment-app gives new pods that read the new value, one by one, with no downtime. (Same lesson as the TICKER change in Session 09.)

5. kubectl get externalsecret shows SecretSyncedError, READY False. Where do you look, and what are the likely causes?

Show answer

kubectl describe externalsecret <name>, then the Events at the bottom. SecretSyncedError always means the operator couldn't read the secret. Usual causes: wrong path (e.g. NAMESPACE left unreplaced), permission refused (AccessDenied), the secret doesn't exist, or a wrong SecretStore name. Next: kubectl logs -n external-secrets <operator-pod>, then the secret itself in AWS.

6. Interview: you see AccessDeniedException … assumed-role/containers-26a-secrets-ana/… is not authorized to perform: secretsmanager:GetSecretValue on resource: /26a/bob/investment-app. Read it. And why did Kubernetes accept the object?

Show answer

Who, what, where, and the answer: no. Who: the IAM role behind ana's secrets-reader. What: GetSecretValue. Where: bob's path. Answer: no policy allows it. Kubernetes accepted it because the *object* is allowed in ana's namespace; the *read* is AWS's decision. That is least privilege doing its job.

7. Node A and node B each have 400m CPU allocatable left. A new pod requests 600m. What happens, what do you see, and what could still get it running?

Show answer

Pending: it fits on neither node, and a pod can't be split. The scheduler places a pod only where its request fits on one node. describe shows PodScheduled: False and FailedScheduling with not enough capacity. A cluster autoscaler can add a bigger node; the pod stays Pending until that node is Ready.

8. Under load, pod A answers slowly but never restarts. Pod B shows RESTARTS 6. Which limit did each hit, and how do you prove it?

Show answer

A: CPU limit (throttled). B: memory limit (OOMKilled). CPU over the limit makes extra work wait, and the container keeps running. Prove it with throttling metrics + response times, because slow alone could be the app's own code. Memory over the limit kills the container. describe pod shows Last State: Terminated, Reason: OOMKilled.

9. A container is OOMKilled. Is the pod replaced? What happens to its name, its IP and its memory?

Show answer

No. The kubelet restarts the container inside the same pod. Same pod name, same IP, RESTARTS +1, and its RAM is released. If the app needs that memory every time, it's killed again, so a climbing RESTARTS means read logs --previous and describe. A pod is only *replaced* when it's deleted or its node goes (ReplicaSet, unit 2).

10. A developer asks you to choose requests and limits for a new service. How do you pick them, and why is a request not "CPU the pod uses"?

Show answer

Measure first, then set, then adjust. Run kubectl top at startup, normal traffic and peaks. Set requests from what you saw, a CPU limit that keeps response time acceptable, and a memory limit above the peak plus headroom. Then watch for throttling, OOMKilled and Pending. A request only reserves scheduling room. It doesn't consume CPU and doesn't stop the container using spare CPU above it. (1000m = 1 core, 1024Mi = 1Gi.)
