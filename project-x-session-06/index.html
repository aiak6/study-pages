🌳 Root vs child modules, and why split at all

  • Root module = the folder where you run terraform init / plan / apply. It's the starting point where files turn into real resources. Each root has its own state.
  • Child module = a reusable block in terraform/modules/. It only runs when a root calls it with a module block.
  • Our roots: bootstrap (run once, makes the state bucket), network, eks. Day to day you only touch network and eks.
Root (where you run)Child it callsCreates
terraform/envs/dev/networkmodules/eks-network2 private subnets + their route table associations
terraform/envs/dev/eksmodules/eks-clusterLog group, cluster, access entry, launch template, system node group, add-ons, Karpenter's AWS side
  • One root can call one or many children. Ours call one each for now.
  • Why split? One word: scale. With 150 modules and six roots, small pieces are easier to reuse, maintain and review. It helps AI too: a smaller piece of code to read means fewer mistakes. (Same idea as Scale Session 15.)
  • Blast radius is limited first by AWS account (dev / staging / prod), then by root (each has its own state).
  • First job at a new company: find out how many roots they have and which children each one calls.
aws sts get-caller-identity          # am I logged in to the right account?

cd terraform/envs/dev/network        # root 1
terraform init                       # needs login: the state is in S3
terraform plan

cd ../eks                            # root 2, its own state
terraform init
terraform plan                       # asks for admin_role_arn (a variable with no value)

🔎 Data sources: find it, don't create it

  • resource = create something. data = read something that already exists, whether Terraform manages it or not.
  • The network root needs the VPC ID, but CloudFormation made the VPC. So it looks it up by the tags CloudFormation leaves on everything it creates:
locals {
  stack_name = "projectx-dev"
}

data "aws_vpc" "dev" {
  tags = {
    "aws:cloudformation:stack-name" = local.stack_name
    "aws:cloudformation:logical-id" = "Vpc"
  }
}

data "aws_route_table" "private_app" {
  vpc_id = data.aws_vpc.dev.id          # only search inside that VPC
  tags = {
    "aws:cloudformation:stack-name" = local.stack_name
    "aws:cloudformation:logical-id" = "AppRouteTable"
  }
}
  • Docs trick: in the Terraform Registry every type has two pages. "Resources → aws_vpc" shows how to create one. "Data Sources → aws_vpc" shows how to find one and what you can filter by.
  • "Why keep the data block after the first run?" Terraform has no chat memory. Every run it reads all the files again and checks them against state and AWS. Delete the lookup and vpc_id points at nothing, so the plan fails.
  • It's also a safety check. If someone deletes the VPC or changes its tag, the next plan fails loudly instead of building in the wrong place.
  • Use data only when you need it. If the same root creates the thing, point at the resource directly.
  • data vs import: data only reads. import makes Terraform the owner of an existing resource. Import comes later, when the VPC leaves CloudFormation.

📥 Variables, locals & outputs: which way the value moves

ObjectDirectionUsed forIn our repo
VariableInRoot → child. From terraform.tfvars. Typed by a human at the promptRoot: vpc_id = data.aws_vpc.dev.id → child: variable "vpc_id" → used as var.vpc_id
LocalStays inside one moduleName a value once, reuse it, avoid repeating codelocal.stack_name = "projectx-dev", used in both lookups
OutputOutPrint to the terminal. Child → parent. Root outputs are saved in the state fileoutput "subnet_ids" in the child, then again in the root
Data sourceA lookup, not an inputRead existing things from AWS (or from another state)data.aws_vpc.dev.id
  • Local = a local variable. That's the two-word definition. It lives only in the module that defines it: the child eks-network can't read the root's local.stack_name.
  • A local can't "become" a variable. If a child needs the value, declare a variable in the child and pass it in.
  • A variable with no value and no default makes Terraform ask you. That's why the EKS root prompts for admin_role_arn.
  • A data source is not an input by itself. It's a request to go and look. You can then use its result as an input.
  • AI likes locals too: change one line and every use changes.

🔁 for_each: one block, many resources

Two subnets, but only one resource "aws_subnet" block. for_each repeats the block once per item in a map.

# network root: the map (2 keys = 2 subnets)
private_subnets = {
  use1-az6 = { cidr_block = "10.40.32.0/19", route_table_id = data.aws_route_table.private_app.id }
  use1-az1 = { cidr_block = "10.40.64.0/19", route_table_id = data.aws_route_table.private_app.id }
}

# child module eks-network
resource "aws_subnet" "eks" {
  for_each = var.private_subnets

  vpc_id               = var.vpc_id
  availability_zone_id = each.key                 # use1-az6, then use1-az1
  cidr_block           = each.value.cidr_block    # 10.40.32.0/19, then 10.40.64.0/19

  tags = {
    Name = "${var.cluster_name}-${each.key}"      # projectx-dev-eks-use1-az6
  }
}

resource "aws_route_table_association" "eks" {
  for_each = var.private_subnets

  subnet_id      = aws_subnet.eks[each.key].id
  route_table_id = each.value.route_table_id      # the same route table for both
}
  • each.key = what's before the = (the AZ ID). each.value = everything after it. each.value.cidr_block = one field inside the value.
  • It's a repetition with different values each turn, like a for loop in programming.
  • Each copy gets its own address: module.eks_network.aws_subnet.eks["use1-az6"].
  • Add a third key → a third subnet. No change in the child module.
  • An empty map means zero copies, so Terraform would plan to destroy the existing ones. This module blocks that: a validation rule wants at least two zones, because EKS needs two AZs.
  • You can put for_each on a module block too and call the same child several times.
  • Same tool as Scale Session 08 (two app servers from one block).
  • Practice without AWS: the class 6 terraform console example.
cd terraform-console && terraform init && terraform console
> local.private_subnets
> keys(local.private_subnets)
> local.private_subnets["use1-az6"].cidr_block     # "10.40.32.0/19"

🔗 Getting the subnet IDs from the network root into the EKS root

  • Problem: the cluster needs subnet IDs. The network root made them. The eks root is a separate run with a separate memory. Nothing connects the two.
  • What the PR does: save the IDs in the network state, then read that state from the EKS root.
  1. Child eks-network declares output "subnet_ids" (zone → subnet ID).
  2. The network root publishes it again as its own output. Root outputs are written into the state file.
  3. terraform apply in network → the IDs now sit in foundation/network.tfstate in S3.
  4. The EKS root reads that file with a data source and passes the IDs down as a variable.
eks-network child → output subnet_ids → network root output → foundation/network.tfstate (S3) → eks root: data "terraform_remote_state" "network" → module "eks": subnet_ids = values(...) → the cluster
# network root
output "subnet_ids" {
  value = module.eks_network.subnet_ids
}

# eks root
data "terraform_remote_state" "network" {
  backend = "s3"
  config = {
    bucket = "projectx-dev-eks-tfstate-ACCOUNT_ID-us-east-1"
    key    = "foundation/network.tfstate"
    region = "us-east-1"
  }
}

module "eks" {
  source     = "../../../modules/eks-cluster"
  vpc_id     = data.terraform_remote_state.network.outputs.vpc_id
  subnet_ids = values(data.terraform_remote_state.network.outputs.subnet_ids)   # drop the AZ keys, keep the IDs
}
  • It's "reading the memory of another Terraform run". Really it's just reading a file in S3.
  • The read happens when you plan EKS. EKS doesn't update by itself when network changes (Session 05).
  • Order is on you: apply network first, then eks. The other way round, the EKS plan fails: there's no network state yet.
Way to shareHowGood / bad
Remote state (used here)terraform_remote_state reads the other root's outputsSimple and common in companies. Needs read access to the whole state file
Tags + data sourceGive the subnets a unique tag, look them up by tag in the EKS rootNo state access needed. You must keep the tag unique
One rootsubnet_ids = module.eks_network.subnet_idsSimplest: the parent passes the value from one child to the other. But one state and one lifecycle

⛓️ Dependencies & depends_on

  • Real clouds have an order: network before servers, cluster before workers, IAM role before cluster, policies attached before the cluster starts.
  • Obvious order = automatic. When one block references another (cluster_name = aws_eks_cluster.this.name in the node group), Terraform sees it and builds in the right order.
  • Not obvious = depends_on. A node group references its IAM role, so the role will exist. Nothing tells Terraform the policies must be attached too. Without them the worker may not come up.
resource "aws_eks_cluster" "this" {
  # ...
  depends_on = [
    aws_cloudwatch_log_group.control_plane,
    aws_iam_role_policy_attachment.cluster,
  ]
}

resource "aws_eks_node_group" "system" {
  cluster_name  = aws_eks_cluster.this.name              # reference = automatic order
  node_role_arn = aws_iam_role.system.arn
  # ...
  depends_on = [aws_iam_role_policy_attachment.system]   # explicit: wait for the policies
}
  • depends_on guarantees the order. Without it you rely on luck: it works today and fails next month when one step runs a bit slower.
  • You don't need it everywhere. The reference build has only a few, almost all about IAM.
  • Across roots there is no depends_on. You (or your AI) run network first, then eks. Run them the wrong way round and it simply fails.

📋 Reading a plan: log retention & a replaced subnet

  • AI added a CloudWatch log group for the cluster. It holds control plane logs (the system side that AWS runs), not your pod logs.
  • Logging is part of any real work. So is retention: 7, 14 or 30 days is usually enough. Keeping logs forever costs money.
  • Here retention comes from a variable with a default: log_retention_days = 14. The root doesn't set it, so 14 is used.
  • To change it, set it in the root, inside the module "eks" block:
module "eks" {
  # ...
  log_retention_days = 30
}
# module.eks.aws_cloudwatch_log_group.control_plane will be updated in-place
  ~ retention_in_days = 14 -> 30

Plan: 0 to add, 1 to change, 0 to destroy.

A scarier edit, in the network root: change one subnet's CIDR (from the class rehearsal, which used small /24 subnets).

# module.eks_network.aws_subnet.eks["use1-az6"] must be replaced
-/+ cidr_block = "10.40.96.0/24" -> "10.40.98.0/24" # forces replacement
# module.eks_network.aws_route_table_association.eks["use1-az6"] must be replaced

Plan: 2 to add, 0 to change, 2 to destroy.
  • A subnet's CIDR can't be edited in place, so Terraform destroys and recreates it. The association points at the subnet ID, so it's replaced too. One edit, two replacements.
  • Read the last line first: add / change / destroy. If destroy isn't 0, find out exactly what dies before you type yes.
  • Before any plan, check three things: the folder (which root), the account (aws sts get-caller-identity), the state key (foundation/eks.tfstate).

🌊 Drift: the files always win

files (the code) → state (Terraform's memory) → actual environment (AWS)
  • Drift = reality no longer matches the files. Example: Git says log retention 14 days, someone sets 7 in the console.
  • Nothing happens by itself. Drift is only found when you run plan or apply.
  • The next run compares all three and plans to put AWS back to what the files say: 7 -> 14. It doesn't tell you who changed it.
  • Terraform is file-first. To change something properly: edit the file → apply → state and AWS follow.
  • Careful with "the files fix everything". Files say what should exist. State is how Terraform knows what already exists. If the state itself is lost or broken, restore it first (Session 05). Don't apply a plan that wants to create everything again.

🚪 How we, the workers and the pods reach things

Workers / pods → outsidePrivate subnet → AppRouteTable → NAT gateway in the public subnet → internet and AWS services (ECR, S3, EC2 API)The NAT gateway CloudFormation already made
  • Every kubectl command (get, delete, run) goes to the API server. That's the only door we use.
  • A network route gets your request to the API. It doesn't give you permission.
  • Human access = two checks (Containers Session 10): your AWS identity (IAM role) → an EKS access entry + policy maps it to a Kubernetes identity → Kubernetes permissions (RBAC).
  • Pod access to AWS: an app pod that reads files from S3 (the example was a video-processing app) needs AWS permission. Simple way: give it to the worker's IAM role, and every pod on that worker gets it. Pod-level permissions come in a later class. The EKS Pod Identity Agent add-on is already installed for that.
aws eks update-kubeconfig --region us-east-1 --name projectx-dev-eks
kubectl config current-context        # check the context before anything else
kubectl get nodes
kubectl -n kube-system get pods       # the add-on pods
kubectl auth whoami                   # which Kubernetes identity am I?
  • Three kinds of IAM role here: yours (human), the cluster role, the node role. Every cluster gets its own cluster and node roles. A role lives in one account, so another account means another role.
  • How does a worker join the cluster? We use an EKS managed node group (aws_eks_node_group), not a plain Auto Scaling group. EKS launches workers from its own AMI with kubelet already inside and hands them the cluster name. With the node role's permissions they join.
  • Want to really understand joining? Swap the managed node group for a plain Auto Scaling group and make the node join yourself.

Self-test

Check yourself

Answer each question out loud first, then open the answer. Score yourself out of 10.

1. An interviewer asks: "What's the difference between a root module and a child module? And what happens if I run terraform apply inside modules/eks-network?"

Show answer

The root is where you run Terraform and where the state lives. The child is a reusable block that a root calls. A root has a backend, provider settings and real values. A child only has variables waiting for values.

If you run Terraform inside the child folder, Terraform treats that folder as a root. There's no S3 backend there, so it starts a new empty local state, and it asks you to type vpc_id, cluster_name and private_subnets. It knows nothing about the subnets that already exist and would try to make new ones. That's why you always run from terraform/envs/dev/network.

Think of the child as a recipe and the root as the cook who actually turns on the stove.

2. The network root creates the subnets. The EKS root needs their IDs. Give three ways to get the IDs across, with one trade-off for each.

Show answer

Remote state, tags plus a data source, or one root.

  • Remote state (what the PR does): the network root publishes subnet_ids as a root output, it lands in network.tfstate, and the EKS root reads it with terraform_remote_state. Simple, but EKS needs read access to the whole network state file, and it only sees new values when you plan EKS again.
  • Tags + data source: tag the subnets with something unique and look them up in the EKS root. No state access needed, but the tag has to stay unique and correct.
  • One root: call both children from one root and write subnet_ids = module.eks_network.subnet_ids. Simplest, but now network and cluster share one state and one lifecycle.

Bonus from Session 05: publish the IDs to SSM Parameter Store and read them with a data source.

3. A teammate says: "The subnets exist now, so I deleted the data "aws_vpc" "dev" block. We already know the VPC ID." What happens on the next terraform plan in the network root, and why?

Show answer

The plan fails. The module call still says vpc_id = data.aws_vpc.dev.id, and the route table lookup uses it too. Terraform reports a reference to something that isn't declared.

Terraform has no chat memory. Every run it reads all the files again and checks them against state and AWS. A lookup is not a one-time step.

He could hardcode the ID and the plan would work. But he'd lose the safety check: today, if someone deletes the VPC or changes its tag, the lookup fails loudly instead of building in the wrong place.

4. In private_subnets you rename the key use1-az1 to use1-az2 and keep the same CIDR. What does the plan show, and why isn't it "1 to change"?

Show answer

It destroys the old subnet and its association and creates new ones: 2 to add, 2 to destroy.

With for_each, the map key is the identity of the copy: aws_subnet.eks["use1-az1"]. A new key is a new address, so Terraform sees a brand-new resource. The old address has nothing in the files any more, so it's destroyed.

Here it's even stronger: the key is also used as the AZ ID, and a subnet can't move to another zone in place.

And it doesn't stop there. The network state now holds a different subnet ID, so the next EKS plan reads different subnets for the cluster. On a live cluster that's a big change.

Lesson: for_each keys are names. Pick stable ones and don't rename them casually.

5. You change one subnet's cidr_block. The plan ends with Plan: 2 to add, 0 to change, 2 to destroy. You edited one value. Why 2 and 2? Would you apply it on a cluster with running workers?

Show answer

A subnet's CIDR can't be changed in place, so the subnet is replaced. The route table association points at the subnet's ID, so it's replaced with it. In the plan you see -/+ and # forces replacement.

On a live cluster: no, not like this. Workers and their network interfaces live in that subnet. AWS won't delete a subnet that still has network interfaces in it, so the apply would get stuck or fail halfway. If it did go through, the nodes in that zone would be gone.

Safer: add a new subnet next to it (one more key in the map), move the workloads, then remove the old key.

Habit to keep: read the add / change / destroy line first, then find every line that says "must be replaced".

6. The node group block already has node_role_arn = aws_iam_role.system.arn. Why does the code still add depends_on = [aws_iam_role_policy_attachment.system]?

Show answer

The reference only guarantees the role exists. It doesn't guarantee the policies are attached to it.

The role and its policy attachments are separate resources. When Terraform sees no link between two things, it's free to build them in any order or at the same time. So a worker could boot with an empty role: it can't register with the cluster and it can't pull what it needs.

depends_on makes the order guaranteed. Without it, it may still work today, by luck, and fail next month when one step runs a bit slower.

Rule of thumb: references handle the obvious order. depends_on is for the order Terraform can't see.

7. The code says log retention is 14 days. Someone sets it to 7 in the console. (a) What does Terraform do right now? (b) What does the next plan show? (c) The team actually wants 7. What's the right fix?

Show answer

(a) Nothing. (b) ~ retention_in_days = 7 -> 14. (c) Change the file, then apply.

  • Drift is only found when someone runs plan or apply. Until then files and state say 14 and AWS says 7.
  • The next run compares files, state and AWS and plans to put AWS back to what the files say. It doesn't tell you who changed it.
  • If 7 is what you want, set log_retention_days = 7 in the root's module "eks" block, commit, apply. If you leave it as a console change, the next apply by anyone on the team quietly reverts it.

Terraform is file-first.

8. Inside the child module eks-network you write Name = "${local.stack_name}-subnet". The local is defined in the network root. What happens, and how do you fix it?

Show answer

Error: the child can't see the root's locals. A local lives only in the module that defines it. That's what "local" means.

Fix: declare variable "stack_name" in the child, and pass it from the root's module block: stack_name = local.stack_name.

Easy way to remember: a local is a note on your own desk. A variable is the door between two modules. An output is the door going the other way.

9. You run kubectl get nodes against the Dev cluster. Case A: it hangs and then times out. Case B: it answers at once with Unauthorized or Forbidden. Which layer do you check in each case?

Show answer

A = the network path. B = permissions.

  • Timeout: the request never reached the API server. Is the endpoint public or private? Do you need the VPN? Is your IP allowed? Does your kubeconfig point at the right cluster?
  • Fast "no": you reached the API server, and it refused you. Now walk the two checks from Containers Session 10. First the AWS identity: right profile, session not expired, is there an EKS access entry for this role? Then Kubernetes: does the access policy or RBAC role allow listing nodes?

Useful commands: aws sts get-caller-identity, kubectl config current-context, kubectl auth whoami.

A route gets your request to the door. It doesn't open the door. Same idea as "timed out vs refused" from Scale Assignment 04.

10. terraform apply on the EKS root says "Apply complete". kubectl get nodes shows one node. You deploy the app with 4 replicas and most pods stay Pending. What's going on, and what step is missing?

Show answer

The cluster isn't finished: the Karpenter controller was never installed.

  • The one node is the managed system worker (t3.medium, min 1, max 1). It runs the add-on pods and can't grow.
  • Terraform built only Karpenter's AWS side (IAM roles, instance profile). The controller and its capacity rules come from terraform/platform/install.sh, which uses Helm.
  • Until that runs, nothing is watching Pending pods, so no general workers are launched.

How you'd confirm: kubectl describe pod shows a scheduling event like "0/1 nodes are available", and kubectl -n kube-system get pods shows no Karpenter pod.

Lesson: "Apply complete" means Terraform did what the files say. It doesn't mean the platform is complete.
