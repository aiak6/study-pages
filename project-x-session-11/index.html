Session 11: Application CI and a manual Dev release

Thu, Nov 19, 2026Ticket PX-109 — weekend taskSources: class recording, written notes, class materials, CI teaching page

Everything so far has been built by hand. This is the class where the building starts happening by itself. It opens by tracing a request all the way back — past the ALB, past the Service, past the Pod — to the one thing that actually answers you: a running process. That distinction (an image is just files; a container is files plus a process) is what makes the rest make sense. Then the same journey in reverse: from a developer typing code to that process running, and the realisation that a developer should only ever do two steps — write it, push it — and everything after is our job to automate. That's CI. The class built it live in GitHub Actions: push to a feature/* branch, build the image, run nine tests against a throwaway Postgres, then log into AWS through OIDC and push to ECR tagged with the Git commit ID. It failed twice before it worked. And it deliberately stopped short: a new image in ECR is not a running app, so the release itself was still a manual helm upgrade.

🔎 Tracing a request all the way back to the code

The class started by following one browser request backwards through everything built since Session 06.

  ↓

  ↓

  ↓

  ↓
a RUNNING PROCESS   ← this is the thing that actually answers
  • Which Pod answered? A classmate suggested exec; the answer is logs: kubectl -n main-product-line logs <pod> --tail 3.
  • A nice accident in the demo: plain page loads weren't logged, but a buy was — so he bought a share to make the serving Pod reveal itself. The balance change on screen matched the log line.
  • Then he deleted the Pod that was serving him — and the page kept working. The next request simply went to the other Pod, and the data was unchanged.

🔑 That's what "stateless" means. The Pods hold no state; the trades live in RDS, outside both of them. Add Pods, delete Pods — it doesn't matter as long as enough remain. It's fine to kill a Pod in production. That's exactly why Deployment is the default workload type.

  • A classmate was surprised how fast the replacement became Ready — a few seconds, because the readiness probe's initial delay is 3 seconds (Session 08).
  • What would a user actually notice? Only if all Pods were down, all were overloaded, or the database was down.

🧠 Image vs container, package vs runtime

The question that drove the whole first half: "What exactly inside a container gives us back the response?" Not the server, not the API — a running process. A process is what uses CPU, RAM and storage. Without one, you have files that do nothing.

ImageContainer
What it isA bunch of filesThe image with running processes
NeedsOnly storageCPU, RAM, storage, power
Answers requests?NoYes

💡 Two analogies worth keeping:

  • A downloaded app. The installer file is dead — just files. It becomes something only when you open it, and opening it starts processes.
  • A brain. A dead brain is biomaterial. A living one has neurons firing — and it's burning energy. Same with a process and CPU.

The same distinction has a formal name: package vs runtime. Runtime is the package while it's actually running.

🔑 "You could put an image on a USB stick and keep it for 1,000 years and it still wouldn't do anything." This is why pushing to ECR is not deploying — the point the whole class builds toward.
kubectl -n main-product-line get pods
kubectl -n main-product-line describe pod <pod> | grep -i image
# the part before the colon is the ECR repository address
# the part after the colon is the TAG you chose
# the sha256 line is the image's own digest — a different thing

A classmate asked whether EKS still needs permissions to pull from ECR when both are in the same account. Yes — simpler permissions, but still permissions.

🛤️ The other direction: from a developer's keyboard to a running process

Creation: a developer writes code in an editor or an agent tool. Destination: running, with processes, in the Kubernetes cluster. What happens in between?

#StepThe decision it hides
1Write the code—
2Add it to version control (Git)Standard practice: history, and somewhere to go back to
3Package it — build the imageWhere does this happen, and who does it? Packaging needs a machine
4Run automated testsBefore, during or after packaging
5Store the package somewhere reachableWhere · permissions · network access
6Deploy (kubectl apply / helm upgrade)Which version? There are many

Why store it at all? Because an image built on your laptop isn't reachable by the cluster's workers. It has to live somewhere they can pull from.

# how it works today, by hand
cd <app folder>            # where the Dockerfile is
docker build -t <name> .
aws ecr get-login-password ... | docker login ...   # and you need permissions
docker push <ecr-repo>:<tag>

🔑 The target state: a developer should only ever do steps 1 and 2. Everything from step 3 onward happens on its own, in seconds or minutes.

🔑 "That's the design of modern engineering platforms — and we are the people who set up the rest." Steps 3–6, automated, are exactly what CI/CD names.

☁️ Why run the build on a cloud runner instead of your laptop

A runner is a machine provisioned to do one short job and then disappear. GitHub Actions provides them.

ReasonWhy it matters
Doesn't depend on your machineLaptop closed, you're asleep, you're on holiday — it still runs
Choose the machineNeed Linux when you're on a Mac? More CPU or RAM? Pick it
SecurityPermissions live on an isolated datacenter machine, not on the laptop you might leave in a restaurant
🔑 Automatic triggerThe big one. Any push or merge starts the job. Nobody has to remember, be in the right folder, or have the right permissions
  • Without it, somebody has to sit down, be in the right directory, run the right commands, have the right credentials, and do it at the right moment. Every single time.
  • These are short-lived machines, not an EC2 you manage. GitHub creates one, runs the job, deletes it.
  • 💡 The runner spec, for the interview: ubuntu-latest gives 2 CPUs, 8 GB RAM, 14 GB storage on private repos, and already has Docker, Docker Compose, kubectl and Helm installed. Windows and macOS runners exist but cost noticeably more, so Linux is what nearly everyone uses.
  • Self-hosted runners (your own EC2s or Kubernetes containers) are supported, usually for compliance reasons — a company that won't run jobs on GitHub's servers. Extra setup, but not difficult.

🤝 What the "I" in CI actually means

A fair question: why is it called continuous integration and not just "automation"? Integration is the ordinary English word: bringing changes together.

DeveloperChange
ARename the database field price → trade_price (to avoid confusion with another price)
BWrite code that reads price from the database
  • Each change works on its own. Put them together and the trade history page breaks.
  • 🔑 So CI is: merge changes from different people frequently, and automatically check that the combined app still works. The automation is the means; the integration is the point.
  • Integration tests are the tests that specifically check several features still work together.
  • Whose job are the tests? Developers or QA write them — not the platform engineer. "Our job is to make sure they run, and that the job fails if they fail."
  • The app's nine existing tests check things like: paginating trade history (create 12 trades, the page must show exactly 10) and buy/sell regressions.
  • 💡 AI is now very good at writing test cases — but deciding they run on every change is still a platform decision.

⚙️ GitHub Actions: triggers, runners, jobs and steps

A workflow is just a YAML file in .github/workflows/ in the repo. Nothing to click, nothing to install. The class built a throwaway demo job first, to see the shape before the real thing.

name: GitHub Actions basic job demo

on:                       # WHEN it runs
  push:
    branches: [ "feature/*" ]   # no branches: key at all → ANY branch
  pull_request:
    types: [ opened ]
  workflow_dispatch:      # a manual button in the GitHub UI
  # schedule:
  #   - cron: "0 23 * * *"      # cron-style, e.g. the class's own publishing job

jobs:
  do-something:
    runs-on: ubuntu-latest        # WHICH machine
    steps:
      - uses: actions/checkout@v4 # a ready-made action
      - run: echo "hello"         # a raw command
      - run: |
          echo "${{ github.repository }}"
          ls
TriggerWhen it fires
pushA change lands in a matching branch (including a merge)
pull_requestA PR is opened
workflow_dispatchYou click a button in the Actions tab
scheduleCron-style, on a timer
  • 🔑 Jobs fail fast. If any step fails, the whole job aborts — which is the entire safety mechanism: a failed test can never reach the push step.
  • The workflow is always tied to its own repository. A classmate asked how checkout knows which repo — it defaults to the one the workflow lives in; another repo has to be named explicitly.
  • Where to watch it: the repo's Actions tab shows every run, its branch, each step and its output.
  • 💡 It isn't only for builds. The class's own recording-publishing pipeline is a scheduled GitHub Actions job: it checks Vimeo for new recordings, publishes them to the site and posts to Slack.

🧩 uses vs run: why they're called "actions"

KeywordWhat it is
run:A raw shell command on that machine. Nothing prepackaged
uses:A ready-made action — a packaged tool that does a whole process for you

The comparison that makes it click. To log into ECR by hand you'd run aws ecr get-login-password ... | docker login ... — and first work out your region and account ID. That's 10–15 lines once you include assuming a role and setting credentials. Or:

- uses: aws-actions/amazon-ecr-login@v2      # ...just this

AWS publishes official actions under aws-actions/: configure-aws-credentials (log into AWS — give it a role and a region), amazon-ecr-login, and a Secrets Manager retrieval action which can even transform the values it fetches.

🔑 This is the interview point. Actions are GitHub Actions' main differentiator against Jenkins, GitLab CI/CD and CircleCI — those run jobs too, but none has this library of prepackaged steps. It's a big part of why so many teams moved.

  • 💡 Context worth having: GitHub Actions launched in 2019; GitLab CI and Jenkins are much older. GitHub is owned by Microsoft, so trusting GitHub Actions means trusting Microsoft.
  • A classmate confused GitLab with GitHub — they're separate competing companies, each with their own hosting and their own CI tool.
  • Each action has its own documentation. If you need something non-default (pushing to a different AWS account, say), that's where the option lives.

🛠️ The real pipeline: build-test-push.yml

The plan, written out before any YAML: clone the repo branch · build the image · run the tests · log into AWS as an IAM role · log into ECR · push the image.

🔑 The prompting method is worth copying. Rather than asking for YAML straight away, he asked the AI to write the workflow in plain English first, following the shape of a workflow but without syntax — "so I can explain the job to somebody in English" — and kept that file as plain-english.md. Only then: "Now build an actual YAML… Make it minimal and simple as possible. Don't overcomplicate it." His reasoning: "Spending time on GitHub Actions syntax, I don't believe that's going to be worth our time. Nobody's going to question you on the syntax."

name: Build, test and push to Dev ECR

on:
  push:
    branches: [ "feature/*" ]     # only feature branches trigger this

env:
  AWS_REGION: us-east-1
  ECR_REPO: investment-app
  IMAGE_TAG: ${{ github.sha }}    # the Git commit ID as the version

jobs:
  build-test-push:
    runs-on: ubuntu-latest
    services:
      postgres:                   # a throwaway DB, on the same runner, for the tests
        image: postgres:16
    steps:
      - uses: actions/checkout@v4                 # 1. get the code
      - run: docker build -t $ECR_REPO:$IMAGE_TAG ./candidate/   # 2. build
      - run: python -m unittest discover          # 3. nine tests
      - uses: aws-actions/configure-aws-credentials@v6
        with:
          role-to-assume: ${{ vars.AWS_ROLE_ARN }}   # 4. log into AWS
          aws-region: ${{ env.AWS_REGION }}
      - uses: aws-actions/amazon-ecr-login@v2     # 5. log into ECR
      - run: docker push <account>.dkr.ecr.$AWS_REGION.amazonaws.com/$ECR_REPO:$IMAGE_TAG
  • The services: block starts a Postgres container on the same runner purely so the tests have a database. It is completely separate from the real RDS — a classmate asked exactly this, and the answer is that tests don't need the real environment.
  • 🔑 IMAGE_TAG: ${{ github.sha }} is the detail to remember. The image is tagged with the full commit ID, so from any running image you can find the exact code that produced it. He proved it live: git log's newest commit ID matched the tag in ECR character for character.
  • Nothing happened on the first push — because his branch was named codex/... and the trigger only matches feature/*. He created feature/ci-cd and it fired.
  • 💡 He also moved an older standalone test workflow into an archive/ folder, because those tests now run inside this job. Two workflows doing the same work is noise.

🔐 OIDC: how an IAM role trusts something outside AWS

The first real run got all the way to "Login to AWS" and failed. Expected — the runner had no credentials yet.

🔑 Never put AWS access keys in GitHub. The best practice is an IAM role that trusts GitHub through OIDC.

What OIDC (OpenID Connect) is: a protocol that lets AWS establish a trust relationship with something that isn't an AWS resource. Normally you attach a role to an EC2 instance, a Lambda, an EKS cluster. OIDC extends that to a Kubernetes Pod (this is what Pod Identity does — Session 10, Containers Session 11), a GitHub Actions runner, cloud-hosted AI agent sessions, and anything else that can present a token.

StepWhereValue
1. Add an identity providerIAM → Identity providers → OpenID ConnectURL https://token.actions.githubusercontent.com, audience sts.amazonaws.com
2. Create a roleIAM → Roles → Web identityPick that provider, then narrow it to your organisation and repository (a branch too, if you want)
3. Attach permissionsThe role's policiesECR push rights. He took a shortcut with a broad image-builder policy and said so out loud — a repo-scoped custom policy would be tighter
4. Give GitHub the role ARNRepo → Settings → Secrets and variables → ActionsA repository variable named AWS_ROLE_ARN
SyntaxComes from
${{ vars.X }}A repository variable — non-sensitive configuration
${{ env.X }}The env: block in this workflow file
${{ secrets.X }}A repository secret — sensitive values, hidden in logs

💡 Narrowing the trust to one org and one repo is the whole security story: only jobs from that repository can assume the role. You can go further and scope it to a single branch.

🐛 Two failures debugged live (the most useful part)

Even with the role in place, the job still failed at login. Twice. Both are worth knowing.

Failure 1 — the AI wrote an outdated action version

The step sat on configure-aws-credentials without progressing. A classmate suggested the action version, and the docs confirmed v6 was current while the workflow pinned something older. 🔑 His read on why: "AI probably wrote it from memory, and it might have used some old version." A good thing to check first whenever a ready-made action behaves oddly.

Failure 2 — GitHub's new immutable subject

Not authorized to perform sts:AssumeRoleWithWebIdentity

🔑 His first move was the right one: "Is this a GitHub permission or an AWS permission?" — decide which side is refusing before you start changing things. The message pointed at the AWS side.

The cause was genuinely new: GitHub now puts numeric organisation and repository IDs into the OIDC token's sub claim (the "immutable subject" change). A trust policy written the old way — with just the org and repo names — no longer matches. The fix: update the StringLike condition in the role's trust policy to include those numeric IDs, one entry per repository.

💡 He was candid that he'd never seen this before and that it hadn't been like this five months ago. Even the documented path can be stale — read the actual error.

With that fixed, the run went green: logged into AWS, logged into ECR, pushed the image. He then spotted a leftover manual run: login he'd written while demonstrating, sitting redundantly next to the action — and removed it.

🚀 The release: where CI stops and CD would begin

To show the whole path end to end, he played the developer: a real application change, from ten recent trades to five. The AI touched several files — the query, the page text, and the tests (which asserted 10 and now assert 5). Then: git commit, git push. And that is the entire developer experience.

StepWho does itWhat happened
1. Change the codeDeveloper10 → 5 recent trades
2. Push to GitDeveloperTheir job ends here
3. Build + test + pushAutomaticA new image reached ECR, tagged with the commit ID
4. DeployStill a humanEdit the tag in values-dev.yaml, run helm upgrade
🔑 "Nobody's watching it. We're watching because we want to see it, but generally nobody cares about this unless something fails." That is what success looks like.
# the manual half — this is what next class automates
# values-dev.yaml:  image.tag: <the new commit ID>
helm upgrade --install investment-app charts/investment-app \
  --values charts/investment-app/values-dev.yaml -n main-product-line

kubectl -n main-product-line get pods -o wide
  • The rollout behaved exactly as Kubernetes should: the new Pod went Pending first (Karpenter had to bring up a node), and the old Pod kept serving until the new one was Ready. Then the page showed five trades.
  • 💡 The image tag belongs in values-dev.yaml, not the shared values.yaml — he caught himself putting it in the wrong file and moved it. Each environment runs its own version (Session 09).
  • Older trades were still there in RDS. Only the view changed; the data never moved.

🔑 The gap this leaves is the whole point: a green pipeline means a new image exists. The running Deployment doesn't care until someone changes the tag. CI got the package made and stored; CD gets it running.

🏢 How promotion works at a real company

Several classmates asked variations of the same thing: does every push go to production? 🔑 No. This pipeline deploys to Dev only. Reaching production takes a lot more.

  • Humans still control promotion — but they do it through Git: merging into a particular branch, or adding a Git tag. A specific, defined Git event triggers a deployment to the next environment.
  • Changes can move one at a time or grouped: several changes can sit in staging and be released to production together.
  • Each environment runs the same checks, and usually a few more as you get closer to production.
  • 💡 On scale: the class's scale matrix cites Square running ~300 builds a day for a single iOS app. Running the pipeline often is the normal state, not an exception. And it's cheap — you pay a small amount per run.
  • 💡 Where manual QA fits was asked repeatedly. The honest answer: not yet. These nine automated tests are not a QA sign-off — the same point as the missing sign-off in Session 10. Dev/staging/production as a full flow is a later topic.

1. An interviewer asks: "You push a new image to ECR. Is the new version live?" Answer it, and explain the difference you're relying on.

Show answer

No. An image is a package sitting in storage; nothing is running until something starts a process from it.

  • An image is a bunch of files. It needs only storage. You could keep it on a USB stick for a thousand years and it would never answer a request.
  • A container is that image with running processes. It needs CPU, RAM and power. That process is the thing that actually returns a response.
  • The same distinction is package vs runtime: the runtime is the package while it's actually running.
  • So the running Deployment keeps serving the old image until someone changes which image it uses — the tag in values-dev.yaml plus a helm upgrade.
  • 🔑 That gap is exactly the CI / CD boundary. CI produced and stored the package; CD would get it running.

💡 Good analogy to reuse: a downloaded app installer is dead files. It becomes something only when you open it — and opening it starts processes.

2. Your app is serving traffic from two Pods. You delete the exact Pod that just answered your request. What does a user see, and what single design fact makes that true?

Show answer

Nothing — the next request goes to the other Pod. It works because the Pods hold no state: the trades live in RDS, outside both of them.

  • The Service keeps routing to whichever matching Pods are Ready, so the remaining Pod simply answers.
  • The data is identical because it was never in the Pod. The replacement Pod starts empty of state and reads the same database.
  • The new Pod became Ready in seconds — the readiness probe's initial delay is about 3 seconds.
  • 🔑 This is what stateless means, and it's why Deployment is the default workload type: it's fine to kill a Pod, even in production.
  • What a user would notice: all Pods down, all Pods overloaded, or the database down.

💡 To find which Pod answered, read its logs, not exec. In the demo plain page loads weren't logged but a buy was, so the instructor bought a share to make the serving Pod reveal itself.

3. Trace a code change from a developer's editor to a running process. Name every step — and say which two steps the developer should be doing.

Show answer

Write → commit to Git → package → test → store → deploy. The developer should only do the first two.

  1. Write the code.
  2. Add it to version control — history, and a place to roll back to.
  3. Package it (build the image). Hidden decision: where does this happen, and who does it? Packaging needs a machine.
  4. Run automated tests — before, during or after packaging.
  5. Store the package somewhere reachable (ECR). Hidden decisions: where, permissions, network access.
  6. Deploy (kubectl apply / helm upgrade). Hidden decision: which version?
  • Why step 5 exists at all: an image built on your laptop isn't reachable by the cluster's workers.
  • 🔑 Steps 3–6 automated is the definition of CI/CD, and building that is the platform engineer's job.

💡 A strong closing line for an interview: done right, a developer pushes and the change is running within minutes, and nobody watches it happen unless something fails.

4. Your teammate says "I can just run docker build and docker push from my laptop — why pay for a cloud runner?" Give the reasons, and say which one actually matters most.

Show answer

Four reasons — and the one that matters is the automatic trigger, not the machine.

  • Independence: it doesn't need your laptop powered on, connected, or you being awake and available.
  • Machine choice: you need Linux and you're on a Mac, or you need more CPU and RAM than your laptop has.
  • Security: the AWS permissions live on an isolated datacenter machine instead of the laptop you might leave in a restaurant.
  • 🔑 The automatic trigger. Without it, a person must sit down, be in the right folder, run the right commands, hold the right credentials, and do it at the right moment — every time, for every change.
  • That's the real argument: the laptop version is not harder, it's manual, and manual doesn't scale or survive someone's holiday.

💡 Runner facts worth having ready: ubuntu-latest gives 2 CPUs, 8 GB RAM, 14 GB disk, with Docker, Compose, kubectl and Helm pre-installed, and it's destroyed when the job ends.

5. Why is it called continuous integration rather than just "build automation"? Give a concrete example of what it catches.

Show answer

Because the point is bringing several developers' changes together often and proving the combined app still works. The automation is the means, not the meaning.

  • "Continuous" = merge frequently and check every time, instead of a painful big merge later.
  • 🔑 Who writes the tests? Developers or QA — not the platform engineer. "Our job is to make sure they run, and that the job fails if they fail."

7. You want the runner to push to ECR. A teammate suggests creating an IAM user and putting its access key in GitHub Secrets. What do you propose instead, and how does it work?

Show answer

No long-lived keys — an IAM role that trusts GitHub through OIDC, so the runner gets temporary credentials.

  • OIDC (OpenID Connect) lets an IAM role trust something that isn't an AWS resource. Normally a role attaches to an EC2 instance, a Lambda or an EKS cluster; OIDC extends that to a GitHub runner, a Kubernetes Pod, or a cloud-hosted agent session.
  • The setup: (1) add an OIDC identity provider in IAM — URL https://token.actions.githubusercontent.com, audience sts.amazonaws.com; (2) create a role with Web identity trust scoped to your org and repository; (3) attach ECR push permissions; (4) store the role ARN as a GitHub repository variable.

8. Your workflow fails with Not authorized to perform sts:AssumeRoleWithWebIdentity. Walk through how you'd diagnose it — and name the specific recent change that causes this.

Show answer

First decide which side is refusing, then check the trust policy — GitHub now puts numeric org and repository IDs in the token's subject.

  • 🔑 The first question is the right one: "is this GitHub refusing to give me a token, or AWS refusing to accept it?" The wording points at the AWS side — the token arrived and the role declined it.
  • That narrows it to the role's trust policy, not the workflow, not the permissions policy.
  • The cause: GitHub's immutable subject change puts numeric organisation and repository IDs into the OIDC token's sub claim. A trust policy matching only org and repo names no longer matches.
  • The fix: update the StringLike condition in the trust policy to include those numeric IDs, one entry per repository.
  • The other failure the same day: the AWS login action was pinned to an old version (v6 was current). "AI probably wrote it from memory." Check the action's version when a ready-made step behaves oddly.

💡 The honest takeaway: this was new enough that the instructor had never seen it and it hadn't been that way five months earlier. Documentation and AI both go stale — read the actual error.

9. Your pipeline tags images with ${{ github.sha }}. A teammate wants latest instead — "simpler, and you don't have to update the Helm values every time." What's your answer?

Show answer

The commit ID is the point: it ties a running image back to the exact code that made it. latest throws that away and makes deploys unrepeatable.

  • With the commit ID you can take any running Pod, read its image tag, and find that exact commit in Git. The instructor proved it live — git log's newest commit matched the ECR tag character for character.
  • latest is a moving pointer. Two deploys of "latest" can be different code, and you cannot tell afterwards which is running or roll back to a known build.
  • It also breaks the thing they think it fixes: having to choose the version is a feature. It's what lets you promote a specific, tested image from Dev to Staging to Production.
  • And nothing would change in the cluster anyway — the tag string stays identical, so Kubernetes may not pull at all.
  • 🔑 Traceability and repeatability. With the commit ID the deploy is a deliberate choice; with latest it's a guess.

💡 Put that tag in values-dev.yaml, not the shared values.yaml — each environment runs its own version (Session 09).

10. Your CI pipeline is green and the new image is in ECR. The product manager asks whether every push now goes straight to production. Answer it, and describe what actually controls promotion.

Show answer

No. This pipeline reaches Dev, and only Dev. Humans still control promotion — but they do it through Git.

  • The Class 11 workflow built, tested and pushed. It did not deploy anything at all: the release was a manual helm upgrade.
  • Even once deployment is automated, it targets Dev. Getting to production takes considerably more.
  • What controls promotion: a specific Git event — merging into a particular branch, or adding a Git tag. A person decides; the automation reacts.
  • Changes can move one at a time or grouped — several can sit in staging and go to production together.
  • 🔑 The shape to remember: everything is automated except the Git change.

💡 Two honest caveats: nine passing tests are not a QA sign-off (the same gap as Session 10's missing developer/QA confirmation), and running often is normal — the scale matrix cites Square at ~300 builds a day for one iOS app.
