What, where, why.

Follow the build from Terraform to a working investment app, then put Helm and Karpenter in their proper places. Every stop connects a concept to the files and the reason for the decision.

Lab status: the personal EKS/ECS/RDS lab was verified and removed. The app ran live with a managed node group. Helm was checked locally afterward. Karpenter was not installed in this lab. This page is a study guide; its controls do not contact AWS.

01 · Start with the outcome

A place to run containers. Then a real app.

PX-107 established the Kubernetes foundation. PX-108 used that foundation to run the investment app against the same private RDS database as ECS.

The relationship between the tickets
PX-107 · infrastructureNetwork → EKS control plane → worker → add-ons
Smoke testA small web workload proves scheduling, DNS and Service access.
→
PX-108 · applicationSame image → app pod → existing RDS
Real application testOpen the portfolio and compare trades from ECS and EKS.

A successful cluster test does not prove the investment app has the right settings, credentials or database access.

What

A cluster is the environment that manages workloads. The investment app is one workload placed into it.

Where

PX-107 code is under class/04/terraform/. The current PX-108 roots and app examples are under class/05/.

Why

Verify the platform first, then prove the application works. This separates a broken cluster from a broken app configuration.

Important: the old PX-107 root is not the PX-108 network

The original PX-107 rehearsal created its own VPC and public worker subnets, then was destroyed. PX-108 reused the EKS child module, but supplied new private subnets inside the CloudFormation VPC. The module was reusable; the original root's network design was not copied.

Keep this sentence: PX-107 proved Kubernetes could run a workload. PX-108 proved this application could use the existing database without taking ECS down.

02 · Placement and ownership

One VPC. Two ways to run the same app.

The personal account had no foundation. CloudFormation created ECS and RDS first; Terraform added EKS beside them. “Existing RDS” meant existing by the time EKS was deployed.

A subnet is an address range and placement boundary. It is not a server. Two subnets do not mean two running workers.

What

Terraform owns the additions. It looks up the CloudFormation VPC/NAT and database security group.

Where

cloudformation/projectx-app.yaml owns the foundation. class/05/terraform/network/main.tf owns the new subnets and routing.

Why

Local VPC routing connects EKS to private RDS. Reusing the NAT avoids duplicate infrastructure and cost.

Why /19, and why not start at 10.40.6.0?

A /19 starts on a third-octet boundary of 0, 32, 64, 96 and so on. 10.40.6.0/19 falls inside 10.40.0.0/19, overlapping the foundation. The selected /19s each contain 8,192 addresses before AWS reservations. VPC CNI uses VPC addresses for pods, so address space matters. Actual pod capacity is also limited by instance networking and CNI configuration; a large subnet does not give one small node thousands of pod slots.

Could private RDS be reached from another VPC?

Yes, with a deliberately configured private network connection such as peering or Transit Gateway, routes and security rules. The same VPC was the simpler choice for this lab; it is not the only possible private connectivity design.

A data "aws_vpc" block reads the VPC. A resource "aws_vpc" block would manage one. Reading a resource does not transfer its ownership.

Roots run separately. Modules share implementation.

A root is the directory where you run Terraform. A child module is code called by that root. Separate roots have separate state and do not apply automatically together.

What

State records Terraform's bindings between addresses in code and real AWS objects. It is operational data, not a backup of the database.

Where

Independent lifecycles make ownership and teardown clearer. The shared child module avoids rewriting EKS implementation.

What does the RDS rule reference teach about destroy order?

The source module.eks.node_security_group_id creates a Terraform dependency. During teardown, Terraform removes the referencing rule before deleting the EKS resource that supplies that group. In this module the output is the EKS-created cluster security group attached to workers, not a separately managed aws_security_group resource. The destroy evidence shows the rule gone before cluster deletion.

The S3 backend is configured during init; it cannot use ordinary Terraform input variables. The ignored backend files and the EKS remote-state inputs must point at the same intended account, region and bucket.

04 · Control plane, worker, pod

EKS manages Kubernetes. Workers run the containers.

The API server is not the app server. A Ready cluster also needs usable worker capacity and networking before an ordinary application pod can run.

CoreDNSResolves Kubernetes Service names.

What

A node group manages EC2 workers. A pod is scheduled onto a worker. A container is a process inside a pod.

Where

modules/eks/eks.tf defines the cluster and node group; addons.tf defines the managed networking add-ons.

Why

The lab needed a predictable small worker, not automatic node provisioning. One node was sufficient for the comparison but provided no worker redundancy.

kubectl get nodes -o wide
kubectl get pods -n investment-app -o wide
kubectl describe pod -n investment-app <POD_NAME>

These are live-cluster inspection commands. With this lab destroyed, they cannot reproduce the old results; use the saved verification record instead.

Why install CNI before creating the node group?

Workers need networking to become useful. Installing the managed VPC CNI first avoids the creation dependency where nodes wait for networking while Terraform waits for the node group. CoreDNS and kube-proxy are added after worker capacity is available.

Which identity is being checked?

aws sts get-caller-identity checks the AWS caller. An EKS access entry grants the intended IAM identity Kubernetes access. kubectl then uses its selected context and namespace. Correct AWS credentials do not automatically mean access to every Kubernetes cluster.

A managed node group is a worker lifecycle mechanism. In this lab min=desired=max=1; it did not automatically add nodes for pending application pods.

The image packages the application. It does not contain this environment's database password or create the RDS database.

What

The namespace groups names. The Deployment manages replicas. The Service selects pods. The Secret holds the password value for the app.

Where

class/05/kubernetes/ holds marked examples. scripts/load-db-secret.py loads the real credential into the chosen cluster.

Why

Pods can be replaced without changing the image or moving data out of RDS. A digest identifies the exact image tested on both platforms.

kubernetes/deployment.yamlFill marked image/DB placeholders in an ignored copy. Current placeholders are intentional; the original endpoint no longer exists.
kubernetes/service.yamlThe selector must match pod labels. A matching container port alone does not connect a Service to a pod.
scripts/load-db-secret.pyExplicit caller/region/user inputs; refuses to replace an existing Secret automatically.
What is different from the class manifests?

The class examples use a ConfigMap for non-secret settings and may use two app replicas on a Karpenter pool. This lab used one replica and inline non-secret environment values in the Deployment. Both approaches are valid. Do not assume a ConfigMap or Karpenter selector exists in this lab merely because it appears in a class diagram.

A Kubernetes Secret's base64 representation is encoding, not encryption. Access controls still matter. A password injected as an environment variable also does not update inside an existing process when the Secret changes; a coordinated restart is required.
“Same image” proves the application binary matches. It does not prove the database endpoint, settings or security rules match.

Isolation: who gets network access with the node SG rule?

Other pods using that node security group get the same network path. Namespace or app labels do not narrow an AWS SG rule by themselves. Valid DB credentials are still required. For application-specific AWS network access, security groups for Pods can attach a dedicated group to selected pods; the broad node-source RDS rule must then be removed. The managed-node-group design used here would also need a supported instance type: T-family instances do not support that feature.

AWS: security groups for Pods and instance limitations

Why can /health pass while the portfolio is broken?

The endpoint tests the process, not a trade query. In this lab all three HTTP probes used /health; the portfolio and shared-trade tests supplied the database proof. If startup blocks on the DB, even /health may fail because the server never starts. Class examples with readiness on / behave differently.

When Karpenter launches a future worker, inspect its actual security groups. A DB rule for today's managed worker does not automatically authorize a different Karpenter node group.

08 · Provision capacity when needed
Karpenter supplies nodes. The scheduler places pods.
Karpenter was deliberately skipped in the working personal lab. This stop explains the class/reference architecture; it is not additional deployment evidence.


Two installation layers, then capacity policies
AWS prerequisitesIAM permissions, worker identity and cluster/network integration; reference Terraform prepares these.
Running Karpenter controllerInstalled with Helm, plus CRDs. Needs existing compute to run; a system managed node group is one option.
NodePoolAllowed capacity: instance constraints, capacity type, limits and disruption rules.
EC2NodeClassAWS settings: AMI, subnet/security-group selection and node identity.
NodeClaimKarpenter's request and lifecycle record for a particular node.


What
A controller reacts when eligible pods lack suitable capacity. A NodePool and NodeClass tell it what it is allowed to launch.
Where
Class 7 examples and codex/dev-eks-foundation, not our Class 5 EKS implementation. Adding a pool YAML alone does not install Karpenter.
Why
Workload-driven capacity can avoid a permanently oversized fleet, with more lifecycle, permissions and cost controls to understand.

What did the class configuration actually choose?
The prepared Class 7 example used a Spot-only general NodePool, allowed t3.medium and m5.large, capped total CPU at 8, and consolidated empty nodes after one minute. Its EC2NodeClass used private subnets, a chosen security group, an instance profile and a pinned AL2023 image. These were class settings, not a price guarantee or general production recommendation.
A pod selecting karpenter.sh/nodepool: general cannot simply fall back onto a node missing that label. The later CPU-heavy class test remained Pending without a confirmed cause; do not invent a diagnosis.


Helm can install both the investment-app chart and the Karpenter controller chart. Those are separate releases with completely different responsibilities.

The bucket error and state reconciliation
The first wrapper failed while parsing an empty successful S3 response, before deleting the bucket. The owner then removed the already-empty bucket with aws s3api delete-bucket. Six stale bootstrap resource bindings were subsequently removed using terraform state rm, after checking the account and confirming the bucket was absent. A state list returned no resource entries. State removal did not delete AWS resources and is not a substitute for the cloud absence checks.


What was kept, and what does the cost number mean?
The ACM certificate and its validation CNAME, the image in ECR and the hosted zone were deliberately retained. Unrelated resources were left alone. Retaining an ECR image can still incur storage charges.
The approximately $0.47 figure is a base-runtime estimate, not a final settled invoice. Cost Explorer was delayed and account-wide; posted usage and credit offsets did not establish the final lab total. Credits did not increase the accepted $15 gross-use target.
