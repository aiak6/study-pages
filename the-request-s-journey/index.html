The one-sentence version to say out loud: Route 53 turns the name into the load balancer's address; the ALB is the public front door; it forwards inward across subnets to the EC2 running your app; the app talks to RDS. Security groups are the gate at each hop.

02The part you kept second-guessing

Where security groups actually live

You had this half-right and half-tangled. Let's nail it: a security group is a per-resource firewall, not a VPC setting.

✕

The myth: "Security groups are attached to the VPC." The VPC is just the private network — the address space where everything lives. It has no ports to open.

✓

The truth: Each security group is associated with a resource — the ALB, the EC2, the RDS. It decides which traffic that one resource accepts. They live inside the VPC, but they attach to the resource, not the network.

So the answer to "how many security groups?" is normally three — one guarding each tier. Here's each one and, crucially, what it lets in and from where:

On the ALB

Load balancer SG

Lets in: 80 and 443 from 0.0.0.0/0 — anywhere. This is the public door, so the whole internet is allowed to knock.

On the EC2

App SG

Lets in: 80 only from the ALB's SG, plus 22 for your SSH. The public can't reach the EC2 directly — only through the front door.

On the RDS

Database SG

Lets in: 5432 only from the App SG. Nothing else on earth can open the database. Not you, not the internet.

?

Why does the DB group point at the App group instead of an IP range? This is a real interview question and you almost had it. If you hard-code the EC2's IP and that instance restarts or gets replaced, the IP changes and the database locks out your app. Referencing the App SG means "whoever is currently the app can connect" — it keeps working no matter how many times instances come and go. That's the whole idea behind least privilege chaining: open the smallest door, to a role, not an address.

03Inside the front door

Listener, forward, redirect — and why 443 becomes 80

The security group only answers one question: is this traffic allowed in at all? Once it's in, the listener takes over and decides what to do with it.

Action: forward

Forward → target group

The normal path. The 443 listener hands the request to the target group, which passes it to a healthy EC2. "Go to my app." This is what serves your actual pages.

Action: redirect

Redirect → somewhere else

The listener tells the browser "go knock on a different door instead." The classic use: the 80 listener redirects to 443 so plain HTTP visitors get bumped up to HTTPS. The browser comes back on the secure door.

↔

Why HTTPS (443) turns into plain HTTP (80) inside: the ALB terminates TLS — it does the decrypting right at the front door using your ACM certificate. Once traffic is inside your own VPC it's already on a trusted private network, so re-encrypting to the EC2 buys little. The ALB receives on 443, then forwards on 80 to the instance. That's why the EC2's SG only needs 80 open, not 443.

✓

What the certificate actually does: the ACM cert (the thing you "requested and verified") doesn't do the encrypting by itself — it proves the domain is yours. The encrypting is done by the TLS protocol underneath. Cert = identity/ownership; TLS = the lock. Two different jobs people mash together.

i

Don't confuse the two "redirects." The ALB redirect action (80 → 443) and a 301 from curl are the same idea seen from two sides: the server telling the browser "use the other address." When you curl your HTTP URL and see 301, that is the ALB redirect doing its job — not an error.

04The interview favorite

"The site's down" — walk me through it

Always go in this order, outside-in. Each command answers one question, and each failure points at a different place to go fix.

1

ping — is anything reachable at all?

$ ping aiturgan.space

Answers: is my own internet up, and does the name resolve to something that responds? It's the "is the patient breathing" check before anything fancy. (Note: many AWS setups block ping/ICMP on purpose, so no reply isn't always a real failure — but it's still where you start.)

2

dig / nslookup — does DNS point to the right place?

$ dig aiturgan.space # or: nslookup aiturgan.space

Answers: what IP does this domain actually resolve to? dig and nslookup do the same core job — look up the address behind a name. If the answer is wrong, empty, or points at an old IP, the fix lives in Route 53 — update the record so the domain points at your load balancer.

3

curl — does the server answer, and with what?

$ curl -I https://aiturgan.space # -I = headers only, -v = verbose, -L = follow redirects

Answers: is the server actually responding, and what status code does it give back? This is where DNS is fine but something deeper is wrong. The status code tells you which layer to blame — that's the table below.

Reading the curl result: where do I go next?

This is the answer to your real question — "if curl fails, which piece of AWS do I troubleshoot?"

What curl doesMeansGo troubleshoot →
hangs / times out The request left but nothing ever replied. A gate silently dropped the packet. Security group. A port isn't open for that source. Traffic isn't refused — it's dropped, so it just hangs. Check the ALB SG (80/443 from anywhere) and the App SG (80 from the ALB SG).
200 OK Everything worked. The page came back. Nothing — you're healthy.
301 / 302 Redirect. Almost always HTTP → HTTPS. This is normal after you add the certificate. Nothing's broken. Add -L to follow it and you'll land on 200.
404 Not Found Server answered, but nginx couldn't find that file. The traffic got all the way in. The EC2 / nginx. The HTML file for that page is missing or in the wrong folder. SSH in and check nginx's web root.
500 Internal Server Error The app itself crashed while handling the request. Traffic reached the app. The app on the EC2 (and often RDS). Check app logs. A very common cause: the app can't reach the database — so check the DB security group (5432 from the App SG).
502 / 503 The ALB answered, but it has no healthy instance to forward to. Target group health. The EC2s are failing their health check, so the target group is empty. Jump to section 05.
◎

The mental model to carry into the interview: you troubleshoot outside-in, following the request's path. Hang = a gate (security group). An error code = you got past the gates and something inside answered — now the number tells you whether it's nginx (404), the app/DB (500), or no healthy target (502/503).

05Your weak spot — now cleared

Two health checks, one probe

The confusion was real: the target group and the auto scaling group both "check health." Here's the clean version — they read the same probe but do different jobs with the answer.

Target group

Should I route traffic here?

"Are you well enough to get visitors right now?"

  • If an instance fails, the target group stops sending it traffic.
  • The instance keeps running — it's just taken out of rotation.
  • Reroutes those visitors to the healthy instances instead.
Auto scaling group

Should I replace this box?

"Are you broken enough that I should kill you and launch a fresh one?"

  • If an instance fails, the ASG terminates it and launches a replacement.
  • It's the only one that creates and destroys instances.
  • Keeps the fleet at the desired count of healthy machines.
✓

The precise version: there's usually one HTTP probe — the target group hitting something like /health every 30 seconds. The target group reads the result to decide routing. The ASG (set to health check type ELB) reads the same verdict to decide replacement. Same probe, two readers, two different actions.

?

"Can an instance be healthy to one but not the other?" → Yes. That's exactly why they're separate. Set the ASG's health check type to EC2 and it only checks "is the machine booted?" — while the target group checks "does the app actually answer?" So an instance can be a running box (healthy to the ASG) whose app is broken (unhealthy to the target group). Set the ASG type to ELB and you tell it "trust the load balancer's opinion" — now they agree.

interval Health check interval (≈30s) How often the probe runs. Every 30 seconds, "you still ok?"
grace Health check grace period (≈300s) How long the ASG waits after launching a new instance before it starts judging it — so a booting machine isn't killed for being slow to start.

Easy to mix up: interval = how frequently checks happen; grace period = a one-time head start for a brand-new instance. Different clocks.

What makes an instance "unhealthy" in the first place

Wrong port. The health check points at a port the app isn't listening on.

Wrong status code. The probe expects 200 but the app returns something else (a 301 or 500 at /health).

App listens on localhost only. It answers on 127.0.0.1 but not on the interface the ALB reaches.

Security group blocks the probe. The health check traffic can't get through to the instance.

Grace period too short. The app needs longer to boot than the ASG waits, so it's killed mid-startup.

Wrong path. The probe hits /health but that route doesn't exist, so it gets a 404.

06Say it out loud

Practice questions with model answers

The three your group worked through, written the way you'd actually answer them. Try covering the answer and saying it first.

Q1Walk me through what happens from a user typing the URL to the app reading from the database.▾

The browser asks DNS (Route 53) to turn the domain into an address, and gets back the load balancer's address. The request hits the ALB on 443, where the security group allows it in and the listener terminates TLS using the ACM certificate.

The listener forwards the request to the target group, which picks a healthy EC2 and sends it on port 80 inside the VPC. The app on the EC2 handles it, and when it needs data it connects to RDS on 5432 — allowed because the database's security group trusts the app's security group. The response travels back out the same way.

Q2You've got three security groups chained together. Why does the RDS security group reference the app security group as its source instead of an IP range?▾

Because instances are disposable. If I hard-coded the EC2's IP and that instance restarted or the auto scaling group replaced it, the IP would change and the database would lock out my app.

Referencing the app's security group means "allow whichever instance is currently the app," so it keeps working no matter how many times instances come and go. It's also least privilege — I'm opening 5432 to a specific role, not to a broad range of addresses.

Q3There are two health checks — one on the target group, one on the auto scaling group. Why two? Can an instance be healthy to one but not the other?▾

They answer different questions. The target group asks "should I send traffic here?" — if an instance fails, it just stops routing to it but leaves it running. The auto scaling group asks "should I replace this box?" — if it fails, the ASG terminates it and launches a fresh one. Routing versus replacement.

Yes, an instance can be healthy to one and not the other. If the ASG's health check type is EC2, it only checks whether the machine is booted, while the target group checks whether the app actually responds — so a running box with a dead app is healthy to the ASG but unhealthy to the target group. Setting the ASG type to ELB makes it defer to the load balancer so they line up.

Q4A user says the site is hanging — it never loads, no error. Where do you look?▾

Hanging with no error usually means a packet is being silently dropped — the signature of a security group. If it were refused I'd get an error fast; dropping means it just waits. I'd check that the ALB's SG allows 80/443 from the internet and that the EC2's SG allows 80 from the ALB's SG.

To confirm the path I'd work outside-in: ping to see if anything responds, dig to confirm DNS points at the load balancer, then curl -v to see exactly how far the request gets before it stalls.

Q5curl returns 502/503. What's going on and how do you fix it?▾

The ALB is up and answering, but it has no healthy target to forward to — the target group is effectively empty. So the problem is instance health, not networking.

I'd check the target group's health check: is it pointing at the right port and path, does the app return 200 there, is the app listening on the right interface (not just localhost), and is the grace period long enough for the app to boot. If the app is genuinely crashing, I'd SSH in and read the logs.
