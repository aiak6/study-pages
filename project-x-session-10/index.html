📰 Why half the internet broke this month

A student had asked the previous class about the wave of outages — Microsoft, airlines, banks. The instructor came back with a fuller answer.

  • The official line: no cyberattack. The explanation being given is accumulated bugs, found and fixed in a rush.
  • The chain of reasoning: AI got genuinely good this year and started finding real flaws in code, mostly security ones → companies had to fix them, because serious security bugs can't wait → every fix is a change, and every change can break something → many companies making many changes at once produced a cluster of outages.
  • 🔑 The engineering principle underneath, true long before AI: the more you change, the more likely you break something.
  • That's why banks keep old systems running unchanged, and why retailers impose change freezes — no code changes during the holiday season. Roughly 75% of annual US shopping happens in that window, so nobody touches anything.
  • A student asked whether AI actually prevented something worse. The answer: yes, most likely. If a model can find a security flaw, so can an attacker using the same model. Fixing first beats being exploited first.
  • 💡 He also flagged how much outage "news" is fake or AI-generated engagement bait. His filter: trusted sources, or run it through AI before believing it.

🗺️ The four steps to make an app public

Everything in this class fits one checklist. Learn it as a unit — it's a clean interview answer to "how do you expose an app running on Kubernetes?"

#StepHow often
1Install the AWS Load Balancer Controller (IAM role in AWS + Helm chart in Kubernetes)Once per cluster
2Install the Gateway API CRDsOnce per cluster
3Apply GatewayClass and GatewayOnce per cluster
4Apply an HTTPRoute for each applicationPer app
  • 🔑 Three of the four are one-time cluster setup. Once they exist, exposing the next application is a single HTTPRoute and a ClusterIP Service. That's the whole payoff of the design.
  • Why Gateway API rather than a load balancer per app? Shared entrance = fewer load balancers to pay for and manage. In a microservice shop with dozens of small apps, that difference is enormous (Session 09).
  • 💡 The instructor was honest that Gateway API is more complex than ingress-nginx was. Its predecessor was one resource; this is four moving parts. The trade is flexibility — and you only set it up once.

🎛️ Step 1: the AWS Load Balancer Controller

Two halves, and both must exist — the same pattern as Karpenter (Session 08).

HalfWhat it isWhere it came from
AWS sideIAM policy + role, attached via Pod IdentityAlready written in the Terraform EKS module
Kubernetes sideThe controller itself, running as a Pod in kube-systemA Helm chart — this is what had to be run

helm upgrade --install aws-load-balancer-controller aws-load-balancer-controller \

  • 🔑 Read that backslash carefully: 'nodeSelector.projectx\.io/node-role=system'. Helm uses dots to separate setting levels, so a dot that's part of a name must be escaped. Miss it and Helm builds a nonsense nested structure.
  • The settings aren't arbitrary — clusterName, the service account name and the node selector all have to match what Terraform created. The instructor asked Claude to read the branch and produce the matching command rather than copying a generic one from the docs.
  • The VPC ID is the one value the AI couldn't infer; he looked it up in the console (the CloudFormation-tagged VPC) and passed it as a shell variable.
  • A student asked whether this installs into the EKS cluster. Yes — Helm always installs into whatever cluster your context points at, here into the kube-system namespace. And it's more than a Pod: a ServiceAccount plus the linked AWS IAM role come with it.

🧬 Step 2: Gateway API CRDs — and what a CRD is

CRD = Custom Resource Definition. Kubernetes ships with built-in kinds: Pod, Deployment, Service. A CRD teaches the cluster a new kind. Without the Gateway API CRDs installed, kind: Gateway is a word the cluster has never heard of, and kubectl apply refuses it.

kubectl apply --server-side=true \
  -f https://github.com/kubernetes-sigs/gateway-api/releases/download/v1.5.0/standard-install.yaml
  • That one file is roughly 17,000 lines — the full specification of how Gateway API behaves. You never read it; you just install it.
  • There are other install variants (experimental, etc.). Unless you need something specific, take standard.
  • 🔑 Who writes CRDs? The people building the software — the Gateway API project here. As a platform engineer you install and use CRDs; you almost never author them. That's a clean, confident interview answer.
  • ⚠️ Order matters, and the class proved it: the GatewayClass was applied before running this command, producing Ensure CRDs are installed first. The command had been pasted into the notes and never actually run.

🚪 Step 3: GatewayClass and Gateway — and the internal-ALB trap

These two go in the platform repo, not the app chart, because they're once per cluster.

  • Both resources need an apiVersion — the slide excerpts omitted it and the first apply failed on exactly that.

Then the real problem. The ALB got created — and was completely unreachable from a browser.

AWS console → Load balancers
  ECS ALB  → scheme: internet-facing
  EKS ALB  → scheme: internal          ← there it is

Why internal? Two reasons together: no scheme was set, so it defaulted to internal; and the subnets it found were the private ones the ECS design used.

scheme: internet-facing

The test that actually tells you

🔑 How to identify a public subnet, reliably: open its route table. 0.0.0.0/0 → Internet Gateway = public. 0.0.0.0/0 → NAT gateway = private. Names lie; route tables don't. In this VPC the database subnets had no route out at all, the ECS subnets pointed at NAT, and only two subnets were genuinely public.

  • An internet-facing load balancer must sit in public subnets — same logic as a NAT gateway (Scale Session 06).
  • To apply the change the Gateway had to be deleted and re-applied: kubectl delete -f gateway-api/ then kubectl apply -f gateway-api/. That produces a new ALB with a new DNS name, which matters in a moment.

🎯 The TargetGroupConfiguration surprise — and how to doubt your AI properly

Even after the scheme fix, no load balancer appeared. The controller logs (huge, JSON, genuinely unpleasant to read) showed: target group port is empty. The AI's answer: you need a TargetGroupConfiguration.

🔑 "When I see something inconsistent like this, I try not to follow right away what the AI says, but rather confirm — because I assume AI did not confirm. A lot of times it just goes to the best first answer."
  • His actual doubt was sharp and specific: why wasn't this needed five minutes ago, when the internal ALB was created?
  • The confirmed answer: the internal one never had an application behind it. It was an empty load balancer that accepted no routes, so it never reached the point of needing target group settings. The requirement was always there; the earlier attempt just never got far enough to hit it.
  • Where to put it: the AI offered a per-namespace version. He chose the cluster-wide default instead, so every namespace inherits it and nobody has to repeat it per app.
  • He also had to link it from the LoadBalancerConfiguration — creating the object alone did nothing, a step that cost another round.
  • 💡 Reading controller logs: they're verbose JSON. The honest advice is to paste them into an AI to parse — but keep the skepticism above.
  • 💡 Targets are Pod IPs (targetType: ip), not nodes. The ALB talks straight to Pods, which is why the controller must keep updating it as Pods are replaced.

🧭 Step 4: the HTTPRoute — one per application

This is the only piece that repeats, and it lives in the app's Helm chart. The AI generated the template; the interesting part is which values go where:

# values-dev.yaml — environment-specific, NOT shared values.yaml
httpRoute:
  enabled: true
  parentRefs:
    - name: projectx-public       # the Gateway's name
      namespace: kube-system      # where the Gateway lives
  hostnames:
    - <your-app-hostname>

service:
  type: ClusterIP                 # NOT LoadBalancer
  • 🔑 The hostname is different in every environment, so this belongs in values-dev.yaml, never in the shared values.yaml. Putting it in the shared file would give staging and production the dev hostname.
  • 🔑 The Service goes back to ClusterIP. The ALB is managed by the controller now; a LoadBalancer Service would spin up a second load balancer serving the same Pods — pure waste.
  • The chain: HTTPRoute → ClusterIP Service → (selector) → Deployment's Pods. Each link is a name matching a name.
  • A real error worth remembering: the first apply failed with spec.hostnames: Invalid value because the hostname had been pasted with https:// on the front. A hostname is just the name — no scheme, no slashes.
helm upgrade --install investment-app charts/investment-app \
  --values charts/investment-app/values-dev.yaml \
  --namespace main-product-line --create-namespace

kubectl -n main-product-line get httproute

🔀 The DNS cutover: weighted records and canary deployment

Both load balancers now exist and both work. The only thing still sending users to ECS is one Route 53 record. You could flip it in one move, but Route 53 lets you do it gradually with a weighted routing policy: two records, same hostname, different targets.

ECS weightEKS weightWhere traffic goes
991~1 in 100 requests reaches EKS
9999Roughly half and half
—(ECS record deleted)Everything to EKS
  • 🔑 Weights are relative numbers, not percentages. A record's share is its weight ÷ the sum of all weights. The maximum value is 255. So 99 and 99 is 50/50, not 198%.
  • This pattern has a name: canary deployment — send a small slice of real traffic to the new thing, watch, then widen. Used for migrations and for risky releases alike.
  • Full cutover = delete the record pointing at ECS. Then the hostname resolves only to the EKS ALB.
  • Rollback = re-add the ECS record. ECS and its ALB are deliberately left running for a couple of days so this stays possible.
Two honest warnings from this demo

⚠️ DNS caching blurs all of this. With 50/50 weights, a given person doesn't get an even split — they get whatever their resolver cached. And after a cutover some users keep hitting the old address for a while. The instructor had to flush his own DNS cache mid-demo to see the change.

⚠️ Never delete the old system first. If you delete it before switching traffic, users are still being sent there and get nothing. Switch traffic, verify, then decommission. In this class the DNS was switched before the EKS route worked, so the site was briefly broken for everybody — which is exactly what the next section would have prevented.

🧪 Testing without changing public DNS

The whole problem: you want to check the new load balancer using the real hostname (because the route matches on hostname) without affecting any real user.

  • Troubleshooting lesson of the class. After switching to the new ALB, curl returned could not resolve host. A student guessed it was the port.

The real cause fit perfectly: deleting and re-applying the Gateway had created a new ALB with a new DNS name, and the Route 53 record still pointed at the old one. Updating the record fixed it — after a local DNS cache flush.

🔐 Adding HTTPS — and matching what ECS already did

First success was HTTP on port 80. That's not a finished migration: the ECS site served HTTPS, and the replacement has to behave the same.

  • The certificate is already paid for and valid. Look at what the ECS ALB uses: its 443 listener references an ACM certificate for that exact hostname. Point the new ALB at the same certificate.
  • The change is a few lines in the LoadBalancerConfiguration — a 443 listener with the ACM certificate ARN, plus a matching listener on the Gateway. Re-apply, and the browser shows a secure connection.
  • 💡 A student asked about their own domain without a certificate: because we're on an AWS load balancer, an ACM certificate is free when used this way. No Certbot needed (Foundation Class 11 was the manual version).

Self-test

Check yourself

Answer each question out loud first, then open the answer. Score yourself out of 10.

1. An interviewer asks: "You've got an app running in EKS. Nobody outside can reach it. Walk me through making it public." Give the steps in order, and say which one you'd repeat for the next ten apps.

Show answer

Four steps — and only the last one repeats.

  • Install the AWS Load Balancer Controller: an IAM role and policy on the AWS side, a Helm chart into kube-system on the Kubernetes side.
  • Install the Gateway API CRDs, so the cluster understands Gateway and HTTPRoute as kinds at all.
  • Apply the GatewayClass (which controller builds the load balancer) and the Gateway (which ports it listens on).
  • Apply an HTTPRoute per application, pointing a hostname at that app's ClusterIP Service.

Steps 1–3 are once per cluster. Step 4 is the only per-app work — that, plus the app's Service. 🔑 That asymmetry is the argument for Gateway API.

💡 Finish the answer with DNS: once the ALB exists, point the public record at it — ideally gradually.

2. Your Gateway is accepted, the controller logs look clean, an ALB exists in the console — and a browser cannot reach it at all. What's your first suspicion, and how do you prove which subnets are public?

Show answer

Suspect an internal ALB in private subnets — and prove it with the subnets' route tables, not their names.

  • The controller creates an internal load balancer when no scheme is set. Internal means reachable only from inside the VPC — exactly what happened in class.
  • Confirm it in one glance: the AWS load balancer list shows a Scheme column. internal vs internet-facing.
  • The fix: a LoadBalancerConfiguration with scheme: internet-facing and an explicit list of public subnets.
  • 🔑 How to identify a public subnet: open its route table. 0.0.0.0/0 → Internet Gateway = public. 0.0.0.0/0 → NAT gateway = private. No default route at all = fully isolated (the database subnets).

💡 Never trust the name. A subnet called public-1a with a NAT route is private, and the route table is the only authority (Scale Session 06).

3. Your AI says you need a TargetGroupConfiguration. But the load balancer was created five minutes ago without one. How should you handle that contradiction?

Show answer

Don't act on it yet — ask why it worked before. The AI gave the right answer without having checked the inconsistency.

  • The rule, said out loud in class: "when I see something inconsistent like this, I try not to follow right away what the AI says, but rather confirm — because I assume AI did not confirm. A lot of times it just goes to the best first answer."
  • The specific question to ask: why wasn't this needed before?
  • The real answer: the earlier ALB was internal and had no application behind it. It accepted no routes, so it never got far enough to need target group settings. The requirement existed all along.
  • So the AI was right — but you only know that after checking, and the check cost one question.
  • 🔑 The transferable habit: when an AI answer contradicts something you just observed, the contradiction is the thing to investigate. Treating "it was right last time" as proof is how you end up applying fixes you can't explain.

Practical extras from the same debugging run: the configuration had to be referenced from the LoadBalancerConfiguration, not just created, and setting it as a cluster-wide default beat repeating it per namespace.

4. In Route 53 you set the ECS record to weight 99 and the EKS record to weight 99. What share does each get? What's the maximum weight? And why won't 50 students refreshing the page see a clean 50/50 split?

Show answer

50% each — weights are relative, not percentages. Maximum is 255. And DNS caching means individuals don't get a fair coin flip.

  • The formula is weight ÷ sum of all weights. 99 ÷ (99+99) = 50%. Likewise 99 and 1 gives 99% and 1%, which is what the earlier step used.
  • Because they're relative, 99/99 and 5/5 and 255/255 are all identical. The numbers only mean something next to each other. Max: 255.
  • Why the split isn't clean in practice: a browser doesn't ask DNS per request — it uses a cached answer, from the OS or the resolver, for the record's TTL. One person gets one answer and sticks with it.
  • 🔑 Same caching bites after a cutover: some users keep reaching the old address for a while, which is precisely why you leave the old system running rather than deleting it the moment you switch.

💡 The name for this gradual shift is canary deployment — a small slice of real traffic to the new thing, widened as confidence grows.

5. You want to test the new ALB using the real public hostname, without any real user being affected. Give two ways, and explain why the second one works at all.

Show answer

Send a Host header with curl, or point your own machine at the ALB with /etc/hosts — which works because a machine reads its own DNS file before asking the world.

  • Option 1 — Host header: curl -H 'Host: app.example.net' http://<alb-dns-name>/. You connect to the ALB directly but claim the real hostname, so the HTTPRoute's hostname match still fires. Works in curl; not in Chrome.
  • Option 2 — /etc/hosts: add <ALB-IP> app.example.net. Now your browser works too.
  • Why it works: name resolution checks the local hosts file first, then public DNS servers. Your entry wins on your machine only.
  • 🔑 Why you need either: the HTTPRoute matches on hostname. Hitting the raw ALB DNS name doesn't match any route, so you can't test it that way.
  • ⚠️ Remember to remove the line afterwards. A stale /etc/hosts entry is a classic self-inflicted outage.

💡 Doing this before switching DNS is exactly what would have prevented the class's brief public breakage.

6. curl returns could not resolve host. A teammate says "the app's probably on 443, not 80 — try the other port." What do you tell them?

Show answer

It never got far enough to try a port. "Could not resolve host" is DNS — the name didn't turn into an IP address.

  • The request failed at name resolution, before any TCP connection was attempted. The port is irrelevant to an error that happens first.
  • A port problem looks different: connection refused (something answered and said no) or a hang/timeout (a firewall or security group is swallowing it).
  • 🔑 The rule: always look at the first clue first. If somebody says they have stomach pain, don't start by looking at their brain.
  • In class the real cause fit exactly: deleting and re-applying the Gateway created a brand-new ALB with a new DNS name, and Route 53 still pointed at the old one.

💡 Error triage worth memorising: could not resolve host → DNS · connection refused → nothing listening on that port · timeout → security group or route · 404 → you reached the app and it doesn't have that path.

7. In Session 09 the Service was switched to type: LoadBalancer. In Session 10 it goes back to ClusterIP. Why — and what would happen if you left it as LoadBalancer?

Show answer

Because the ALB is now created and managed by the controller through the Gateway. Leaving it as LoadBalancer would create a second, redundant load balancer in front of the same Pods.

  • The new chain: browser → ALB (built from the Gateway) → Pod IPs, selected via the HTTPRoute → ClusterIP Service → the Pods.
  • The Service's remaining job is identifying which Pods are the backend, by selector and readiness. It doesn't need to be publicly exposed itself.
  • Leave it as LoadBalancer and you get two load balancers for one app: double cost, two sets of settings to keep in sync, and a second public entrance nobody documented.
  • 🔑 That's the whole point of the Gateway design: one shared entrance, many ClusterIP Services behind it. A per-app LoadBalancer is the exact pattern it exists to replace.

💡 Ten apps done right: 1 ALB, 1 Gateway, 10 HTTPRoutes, 10 ClusterIP Services.

8. Your HTTPRoute is applied without error, the Gateway is healthy, but the route never attaches and the hostname returns nothing. Give two plausible causes.

Show answer

Either the Gateway doesn't allow routes from your namespace, or the hostname is malformed.

  • Cross-namespace permission: the Gateway lives in kube-system while the app's HTTPRoute lives in main-product-line. The Gateway must explicitly permit routes from other namespaces. If it doesn't, your route is ignored — and it isn't an apply-time error, so nothing complains.
  • Bad hostname: in class the apply failed with spec.hostnames: Invalid value because the value had been pasted with https:// in front. A hostname is just the name — no scheme, no slashes, no trailing path.
  • Two more worth checking: parentRefs must name the Gateway and its namespace correctly, and the backendRefs service name must match a Service that actually exists in the route's namespace.
  • 🔑 Check the status, not just the apply. kubectl get httproute and describe show whether the route was accepted by its parent Gateway. "Applied successfully" only means the YAML was valid.

💡 Then the controller logs — verbose JSON, but they say plainly when a route was rejected and why.

9. The hostname now resolves to the EKS ALB and the browser shows a padlock. Your manager asks if you can delete the ECS cluster today. What do you say?

Show answer

No — three things are still missing, and ECS is the only way back.

  • Settings aren't fully matched. The HTTP→HTTPS redirect was never verified, and the old ALB's listener rules, source IP restrictions, health checks and deregistration delay weren't compared one-for-one.
  • Nobody has confirmed it works. No developer or QA sign-off. A padlock in your browser is not a test of the application.
  • Rollback is the whole reason to wait. While ECS and its ALB run, recovery is re-adding one DNS record. Delete it and the only route back is a rebuild. Leave it a couple of days.
  • ⚠️ And never the reverse order: deleting the old system before switching traffic means users are still being sent somewhere that no longer exists.
  • 🔑 The principle: "if there is no change, there is no problem. If there is a change, there is a possibility of a problem."

💡 Note the honest ordering in class: the DNS was switched before the route worked, and the site was briefly down. Naming that as the mistake is better interview material than pretending it went cleanly.

  • Situation: "We were migrating an application from ECS to EKS. I'd set up Gateway API so the app would get an Application Load Balancer."
  • Symptom: "The load balancer was created and Kubernetes looked healthy, but nothing could reach it from a browser."
  • First theory, and why I dropped it: "My first guess was a security group, since a timeout usually means one. But the ALB's scheme was internal — it had never been reachable from the internet at all."
  • Root cause: "The controller defaults to internal, and the subnets it picked were private — their route tables pointed at a NAT gateway. I added a configuration setting it to internet-facing in the two genuinely public subnets."
  • The second problem: "Then it still didn't come up: the target group needed explicit configuration for Pod IP targets. That hadn't surfaced earlier because the first load balancer had no application behind it. I set it as a cluster-wide default so other teams wouldn't hit it."
  • Result: "The app served over HTTP, then HTTPS with the existing ACM certificate, and I moved DNS across with a weighted record so I could shift traffic gradually and roll back."

🔑 Why this works: a specific symptom, a theory you discarded with evidence, a real cause, and a fix that helped people beyond you. Interviewers want the reasoning, not the YAML.
