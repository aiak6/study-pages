Concepts

The main ideas, from zero

Cluster DNS: how drill becomes an IP

  • Problem: pod IPs change, and nobody wants to memorise ClusterIPs.
  • What: every Service gets the name <service>.<namespace>.svc.cluster.local. The cluster's DNS server, CoreDNS, answers it with the ClusterIP.
  • How: each pod's /etc/resolv.conf has a search line that adds your namespace to short names automatically.
You're calling from…Name that works
Same namespacedrill
Another namespacedrill.<namespace>
Anywhere in the clusterdrill.<namespace>.svc.cluster.local
Your laptopNone of them. CoreDNS answers cluster names only.
  • On EKS Auto Mode, AWS runs DNS on each node, so kubectl get pods -n kube-system is empty. On a standard cluster, CoreDNS is a Deployment there.
  • In nslookup output, ;; Got recursion not available is a notice you can ignore. The answer is in the Name and Address lines.
Same namespace → short name. Different namespace → add .namespace.

Why settings live outside the image

  • The same image runs on your laptop, in testing and in production. Only the settings differ.
  • In Scale that was one file, /etc/investment-app.env. In Kubernetes it becomes two objects.
Goes in the ConfigMap (not sensitive)Goes in the Secret (sensitive)
DB_HOST, DB_PORT, DB_NAME, DB_USER, TICKERDB_PASSWORD, FINNHUB_KEY

The app's code doesn't change. It still reads seven environment variables.

ConfigMap: settings stored in the cluster

  • What: an object holding key: value settings. It belongs to your namespace.
  • Where: in etcd, the cluster's record of every object, on the control plane. It is not on a node and not inside a pod.
  • Creating one starts nothing. Deleting a pod doesn't delete it, and the reverse is also true. They have separate lifecycles.
  • Every value is text, so a number needs quotes: DB_PORT: "5432". Without the quotes, kubectl apply refuses the file.
  • immutable: true locks it. To change a value you then have to delete it and create it again.
apiVersion: v1
kind: ConfigMap
metadata:
  name: investment-app-config
data:                   # the settings: key, then value
  DB_HOST: db
  DB_PORT: "5432"       # in quotes: every value is text
  DB_NAME: investment_app
  DB_USER: investment_app
  TICKER: AAPL
A ConfigMap is a separate object in etcd. Pods read it; they don't contain it.

Secret: same idea, plus a rule about who can read it

  • What: an object like a ConfigMap, used for passwords and keys, and stored the same way.
  • Why it's a separate kind: so an access rule can let someone read ConfigMaps but not Secrets.
  • type: Opaque means "the keys are yours, and Kubernetes doesn't check them." Other types: kubernetes.io/tls, kubernetes.io/dockerconfigjson, kubernetes.io/ssh-auth.
  • You write the values under stringData: in plain text, and the cluster stores them under data: in base64.
apiVersion: v1
kind: Secret
metadata:
  name: investment-app-secret
type: Opaque            # keys and values you choose
stringData:             # the values as you type them
  DB_PASSWORD: change-me-class-password
  FINNHUB_KEY: replace-with-your-finnhub-key

base64 is not encryption

  • base64 writes any data as ordinary text characters. Anyone can reverse it with base64 -d.
  • Why Secrets use it: a Secret can hold binary data (a certificate, a key file), and YAML/JSON can only carry text.
  • describe secret shows only key sizes. get secret -o yaml plus base64 -d shows the real password.
  • On EKS, etcd's disk is encrypted with KMS. The API server still decrypts before answering, so anyone allowed to read the Secret gets the plain value.
What protects a Secret is who is allowed to read it (RBAC), not base64.

How a pod gets the values: copied once, at start

container starts ↓ kubelet asks the API server for the ConfigMaps/Secrets the pod names ↓ sets each key as an env var of the app's process ↓ the values are now a COPY in memory. Nothing refreshes them while it runs.
  • envFrom + configMapRef → every key of the ConfigMap.
  • env + valueFrom + secretKeyRef / configMapKeyRef → one key. name is the variable inside the container and key is the key in the object; they can differ.
  • Postgres reuses the same objects: POSTGRES_USER ← DB_USER, POSTGRES_DB ← DB_NAME, POSTGRES_PASSWORD ← DB_PASSWORD. One source, two consumers.
After you change a ConfigMap or Secret, replace the pods that use it.

Production: External Secrets Operator (ESO)

AWS Secrets Manager (real password) ↓ ESO, a controller in the cluster, reads it on an interval Kubernetes Secret (created for you) ↓ pod env vars
  • The repo holds only an ExternalSecret reference. Nobody writes a Secret file.
  • This is the last part of unit 4 (night 2).

Hands-on

Redo the demo yourself

Before you start:

  • Your local copy has only 04-config-secrets-identity/README.md. Pull main first to get the YAML files.
  • Your investment-app image in your ECR, built with --platform linux/amd64. An arm64 image fails with exec format error.
  • kubectl signed in to the class cluster, namespace my-namespace.
  • In both Deployment files, replace IMAGE_URI with your ECR image URI.
1

Create the ConfigMap. It holds the five ordinary settings.

cd ~/DevOps/containers/04-config-secrets-identity
kubectl apply -f configmap-investment-app.yaml
kubectl get cm                               # DATA 5
kubectl describe cm investment-app-config    # every key and value, plain text

investment-app-config with DATA 5.

2

Create the Secret.

kubectl apply -f secret-investment-app.yaml
kubectl get secret investment-app-secret        # TYPE Opaque, DATA 2
kubectl describe secret investment-app-secret   # sizes only, no values

Opaque 2, and describe showing bytes, not the password.

3

Prove it's not encrypted.

kubectl get secret investment-app-secret -o yaml     # data: DB_PASSWORD: Y2hhbmdl...
kubectl get secret investment-app-secret -o jsonpath='{.data.DB_PASSWORD}' | base64 -d

change-me-class-password in plain text.

4

Start Postgres first. The app connects to db as it starts. With no db, it exits and goes into CrashLoopBackOff.

kubectl apply -f postgres.yaml     # Deployment postgres + Service db
kubectl get pods,svc

the postgres-… pod Running and service/db on port 5432.

5

Start the app.

kubectl apply -f deployment-investment-app.yaml
kubectl rollout status deploy/investment-app

deployment "investment-app" successfully rolled out, with 2 pods Running.

6

Check from outside, then from inside. describe shows where each value comes from, and exec shows what the app actually has. Everything after -- runs inside the container.

kubectl describe pod -l app=investment-app
kubectl exec deploy/investment-app -- env
kubectl exec deploy/investment-app -- printenv TICKER    # AAPL

Environment Variables from: investment-app-config ConfigMap and DB_PASSWORD: <set to the key 'DB_PASSWORD' in secret …>. Then env lists the seven values, plus PATH, HOSTNAME and DB_SERVICE_HOST.

7

Failure 1: the wrong ConfigMap name.

kubectl apply -f deployment-investment-app-missing-configmap.yaml
kubectl get pods -l app=investment-app-broken        # CreateContainerConfigError
kubectl logs deploy/investment-app-broken            # "waiting to start", no app logs
kubectl describe pod -l app=investment-app-broken    # Events at the bottom
kubectl delete -f deployment-investment-app-missing-configmap.yaml

Error: configmap "investment-app-configs" not found in the events, while your real app keeps running.

8

Failure 2: an edit doesn't reach the running pod.

kubectl edit configmap investment-app-config             # TICKER: MSFT, save and close
kubectl exec deploy/investment-app -- printenv TICKER    # still AAPL
kubectl get pods --watch                                 # in a second terminal
kubectl rollout restart deploy/investment-app
kubectl rollout status deploy/investment-app
kubectl exec deploy/investment-app -- printenv TICKER    # MSFT

new pods replace the old ones one by one, then MSFT.

What the instructor stressed

  • Never push a Secret file with a real password. Put it in .gitignore. At work you won't even write one, because ESO does it.
  • No logs doesn't mean no clue. Logs exist only once a container has run. Otherwise, read the events in describe.
  • CreateContainerConfigError → check the ConfigMap and Secret names. It isn't a crash.
  • Editing a ConfigMap does nothing to running pods. Use rollout restart; deleting pods causes downtime.
  • You won't need the DNS details at work. In six years he never had to dig into Kubernetes DNS. Just know the short name vs .namespace rule.

Self-test

Check yourself

1. Your teammate says, "Our Secret is safe, kubectl describe doesn't even show the password." What do you tell them?

Show answer

describe hides it, but get -o yaml | base64 -d reveals it. base64 is encoding, not encryption. The only real protection is limiting who may read Secrets (RBAC).

If this one was shaky, reread "base64 is not encryption."

2. A new pod is stuck in CreateContainerConfigError, and kubectl logs says "waiting to start". Where do you look, and what's the likely cause?

Show answer

In kubectl describe pod, at the events at the bottom. The app never ran, so there are no logs. The likely cause is a ConfigMap or Secret name the pod refers to that doesn't exist (a typo).

If this one was shaky, reread "How a pod gets the values" and demo step 7.

3. You change TICKER to MSFT with kubectl apply. describe cm shows MSFT, but the app still shows AAPL. Why, and what's the zero-downtime fix?

Show answer

Env vars are copied only when a container starts. Run kubectl rollout restart deploy/investment-app to replace the pods one by one.

If this one was shaky, reread "copied once, at start."
