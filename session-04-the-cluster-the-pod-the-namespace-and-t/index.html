Why an orchestrator: the Auto Scaling group, for containers

Problem: docker run gives one container on one machine. Process exits → container stops. Machine replaced → container gone. Nothing starts it again. A company runs tens of images, several copies each (Stash runs every service this way). Nobody can babysit them by hand.

You've seen the fix before: the Scale ASG with desired = 2. An instance died, a replacement launched, nobody typed anything. Desired state: you tell Kubernetes "5 copies of my website," and it keeps making reality match.

Kubernetes featureWhat it means
Self-healingA copy crashes → it notices and starts a new one
AutoscalingTraffic spike (Black Friday) → more copies; traffic drops → fewer
Load balancingSpreads requests across all the copies
Kubernetes does for containers what the Auto Scaling group did for instances.

The cluster: control plane + nodes

PartJobKitchen analogy
API serverReceives every kubectl command. The only way in.The waiter: you never walk into the kitchen
etcdThe cluster's record of every object: what should existThe waiter's order pad
SchedulerPicks a node for each new pod, spreading them evenlyThe seating host

Control plane (a.k.a. master nodes): with EKS, AWS runs it and you never log in. That's what the EKS fee buys.

Node: an EC2 instance that runs your containers. Containers never run on the control plane. More nodes = more money.

etcd is not your app's database and doesn't hold logs. It's the cluster's memory of what exists and where.

A cluster is a control plane plus its nodes.

The pod: the smallest thing Kubernetes runs

Pod: one or more containers that run together on one node, with one IP. In practice, one pod = one container (yours). Kubernetes never runs a bare container. It's always wrapped in a pod, like a gift wrapped before it's handed over.

A pod is NOT…Because
An EC2 instanceThe node is the EC2 instance. The EC2 console shows the node, never the pod.
On your laptopkubectl runs on the laptop; the pod runs in AWS. Its IP is on the cluster's network, which your laptop can't reach.
Replaced on its ownDelete a pod made from its own file and nothing brings it back. Replacing pods is a controller's job (Deployment, Wednesday).

Where the image comes in: Dockerfile → docker build → push to ECR (unit 1). The pod's YAML names that image, and the node pulls it.

If the container's process exits, Kubernetes restarts the container inside the same pod, on the same node. That's why a pod keeps a server running.

Two extra container types for later: an init container runs once before the main one and exits; a sidecar runs the pod's whole life beside it (e.g. to ship logs).

The only way to see or touch a pod from your laptop is a kubectl call to the API server.

The namespace: your room in the shared house

The school runs one cluster (containers-26a). You don't build a cluster; you get a piece of one. A namespace is a set of object names inside one cluster. Your pods, quota and permissions live in yours, named after you.

Why: if everyone could act on every pod, one typo in kubectl delete pod mo2 deletes someone else's app.

Not a machine, not a network. Pods from many namespaces share the same nodes, and one namespace can span several nodes. Your limit: 8 pods at once. Every cluster has a default namespace. Companies don't run apps there, and you have no permissions in it.

Cluster = the house. Namespaces = the rooms. You can only act in a room you have permission for.

The context: which cluster, as whom, which namespace

kubectl reads ~/.kube/config. One entry there is a context = a cluster + an identity + a namespace. One context is current, and every command uses it silently. At work you'll have dozens of clusters in that file.

aws eks update-kubeconfig writes the context (once per laptop). --alias gives it a short name instead of a ~170-character ARN.

The first time, the context has no namespace, so kubectl get pods asks about default and gets Forbidden. Your account isn't broken. Fix once: kubectl config set-context --current --namespace=<you>. It's saved until you change it.

Read the Forbidden error as four facts: who asked (student:<you>), what (list pods), where (namespace default), the answer (no).

The manifest: what should exist, written in YAML

Manifest: a text file describing one Kubernetes object. It says what should exist, not steps to run, so line order doesn't matter, unlike a Dockerfile. Dockerfile → image. Manifest → object that uses the image.

YAML ruleMeaning
4 top-level keys, alwaysapiVersion, kind, metadata, spec
Indentation nestsA line indented under a key belongs to it. Examples use 2 spaces; any number works if consistent.
Spaces, never tabsA tab is an error.
Key, colon, spacename: nginx. A key with nothing after the colon (spec:) owns the indented lines below.
A dash = a list itemA second - name: under containers: adds a second container
# pod.yaml
apiVersion: v1          # which API
kind: Pod               # which kind of object
metadata:
  name: drill           # the pod's name
spec:                   # what it should be
  containers:
    - name: drill
      image: SCHOOL_ACCOUNT_ID.dkr.ecr.us-east-1.amazonaws.com/drill:v1
      ports:
        - containerPort: 8080
Don't memorize manifests; copy the example from the Kubernetes docs and change what you need. But type one per unit from memory, because interviews ask you to.

0 of 9 steps done

1. Sign in

The school's sign-in lasts one day, so this is the first line every class day.

aws sso login --profile 312-cluster              # opens the browser; approve it
aws sts get-caller-identity --profile 312-cluster # who am I on AWS?
What you should see

A JSON block with Account and an Arn containing your name.

2. Point kubectl at the school cluster

Once per laptop; it writes the context into ~/.kube/config.

aws eks update-kubeconfig --name containers-26a --region us-east-1 \
  --profile 312-cluster --alias containers-26a
kubectl config current-context
kubectl config get-contexts
What you should see

containers-26a, with a * next to it and an empty NAMESPACE column.

3. Hit the Forbidden error on purpose

So you recognize it later.

kubectl get pods
What you should see

Error from server (Forbidden): ... User "student:<you>" cannot list resource "pods" ... in the namespace "default"

4. Save your namespace into the context

kubectl config set-context --current --namespace=<your-namespace>
kubectl get pods
kubectl config get-contexts      # NAMESPACE column is filled in now
What you should see

Context "containers-26a" modified. then No resources found in <your-namespace> namespace.

5. Look at the cluster

If get nodes is refused for your user, that's a permission, not a broken setup; skip it.

kubectl get nodes
kubectl get namespaces
What you should see

Node names like i-0b0e… with STATUS Ready, and everyone's namespaces plus default.

6. Write the pod manifest

Type it yourself, spaces only. Maher used nginx:1.14.2 on port 80; the unit uses the school's drill image.

# pod.yaml
apiVersion: v1          # which API
kind: Pod               # which kind of object
metadata:
  name: drill           # the pod's name
spec:                   # what it should be
  containers:
    - name: drill
      image: SCHOOL_ACCOUNT_ID.dkr.ecr.us-east-1.amazonaws.com/drill:v1
      ports:
        - containerPort: 8080
What you should see

A file with the four top-level keys and the drill image.

7. Run the two checks, then apply

The file stays on your laptop; its contents go to the API server.

aws sts get-caller-identity --profile 312-cluster   # check 1: which account
kubectl config get-contexts                         # check 2: which cluster + namespace
kubectl apply -f pod.yaml
kubectl get pods -o wide
What you should see

pod/drill created, then STATUS ContainerCreating → Running, an IP like 10.20.x.x, and a node name.

8. Read what the cluster did, step by step

Scroll to Events at the bottom.

kubectl describe pod drill
What you should see

Events in order: Scheduled → Pulling → Pulled → Created → Started. That's the whole Miro drawing, in text.

9. Delete it and notice nothing replaces it

kubectl delete pod drill
kubectl get pods
What you should see

pod "drill" deleted, then an empty list. Wednesday's Deployment is what brings pods back.

If it goes wrong

ErrorMeaning
Forbidden ... in the namespace "default"No namespace in your context. Step 4, or add -n <your-namespace>.
Token has expired / SSO errorsThe one-day sign-in ran out. Rerun aws sso login --profile 312-cluster.
error converting YAML / found character that cannot start any tokenA tab or mixed indentation in the file. Use spaces only.
Pod stuck in ImagePullBackOffWrong image URI, or your own ECR image isn't readable by the cluster's node role (unit 1 repository policy).
Can't find the node in the EC2 consoleWrong region. The cluster is in us-east-1; find it in EKS → cluster → Compute tab.

Clean up

kubectl delete pod drill --ignore-not-found   # frees one of your 8 pod slots
kubectl get pods                              # empty again

No AWS resources of your own were created, so nothing else costs money.

What the instructor stressed, and what's next

Stressed in class

  • Two checks before anything that changes state (apply, delete, scale): get-caller-identity and get-contexts. A team once ran a dev destroy script while the context pointed at production; it took hours to recover.
  • You'll rarely touch the control plane at work. Know what each part does; real problems are usually in pods, deployments and the app itself.
  • Kubernetes knows pods, not containers. Repeated several times, with the gift-wrap analogy.
  • The cluster is on AWS's side of the fence, not your laptop. Your laptop only talks to the API server.
  • Don't follow along typing during theory. Listen first, then do the hands-on.
  • Don't fight the setup alone; do it when Bakhtiyar is there to fix errors on the spot.
  • Kubernetes "sounds hard, but isn't."
