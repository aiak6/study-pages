Inside one server

The big architecture picture draws each EC2 as an empty box. This is that box cut open — what happens once at boot, what happens on every request, and which layer each failure comes from.

Not answering? Check in this order

AskWhere you lookWhat it rules in or out
1 Did the boot script finish, and did every step succeed?
/var/log/cloud-init-output.log		 Install failed, a package was missing, a step was refused (often the IAM policy). If this log ends early, nothing below matters yet.
2 Is the service running?
systemctl status <app>		 Three different answers: not found (the unit was never installed), failed (it tried and died — the reason is right there), active (move on).
3 Is anything listening, and on which address?
ss -tlnp		 Whether the app opened its port at all — and crucially whether it bound to 127.0.0.1 (only this machine) or 0.0.0.0 (reachable). This is the "works on the box, not from a browser" case.
4 Service is up but answers are wrong.
journalctl -u <app> or the app's own log		 A crash on each request, a missing environment variable, or a database it cannot reach. The machine is fine; the code or its config is not.

Refused or timed out — they mean opposite things

Connection refused

You got an answer, and the answer was "no".

The machine was reached — so the network path, security group and routing are fine. Nothing is listening on that port. Look at: the service being dead, the app bound to 127.0.0.1 only, or the wrong port. Good news, really: it narrows the problem to the machine itself.

Connection timed out

You got silence.

Nothing answered at all — packets were dropped somewhere on the way, so you never got as far as the machine. Look at: the security group not allowing your port, the route table, a NACL, the wrong subnet, or the instance simply being gone. The problem is the path, not the app.

Three things that come up every time

start vs enable

systemctl start — running now, gone after a reboot. systemctl enable — will start at boot, not running yet. enable --now does both.

To prove it: reboot the machine, log in to nothing, and load the site. systemctl is-enabled <app> should say enabled.

why a reverse proxy

It lets your app bind to loopback only, so the only way in is through nginx. It also serves static files, absorbs slow clients, and can handle TLS, redirects and gzip.

The cost: one more thing to configure and debug, and one more place a request can die. A 502 means nginx is healthy but couldn't reach your app.

the SSH key pair

The public key sits in ~/.ssh/authorized_keys on the server; the private key stays on your laptop. The server sends a challenge, your client signs it, the server verifies with the public key — the private key never travels.

Keep it off the server: anyone who got into that box would inherit your identity everywhere that key is trusted.
