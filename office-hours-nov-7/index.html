The gist

The whole session in 5 lines

  1. A cluster lives inside one VPC — but one VPC can hold several clusters.
  2. To picture it all, split it into three levels: real resources, creation tools, and navigation.
  3. kubectl needs two pointers: who you are in AWS, and the cluster's address.

1 · Mental model

The big picture in three levels

Why did the instructor split the diagram into three levels?

Show answer

Because the pieces are not all the same kind of thing. Mixing them is what makes the picture confusing.

LevelWhat it holds
Physical + virtual groupingAWS account, VPC, EKS control plane, EC2 worker nodes, your laptop
Creation toolsTerraform, kubectl, Helm, Ansible — just labels, they don't live anywhere
NavigationHow a tool knows which account and which cluster to talk to

Which parts actually "exist", and which are just tools?

Show answer

The cluster, the nodes, the network and the account are the things that exist and cost money.

Terraform, kubectl and Helm don't exist anywhere — they're just how you ask for something. The instructor's words: they're like a language. You speak, the cloud does the work.

Where does my laptop fit in the picture?

Show answer

Outside AWS, on the public internet. Between your laptop and the AWS cloud there is only the internet. Everything else — accounts, VPCs, clusters, workers — is inside AWS.

your laptop → internet → AWS cloud → AWS account → VPC → EKS cluster → worker EC2s
2 · Networking

VPC, accounts and the cluster

Can one cluster live in two VPCs?

Show answer

No. A cluster launches in one network and stays there.

"Can you be in two apartments at the same time?" Almost nothing in AWS belongs to two networks.

Can one VPC hold more than one cluster?

Show answer

Yes. Two, five, as many as you want in the same VPC.

The reason to do it: they're on the same network, so they can talk to each other. If you don't want them talking, put them in separate VPCs — that's the whole point of network isolation.

What is the difference between an AWS account and a VPC?

Show answer
Isolates
AWS accountpermissions — who is allowed to touch what
VPC (network)traffic — what can reach what

Normally a VPC lives inside one account. It is technically possible to stretch a network across accounts with special AWS features, but 99% of the time it doesn't happen.

Our RDS database and our EKS cluster are in the same VPC — can they talk automatically?

Show answer

Almost. Same network means the road exists, but there's still one more guard: the security group.

The RDS security group has to allow connections from the cluster's security group. Same VPC is not the same as "allowed".

And if the database is in a different VPC?

Show answer

Then by default they cannot reach each other at all. You'd have to build a connection between the networks: VPC peering or a Transit Gateway. That's extra setup — it doesn't happen by itself.

So the choice is yours when you design it:

  • same VPC → simpler networking
  • separate VPC → stronger isolation, more work to connect
3 · Navigation

How kubectl finds the right cluster

I type kubectl get namespaces on my laptop. How does it find MY cluster out of thousands?

Show answer

It doesn't guess. You give it two pointers:

  1. AWS identity pointer — which account, and do you have permission. From ~/.aws/config and ~/.aws/credentials, or environment variables.
  2. Kubernetes identity pointer — the cluster's endpoint, a DNS address, stored in your kubeconfig.
Address + credentials. That's all any client ever needs. The rest — DNS, routing, IPs — the internet handles.

What does the cluster endpoint look like?

Show answer
projectx-eks.<account-id>.us-east-1.eks.amazonaws.com

Every EKS cluster gets its own DNS address.

Does kubectl need to know which VPC the cluster is in?

Show answer

No — and this is the key idea. It doesn't need to know everything, it just needs to know something: the endpoint.

If you know somebody's address and you have the key, you can get in. You don't need to know how the house was built.

What does aws eks update-kubeconfig actually do?

Show answer

It gets you both pointers in one command: the cluster's endpoint and the credentials, written into your kubeconfig.

aws eks update-kubeconfig --name <cluster> --region <region>

What does Terraform need? Is it the same?

Show answer

Simpler — Terraform only needs the first pointer, the AWS credentials.

It talks straight to the AWS API server, not to Kubernetes. It gets into the right account, asks AWS to create resources, done.

So where exactly does a kubectl command land?

Show answer

Not "at the cluster" — a cluster is a collection of things. It lands at one program: the Kubernetes API server, running on the control plane.

That endpoint address is the address of that program. Everything you do to the cluster, you do through it.

AWS has an API server. Kubernetes has an API server. Same pattern.
4 · The request

What happens after kubectl apply

Does kubectl apply go and create the EC2 workers?

Show answer

No. This was the main misunderstanding cleared up in the session.

kubectl apply only sends a request — "hey, I need a deployment with five replicas". At that moment kubectl's job is finished.

Then what actually decides where pods run?

Show answer

Programs on the control plane: the controller, the scheduler and a few others. They receive the request and do the thinking:

  1. A request came in for 5 containers.
  2. Do we have worker nodes with room?
  3. If yes → send a request to the kubelet on that node.
  4. If no → the pods sit in Pending.
That's why it's called an orchestration system — you send a request, the system handles it.

Is there an easy way to remember this?

Show answer

Two pictures the instructor used:

  • Warehouse: you don't tell the warehouse which shelf to put your box on. You say "ship five boxes." How they do it is their problem.
  • Car shipping: you submit a request on a website. Brokers find a driver, check the route, the dates, the space. You don't do any of that.

kubectl is not a magic command that does everything. The cluster does the heavy work.

So what is my job as the operator?

Show answer

To give Kubernetes enough physical resources — mostly worker nodes — so it has somewhere to put the containers. The placement itself isn't yours to do.

5 · The agent

Kubelet — the agent on every worker

What is kubelet, and do we create it?

Show answer

It's a Kubernetes program, like etcd, the controller manager, the API server and the scheduler — but it's the one exception: it doesn't run on the control plane. It runs on every worker node.

You don't create it yourself; it's part of how a node joins the cluster.

What does kubelet do?

Show answer

It's the control plane's representative on that node — the instructor called it an embassy.

  • the control plane tells kubelet "launch this container" → kubelet launches it
  • kubelet reports back: running, healthy, failing, not passing the readiness probe, pending, not enough resources
  • your logs come back through kubelet too

No kubelet on a node = you learn nothing about that node, because everything goes through that agent.

Control plane vs worker — which programs live where?

Show answer
WherePrograms
Control plane (master nodes)API server, scheduler, controller manager, etcd
Every worker nodekubelet (+ kube-proxy)

The control plane is not where your applications run. It's where Kubernetes' own programs run.

6 · Comparison

ECS vs Kubernetes

Why didn't we study ECS properly?

Show answer

Because it isn't the core of what we're learning — but it matters for context. Kubernetes is the leader; ECS, Nomad and Docker Swarm are other brands of the same thing.

They all make the same promise: manage thousands of containers across hundreds of nodes. You can't do that by hand — that's the whole point of a cluster.

What does "cluster" actually mean?

Show answer

When you group the resources of several servers together and use them for one purpose. Here: running many containers in one place.

Example from the session: Netflix runs most of its platform on very large Kubernetes clusters — tens of thousands of containers across thousands of nodes.

How different is ECS really?

Show answer

The concepts are mostly the same, the tools are different. The instructor's comparison: BMW vs Volkswagen — different choices, same idea of a car.

ECS needs the same things Kubernetes needs: a way to connect and manage the cluster (its own API), and nodes where containers run, maybe under a different name.

How do you deploy into each one?

Show answer
KubernetesECS
Define the workloadDeployment YAMLECS task / service definition
Apply itkubectl apply, HelmAWS CLI, CloudFormation
Also possibleTerraform, AnsibleTerraform, Ansible

kubectl and Helm were built by the Kubernetes project, so they only work with Kubernetes. ECS is an AWS service, so it works with AWS tools.

Does doing this migration make me an "ECS expert"?

Show answer

No, and don't claim it. You're taking container images out of ECS and repackaging them for EKS — you're not operating ECS itself.

Only study ECS deeply if you plan to put strong ECS experience on your resume and defend it in an interview. Otherwise: understanding Kubernetes is enough.

7 · Tooling

Which tool can do what

Can kubectl and Helm create the cluster itself?

Show answer

No. They are limited to what's inside the cluster: create or delete a deployment, a service, a pod. They cannot create a node or a server.

ToolCreate the clusterManage things inside it
kubectl❌✅
Helm❌✅
Terraform✅✅ (possible)
Ansible✅✅ (possible)
CloudFormation / AWS CLI✅ (ECS)✅ (ECS)

Can Terraform really create Kubernetes resources?

Show answer

Yes — there's a Kubernetes provider, and a deployment resource looks roughly like this:

resource "kubernetes_deployment" "example" {
  metadata { name = "my-app" }
  spec {
    replicas = 3
    selector { match_labels = { app = "my-app" } }
    template {
      spec {
        container {
          image = "nginx:1.27"
          name  = "my-app"
          resources { limits = {} requests = {} }
        }
      }
    }
  }
}

Some companies do it. The instructor doesn't think it's great. In practice: Terraform builds the cluster, then kubectl and Helm manage what's inside.
