Everything in the cluster is stored as YAML (-o yaml)

Problem: something is running, but you have no file for it (a teammate made it, or it was made with a command). kubectl get <kind> <name> -o yaml prints the object the cluster has stored. It works on anything: pods, deployments, ReplicaSets, namespaces.

Like cat for cluster objects. It also shows extra fields Kubernetes adds: status, timestamps, the pod-template hash. Exam use (CKA-style): some fields can't be changed in place, so you copy the YAML into a file, edit it, delete the old object and apply the new one. You don't write ReplicaSets yourself; the Deployment creates them.

The cluster's copy is the truth. Your file is only what you asked for last time.

The file wins: apply after scale

kubectl scale deploy/drill --replicas=3 changes the count stored in the cluster. kubectl apply -f then compares your file to the stored object and changes what differs: file says 2 → back to 2, no warning. Same as Terraform's apply. Manual commands (scale, set image, rollout undo) change the cluster, never your local file. Real work edits the file and applies it.

Two things restart things

The kubeletThe ReplicaSet's controller
What it isThe agent on every nodeThe control-plane loop that keeps the count
Acts whenA container exitsA pod is gone (deleted, or its node died)
What it doesRestarts the container in the same podCreates a brand-new pod
Name / IPSame name, same IP; RESTARTS +1New name (new hash), new IP

The IP belongs to the pod, not the container. That's why a container restart keeps it. The kubelet knows nothing about the count; the ReplicaSet knows nothing about processes.

port-forward: a tunnel from your laptop to one pod

Problem: pods live on the cluster's private network. Your laptop has no route there, so curl <pod-ip>:8080 times out. Fix: kubectl already talks to the API server, so the API server carries the connection for you.

curl localhost:8000 → kubectl (your laptop :8000) → API server → pod :8080 → back the same way

The rolling update, and the undo

Problem: replacing every pod at once means downtime. A rolling update always keeps some pods answering. Any change under template starts a rollout: image, env var, command, a pod label. Changing replicas does not.

ReplicaSet #1 v1
ReplicaSet #2 v2

The old ReplicaSet stays at 0 pods: that's what rollout undo goes back to. After a rollout, restart port-forward, because the old tunnel went to a pod that no longer exists. Scale equivalent: the instance refresh with its minimum healthy percentage.

The old ReplicaSet isn't deleted. It's kept at zero so you can roll back.

The stop signal: exec form vs shell form

PID 1 = the first process in the container (Session 01). SIGTERM = the polite "please stop" signal. Grace period = how long Kubernetes waits after sending SIGTERM to PID 1 before it force-kills with SIGKILL. 30 s by default.

Exec formShell form
CMD lineCMD ["gunicorn", "--bind", "0.0.0.0:8080", "app:app"]CMD gunicorn --bind 0.0.0.0:8080 app:app
PID 1gunicorn itself/bin/sh -c; gunicorn is its child
On SIGTERMgunicorn hears it, finishes, exitsThe shell doesn't pass it on. gunicorn never hears it.
Delete tookabout 3 sabout 32 s (waits out the full 30, then SIGKILL)
Every rollout and every scale-down waits that extra 30 s per shell-form pod. Use exec form (square brackets).

Reading a pod that isn't Running: get → describe → logs

#CommandTells you
1kubectl get podsThe status word. It tells you which command to run next, not what's wrong.
2kubectl describe pod <name>The Events block: what the cluster did to the pod, step by step, and where it failed
3kubectl logs <name>What the process printed. No process started = nothing to show.
Cluster failures happen before the process exists, so describe comes before logs.

Lab: diagnose the three broken pods

Pick a pod, then run the three commands in order. The verdict appears once you find the cause.

PodStatusCauseShown byImage or process?
image-pullImagePullBackOffTag v0 doesn't exist → not founddescribeImage (can't be fetched)
wrong-archCrashLoopBackOffexec format error: built for arm64 (Mac), nodes are amd64logs (one line)Image (wrong processor)

ErrImagePull = the pull failed. ImagePullBackOff = it keeps retrying with longer waits. If the ECR repo policy from unit 1 is missing, the status is the same but the Failed line says forbidden instead of not found. Pod not yours? kubectl get pod image-pull -o yaml shows the exact image name to look up in ECR; typos in the tag are common.

CrashLoopBackOff = the container starts and exits. The kubelet restarts it with growing waits (up to 5 min), and RESTARTS climbs each time you look. Fix for wrong-arch: docker build --platform linux/amd64 ... (from unit 1).

command and args replace ENTRYPOINT and CMD

ENTRYPOINT (Dockerfile) = the program the container always runs. CMD = its default arguments. With no ENTRYPOINT, CMD is the whole command.

ENTRYPOINT ["echo", "hello"]
CMD ["world"]          # container prints: hello world
DockerfilePod fileOverride at docker run
ENTRYPOINTcommanddocker run --entrypoint ... (harder)
CMDargsJust add arguments after the image (easy)

Set only args: ["Mo"] on the image above → ENTRYPOINT stays → prints hello Mo. Why: change what a container runs without rebuilding and re-pushing the image.

restartPolicy: Never = don't restart a container that exits, so the pod shows Completed instead of CrashLoopBackOff. command: ["sleep", "3600"] gives you a pod that stays up to exec into. vs docker exec: exec is you going inside to type commands; ENTRYPOINT/CMD is the container running something on its own.

command = ENTRYPOINT. args = CMD.

Where the notes correct what was said live

Left: what was said in class. Right: the correct version from the site notes and deck.

Said in classCorrect version (site notes and deck)
"If you want a grace period, use shell form"Backwards. Shell form takes the grace period away from the app. It never gets SIGTERM and is killed without warning after 30 s. Exec form is what lets the app finish its open requests.
"The kubelet sends a signal to the control plane to restart the container"The kubelet restarts the container itself, without asking the control plane first. It only reports status.
"The nodes are ARM64 Linux, not Mac"The nodes are amd64. A Mac builds linux/arm64 images.
"CMD is the fallback if ENTRYPOINT fails"CMD is ENTRYPOINT's default arguments, or the whole command when there's no ENTRYPOINT
"docker build --entrypoint"It's docker run --entrypoint

3. Delete a pod and watch it come back

Two terminals.

kubectl get pods -w                       # terminal 2
kubectl delete pod <one-drill-pod>         # terminal 1
What you should see

In terminal 2, the old pod Terminating and a new one with a new name going to Running.

4. Scale, then let the file win

kubectl apply -f deployment-drill.yaml    # file says 2: back to two, no error
What you should see

Three pods, then two.

5. Open the tunnel and curl

kubectl get pods -o wide                  # note a pod IP
curl <pod-ip>:8080                        # times out
kubectl port-forward deploy/drill 8000:8080   # terminal 1
curl localhost:8000                       # terminal 2
What you should see

Hello from the drill app. Ctrl+C the tunnel and curl fails with Couldn't connect to server.

6. Rolling update to v2, then undo

drill= is the CONTAINER name.

kubectl set image deployment/drill drill=<registry>/drill:v2
kubectl rollout status deploy/drill
kubectl get rs                            # old RS at 0, new RS at 2
kubectl port-forward deploy/drill 8000:8080   # restart it
curl localhost:8000                       # version 2
kubectl rollout undo deploy/drill
What you should see

After the undo, restart port-forward and curl prints the v1 message. kubectl describe pod shows the v1 image.

7. Time the two deletes

kubectl apply -f pod.yaml -f pod-shell-form.yaml
time kubectl delete pod drill             # exec form
time kubectl delete pod drill-shell       # shell form
What you should see

The real line at the bottom: about 3 s vs about 32 s.

kubectl logs command-args

What the instructor stressed, and what's next

Stressed in class

  • Look it up in the Kubernetes docs. Every resource has an example manifest there; Mo copies from it instead of memorizing.

  • Typos in image tags cause a lot of real ImagePullBackOffs. Compare letter by letter.
