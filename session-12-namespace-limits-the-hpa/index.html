Session 12: Namespace limits & the HPA

Thu, Oct 22, 2026Maher (Mo) + after class with Bakhtiyarkubectl patch · Pending & taints · LimitRange · ResourceQuota · HPA · Karpenter

Unit 5, part 2. Session 11 explained request, use and limit. Tonight the investment app actually gets them, with kubectl patch, which changes the Deployment in the cluster but not your file. Then the namespace's own rules: a LimitRange that fills in missing values and rejects anything over a per-container maximum, and a ResourceQuota that caps the whole namespace, so a pod over it is never even created. Then scaling: the HPA adds pods when CPU (measured against the request) passes a target, and Karpenter adds nodes when pods don't fit. It ends on the limit of all that scaling: when the database is down, no number of pods brings the app back.

Recap: placement vs execution

  • A namespace sits on top of all the nodes. Your pod may land on node 1, 2 or 3, and its container takes CPU and memory from that node (an EC2 instance).
  • With no requests or limits, one pod can eat a whole node and starve every other pod there, from any namespace (Session 11).
  • Placement = what must fit before a pod starts (requests). Execution = what happens at a limit: CPU → throttled, memory → OOMKilled (the container restarts in the same pod, RESTARTS +1).
  • kubectl top pods -l app=investment-app showed 1m CPU and 81Mi. That's a snapshot, not a history.
  • Two nodes with 400m free each can't hold a 600m pod: a pod's request must fit on one node.

kubectl patch: requests & limits on the running app

cd 05-health-and-capacity
kubectl get deployment investment-app -o yaml       # resources: {}  → nothing declared yet
kubectl patch deployment investment-app --type=strategic \
  --patch-file investment-app-resources.patch.yaml
kubectl rollout status deployment/investment-app --timeout=120s
kubectl get deployment investment-app -o yaml       # resources now has requests + limits
  • What patch is: like k edit, without opening vi and scrolling to resources:. You hand Kubernetes only the piece that changes.
  • The patch file doesn't start with apiVersion or kind. It starts at the place it changes. Kubernetes walks the live YAML by indentation: spec → template → spec → containers → the container name: investment-app → resources, and merges the values in.
spec:
  template:
    spec:
      containers:
      - name: investment-app
        resources:
          requests:
            cpu: 100m
            memory: 128Mi
          limits:
            cpu: 250m
            memory: 256Mi
  • Two replicas × 100m / 128Mi = 200m CPU and 256Mi of requests in total.
  • Changing the pod template = a rollout: new ReplicaSet, new pod up, old pod down (Session 06). rollout status doesn't do the rollout; it watches it, here for up to 120 s.
  • After the patch, top still shows ~1m used, but 100m is reserved on the node. The scheduler counts the request, not the use.
  • Editing the file and running kubectl apply -f gives exactly the same result. Patch is for changing something in place.
  • 💡 Mo's real use: when terraform destroy hangs because a namespace is stuck on its finalizers, you patch the finalizers off the namespace so the cluster (and its bill) can go away.
🔑 Patch changes the cluster (etcd), not your file. If a teammate later runs kubectl apply -f with the old file from Git, your patch is gone. Put the same resources: in the file and push it.

Pending: three reasons a pod has no node

kubectl describe pods -l app=investment-app     # Events at the bottom
ReasonMeansWaits for
Not enough capacityNo node has the free CPU/memory the request asks forRoom, or a new node
Placement ruleNo node matches the pod's requirements, e.g. every node has a taint the pod doesn't tolerateYou to fix the rule
Node unavailableA suitable node exists but isn't Ready yet (an autoscaler just launched it)A few minutes
  • PodScheduled: False + FailedScheduling = no node assigned. The event names the reason.
  • Taint and toleration, Mo's analogy: a taint is bug spray on a node. A pod without a matching toleration can't land there; a pod with one can. If every node is "sprayed", the pod stays Pending.
  • Why teams use taints: keep ordinary pods off GPU nodes, give one app nodes of its own, or isolate workloads for security. Banks and government apps don't want to share a machine. (Affinity and taints get their own class later.)
  • A pod can also be Pending after it has a node, while its image downloads.

LimitRange: defaults & a maximum per container

kubectl get limitrange -o yaml                         # your namespace's policy
kubectl get pods -l app=investment-app -o yaml         # the resources each pod actually got
  • A LimitRange is a namespace policy, written by the cluster admins. It does two jobs:
    • Fills in requests and limits a container didn't declare.
    • Rejects a container above its maximum (403 Forbidden; the pod isn't created).
Student namespaceCPUMemory
Default request50m64Mi
Default limit250m256Mi
Max per container1 (= 1000m)1Gi
  • A value you write is kept: a 100m request stays 100m. A 2 CPU limit is rejected.
  • Checked only at admission (when the pod is created). Lowering the max doesn't touch running pods; only new pods are refused.
  • Two LimitRanges in one namespace: which defaults apply is unpredictable. Keep one.
  • CPU written without m (1) means a whole core.
  • The instructor namespace has no LimitRange or quota, which is why Mo and Bakhtiyar ran their demos against a student namespace or saw nothing refused.
🔑 The maximum is not a default.
🧮

ResourceQuota: a total for the whole namespace

kubectl describe resourcequota                     # Used vs Hard
kubectl apply -f deployment-quota-failure.yaml     # asks for 600m CPU
kubectl get pods -l app=unit5-quota                # No resources found
kubectl describe rs -l app=unit5-quota             # FailedCreate ... exceeded quota
kubectl delete -f deployment-quota-failure.yaml
  • A ResourceQuota adds up what every pod in the namespace declares (not what it uses) and refuses a new pod that would push the total over the cap.
  • Your namespace: 500m CPU requests, 1Gi memory requests, 2 CPU limits, 2Gi memory limits, 8 pods. The app and Postgres you already run count toward these.
  • A 600m pod is refused even in an empty namespace: 600m > 500m.
  • The Deployment is accepted, but the ReplicaSet can't create the pod. So get pods shows nothing (not Pending), and the error lives on the ReplicaSet: forbidden: exceeded quota … requested: requests.cpu=600m, used: requests.cpu=0, limited: requests.cpu=500m.
LimitRangeResourceQuota
ChecksEach containerThe namespace total
Says"No single container may ask for more than X""The namespace may not ask for more than Y in total"
Over itPod rejected (403)Pod never created (FailedCreate on the RS)
  • You can use both together. LimitRange alone still lets you run 100 pods at 1 CPU each, and the quota stops that.
  • None of the three (container resources, LimitRange, ResourceQuota) is set on a node. A node only has its capacity.
  • 💡 Why it exists: each team gets its own namespace, and the quota stops one team using the whole cluster and its cost. Mo: when a team hits the quota, the increase goes through finance and management, not through you. Expect people to DM you, then your teammate, asking for it anyway.
🔑 A bigger or extra node doesn't help. The quota belongs to the namespace, not to a machine.

The HPA: more traffic, more pods

traffic rises → each pod does more work → CPU use rises → HPA reads the metrics → raises the Deployment's replicas → the Service spreads requests over more pods
  • The Horizontal Pod Autoscaler (HPA) is a controller that changes a Deployment's desired pod count toward a target, between minReplicas and maxReplicas.
  • Same idea as the ASG in Scale Session 09–10 adding an EC2 at 70% CPU. Here it's pods instead of instances.
  • It measures utilization against the request:
utilization = measured CPU ÷ requested CPU × 100 = 200m ÷ 100m × 100 = 200% → target 60% → add pods
  • It also needs working metrics: if kubectl top fails, the HPA can't see CPU either.
  • In Mo's simulator, the pod count went up at ~60–69%. The pause before the new pod appeared is the pod starting.
  • The demo HPA (hpa-cpu-demo.yaml) targets the unit5-cpu Deployment: 60%, 1–2 replicas. Its pod requests 50m, so 60% = 30m per pod.
🔑 No CPU request = no percentage = no CPU scaling. Changing the request changes the percentage even when the app's real use doesn't change.

Karpenter: when pods don't fit, add a node

HPA raises replicas → scheduler places the pods that fit → a pod fits nowhere → Pending → Karpenter sees it → launches an EC2 worker → node Ready → pod scheduled
  • Our cluster runs EKS Auto Mode, which includes Karpenter: a node autoscaler managed by AWS. It watches for pods that can't fit and launches EC2 worker nodes, within its configured limits and available AWS capacity.
  • A new node can't fix a quota refusal. Karpenter might add a node, but the quota still blocks the pod.
  • (Live, Mo described it as watching the nodes' CPU and memory. The deck and notes say it reacts to pods that can't fit.)
🔑 The HPA changes the number of pods. Karpenter supplies machines. These are two separate kinds of scaling.
🩺

What more pods can't fix: the database is down

  • If the shared database goes down, every replica loses it. One pod or eight pods, it's the same outage. More replicas or more nodes don't help.
  • Readiness fails → the Service stops sending traffic to that pod until it can serve again (Session 08).
  • Liveness fails → the kubelet restarts the stuck container. A database outage should not fail liveness, because restarting every app container doesn't repair the database.
🔑 Liveness is for "my app is stuck". Readiness is for "I can't serve right now".

Quiz: Session 12

Self-test for Containers Session 12. Answer each question out loud first, then open the toggle to check. Score yourself out of 10.

Q1. You kubectl patch the Deployment with requests and limits. Next week a teammate runs kubectl apply -f deployment-investment-app.yaml from Git. What happens, and how do you prevent it?

Show answer

Your requests and limits disappear. Patch changed the object stored in the cluster (etcd), not the file. Applying the old file sends the old desired state (resources: {}), and a new rollout starts without them. Prevent it by putting the same resources: block in the YAML and pushing it, or by making the change in the file and running kubectl apply in the first place.

Q2. Why does the patch file start at spec: and not at apiVersion and kind? How does Kubernetes know where to put resources?

Show answer

Because it's a fragment, not a whole object. Kubernetes merges it at the matching path. The command already names the object (deployment investment-app). A strategic merge walks the live YAML: spec → template → spec → containers → the item whose name is investment-app → resources. It adds or replaces only what's in the fragment and leaves the rest alone. Matching containers by name (not list position) is what makes it "strategic".

Q3. A pod is Pending. Name the three reasons the scheduler might give, and the one that will fix itself if you just wait.

Show answer

Not enough capacity, a placement rule, or the node isn't Ready yet. The last one fixes itself.

  • Not enough capacity: no node has the free CPU/memory the request asks for.
  • Placement rule: e.g. every node has a taint the pod doesn't tolerate. It stays Pending until you fix the rule.
  • Node unavailable: a fitting node (e.g. one Karpenter just launched) is still starting. Wait, and the pod gets scheduled.

All three show as PodScheduled: False / FailedScheduling in describe. Separately, a pod can be Pending on a node while its image downloads.

Q4. Interview: "Your platform has GPU nodes that cost 10× more. How do you stop ordinary pods landing on them?"

Show answer

Taint the GPU nodes, and give a toleration only to the workloads that should run there. A taint is like bug spray on the node: any pod without a matching toleration is kept off, so ordinary pods schedule elsewhere. The GPU workloads carry the toleration (usually plus a node selector or affinity, so they're also attracted to those nodes). Same tool for isolating a bank's or a government app's workloads on their own nodes.

Q5. Your namespace's LimitRange has a max of 1 CPU and a default request of 50m. Container A declares nothing. Container B declares requests: cpu: 100m. Container C declares limits: cpu: 2. What does each get?

Show answer

A gets the defaults, B keeps its 100m, C is rejected.

  • A: request 50m / 64Mi and limit 250m / 256Mi, filled in at admission.
  • B: a value you write is kept, so 100m stays 100m (its missing limit gets the 250m default).
  • C: 2 CPU is over the 1 CPU max, so the pod is refused with 403 Forbidden. The maximum is a ceiling, not a default.

Q6. LimitRange vs ResourceQuota: what does each one check, and why would an admin use both?

Show answer

LimitRange checks each container; ResourceQuota checks the namespace's total. LimitRange alone caps every container at, say, 1 CPU, but you could still run 100 such pods and take 100 CPUs. ResourceQuota caps the sum of what everything declares (500m CPU requests, 8 pods…), so one team can't take the whole cluster or its budget. Together they give "no pod too big" and "no team too big". Both count declarations, not measured use.

Q7. You apply a Deployment. kubectl get deploy shows 0/1, but kubectl get pods shows nothing at all, not even Pending. Where do you look, and would Karpenter adding a node help?

Show answer

Describe the ReplicaSet. And no, a node wouldn't help. No pod at all means creation was refused before scheduling. kubectl describe rs -l app=… shows FailedCreate … exceeded quota (e.g. requested 600m, limited 500m). The quota belongs to the namespace, so a new machine changes nothing. Lower the requests, delete something to free quota, or get the quota raised (through approval, not a DM).

Q8. A container shows Last State: Terminated, Reason: OOMKilled, but its peak memory was well under its 1Gi limit. How is that possible?

Show answer

The node ran out of memory, not the container. Limits are per container, but the node's RAM is shared. If the other pods on the node together use most of it, a container growing within its own limit can still find no memory left and be killed. So OOMKilled alone doesn't prove the container's own limit caused it. Compare its limit with the node's memory evidence, and set requests honestly so the scheduler doesn't overpack the node.

Q9. A pod requests 50m CPU and uses 40m. The HPA target is 60%. Does it scale out? Now someone "tidies up" the request to 100m with the same use. What happens, and what does that teach you?

Show answer

50m: 80% → scales out. 100m: 40% → doesn't. The HPA computes use ÷ request × 100, so the request is the HPA's ruler. Change the ruler and the same load reads differently. That's why CPU scaling needs a CPU request (no request, no percentage), and why requests and HPA targets must be chosen together.

Q10. Interview: "Traffic triples. Walk me through what Kubernetes does, from the HPA to new hardware, and name one failure that no amount of scaling fixes."

Show answer

HPA adds pods, the scheduler places them, Karpenter adds nodes for the ones that don't fit. A dead database isn't fixed by any of it.

  • CPU per pod rises past the HPA target (measured against the request), so the HPA raises the Deployment's replicas, up to maxReplicas.
  • The scheduler places the new pods where their requests fit. A pod that fits nowhere goes Pending.
  • Karpenter (EKS Auto Mode) sees Pending pods and launches EC2 nodes. The pods get scheduled once the node is Ready.
  • Limits still apply: a ResourceQuota can refuse pods regardless of nodes.
  • Not fixable by scaling: the shared database being down. Every replica loses it. Readiness should take pods out of the Service; liveness should not restart them for it.
