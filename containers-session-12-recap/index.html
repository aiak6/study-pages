Concepts

The main ideas, from zero

Patching a running Deployment: what it changes, and what it doesn't

  • Problem: the app runs with resources: {}, so it has no request and no limit.
  • kubectl patch edits the object stored in the cluster (in etcd) with only the part you give it. It's like k edit, without opening the editor.
  • The patch file doesn't start with apiVersion/kind. It starts at the path it changes: spec → template → spec → containers → (name: investment-app) → resources. Kubernetes walks the live YAML by indentation to find that place.
  • Values: requests 100m CPU / 128Mi, limits 250m CPU / 256Mi (×2 replicas = 200m / 256Mi of requests).
  • Changing the pod template = a rollout: new ReplicaSet, new pods, old ones removed. rollout status --timeout=120s only watches it.
kubectl patch → changes the Deployment in the CLUSTER (etcd) your YAML file → unchanged on your laptop / in Git teammate later runs kubectl apply -f old-file.yaml → your patch is GONE
After a patch, put the same change in the file and push it. Editing the file and running kubectl apply -f gives the same result as the patch.
  • top after the patch: the pod uses 1m, but 100m is reserved for it on the node. The request is what the scheduler counts.

Pending: three reasons a pod has no node

Reason (event in describe)MeansWaits for
Not enough capacityNo node has the free CPU/memory the request asks forRoom, or a new node
Placement ruleNo node matches the pod's requirements, e.g. every node has a taint it doesn't tolerateYou to fix the rule
Node unavailableA fitting node exists but isn't Ready yet (an autoscaler just launched an EC2)A few minutes
  • Taint / toleration: a taint is bug spray on a node. Only pods with a matching toleration can land there. Used for GPU nodes, an app that gets nodes of its own, and isolation (banks, government). Full lesson later.
  • PodScheduled: False + FailedScheduling = no node assigned. A pod can also be Pending on a node while its image downloads.

LimitRange: defaults and a maximum for each container

  • A namespace policy, written by the cluster admins. It does two jobs:
    • Fills in requests and limits a container didn't declare.
    • Rejects a container above its maximum (403 Forbidden, the pod isn't created).
  • Your namespace: defaults requests 50m / 64Mi, limits 250m / 256Mi. Max per container 1 CPU (= 1000m) / 1Gi.
  • A value you write yourself is kept: a 100m request stays 100m. A 2 CPU limit is rejected. The maximum is not a default.
  • Checked only when a pod is created (admission). Changing it doesn't touch running pods.
  • Two LimitRanges in one namespace = you can't predict which defaults apply.
  • A bare 1 for CPU means a whole core; m means millicores.

ResourceQuota: a total for the whole namespace

  • Adds up what every pod declares (not what they use) and refuses a new pod that would take the total over the cap.
  • Your namespace: 500m CPU requests, 1Gi memory requests, 2 CPU limits, 2Gi memory limits, 8 pods. That includes the app and Postgres you already run.
  • A 600m pod is refused even in an empty namespace: 600m > 500m.
  • The Deployment is accepted, but the ReplicaSet can't create the pod. So there's no pod (not Pending), and the error is on the ReplicaSet.
  • A new node doesn't help: the quota belongs to the namespace, not to a machine.
  • Why it exists: each team gets a namespace, and the quota stops one team using the whole cluster and its budget. Mo: raising it goes through finance and management, not through you, however often they DM you.
WhereCoversWho writes it
Container resources:One container's request and limitYou, in the Deployment
LimitRangeEach container: fills missing values, rejects above maxCluster admins
ResourceQuotaThe namespace's total requests, limits, pod countCluster admins
LimitRange: no single container may ask for more than X. ResourceQuota: the whole namespace may not ask for more than Y. None of them is set on a node.

Read the event on the object that failed

SymptomDescribeLook for
Pod Pendingkubectl describe pods -l app=…FailedScheduling: Insufficient cpu
No new pod at allkubectl describe rs -l app=…FailedCreate: exceeded quota
Container restartedkubectl describe pod <pod>Last State: Terminated, Reason: OOMKilled
  • OOMKilled doesn't prove the container's own limit caused it. If the pods on a node together use more memory than the node has, a container can be killed below its own limit. Mo's example was a 1Gi node with two pods at 250Mi each and a third growing from 500Mi to 600Mi. It is killed, restarts, grows again, and is killed again.

The HPA: more traffic, more pods

traffic rises → each pod does more work → CPU use rises → HPA (a controller) reads the metrics → raises the Deployment's replicas → the Service spreads requests over more pods
  • Horizontal Pod Autoscaler: changes the Deployment's desired pod count toward a target, between min and max replicas. Same idea as an ASG adding EC2s at 70% CPU (Scale stage).
  • It measures utilization against the request:
utilization = measured CPU ÷ requested CPU × 100 = 200m ÷ 100m × 100 = 200% (target 60% → add pods)
  • No CPU request means no percentage, so no CPU scaling. Changing the request changes the % even when use stays the same.
  • It also needs working metrics (kubectl top must work).
  • The lag in the simulator is the new pod starting.

Karpenter: when pods don't fit, add a node

HPA raises replicas → scheduler places the pods that fit → a pod fits nowhere → Pending → Karpenter (part of EKS Auto Mode, managed by AWS) sees it → launches an EC2 worker → node Ready → pod scheduled
  • HPA = more pods. Karpenter = more machines. Two separate ways of scaling.
  • It works within its configured limits and the capacity AWS has available.
  • A new node can't fix a quota refusal.

What more pods can't fix: the database is down

  • Every replica loses the shared database, so 1 pod or 8 pods, it's the same outage. More replicas and more nodes don't help.
  • Readiness failing: the Service stops sending traffic to that pod until it can serve again.
  • Liveness failing: the kubelet restarts a stuck container. A DB outage should not fail liveness, because restarting every app container doesn't repair the database.
The HPA fixes "not enough pods". Karpenter fixes "not enough nodes". Neither fixes a broken dependency or a quota.

Hands-on

Redo the demo yourself

Before you start:

  • aws sso login --profile 312-cluster, with your namespace set in the context.
  • git pull in the containers repo; you need 05-health-and-capacity/.
  • Session 11's app running: investment-app (2 pods) + postgres. The quota counts them too.
  • kubectl top pods works (metrics-server). The HPA needs it.
1

See that nothing is declared yet.

cd 05-health-and-capacity
kubectl get deployment investment-app -o yaml | grep -A3 resources   # resources: {}

resources: {} under the container (or the LimitRange defaults on the pods, since the LimitRange fills them in).

2

Patch in requests and limits, and watch the rollout. This adds them to the live Deployment, which starts a new ReplicaSet.

kubectl patch deployment investment-app --type=strategic \
  --patch-file investment-app-resources.patch.yaml
kubectl rollout status deployment/investment-app --timeout=120s
kubectl get deployment investment-app -o yaml | grep -A6 resources

deployment.apps/investment-app patched, then successfully rolled out, then requests: cpu: 100m, memory: 128Mi and limits: cpu: 250m, memory: 256Mi. patched (no change) means it was already applied.

3

Check nothing is Pending.

kubectl get pods
kubectl describe pods -l app=investment-app     # Events at the bottom

both pods Running. If one is Pending, read the FailedScheduling reason.

4

Read your namespace's two policies.

kubectl get limitrange -o yaml          # default, defaultRequest, max per container
kubectl get pods -l app=investment-app -o yaml | grep -A6 resources
kubectl describe resourcequota          # Used vs Hard for the whole namespace

LimitRange max cpu: "1", memory: 1Gi; quota requests.cpu 500m, pods 8, with your app's 200m already in Used.

5

Get a quota refusal. This Deployment asks for 600m, more than the whole namespace may request.

kubectl apply -f deployment-quota-failure.yaml
kubectl get pods -l app=unit5-quota          # No resources found
kubectl describe rs -l app=unit5-quota       # Events: FailedCreate
kubectl describe resourcequota
kubectl delete -f deployment-quota-failure.yaml

Error creating: pods "unit5-quota-…" is forbidden: exceeded quota … requested: requests.cpu=600m, used: requests.cpu=…, limited: requests.cpu=500m.

6

Deploy the CPU demo and its HPA. The demo pod requests 50m, so the 60% target = 30m per pod. The HPA has min 1 and max 2 replicas.

kubectl top pods                                  # metrics must work first
kubectl apply -f deployment-cpu-demo.yaml         # Deployment + Service unit5-cpu
kubectl rollout status deployment/unit5-cpu --timeout=120s
kubectl apply -f hpa-cpu-demo.yaml
kubectl get hpa unit5-cpu

TARGETS cpu: 2%/60%, REPLICAS 1. <unknown>/60% for the first minute is normal.

7

Send load and watch it scale. pod-load.yaml is a client pod that hammers the Service for three minutes.

kubectl apply -f pod-load.yaml
kubectl get hpa unit5-cpu --watch       # Ctrl-C after REPLICAS reaches 2
kubectl top pods -l app=unit5-cpu
kubectl describe hpa unit5-cpu          # Events: SuccessfulRescale
kubectl get pods -l app=unit5-cpu

target climbing past 60% (Bakhtiyar's reached 128%), a pod at ~129m CPU, then REPLICAS 2 and SuccessfulRescale … New size: 2; reason: cpu resource utilization (percentage of request) above target.

8

Stop the load and watch it scale back.

kubectl logs pod-load                  # how many requests it sent (Bakhtiyar's: 690)
kubectl delete -f pod-load.yaml
kubectl get hpa unit5-cpu --watch      # back near 2%, then REPLICAS 1

back to one unit5-cpu pod after a few minutes. Scaling down is slower than scaling up on purpose.

Self-test

Check yourself

1. In your student namespace you add a container with limits: cpu: 2 and no requests. What happens, and what would happen with requests: cpu: 100m and no limits?

Show answer

The first is rejected (403 Forbidden). The second is admitted with a 100m request and the default 250m limit. The LimitRange's max is 1 CPU per container, and the max is not a default. A value you write is kept; a missing one is filled in from the LimitRange.

If this one was shaky, reread "LimitRange: defaults and a maximum."

2. You apply a Deployment. kubectl get pods shows nothing for it, not even Pending. Where do you look, and will Karpenter adding a node help?

Show answer

In kubectl describe rs, and no, a node won't help. No pod at all means creation was refused. The ReplicaSet's event says FailedCreate … exceeded quota. The quota caps the namespace, so a new machine changes nothing. Lower the requests, delete something, or get the quota raised.

If this one was shaky, reread "ResourceQuota" and the "Read the event" table.

3. A pod requests 50m CPU and uses 40m. The HPA target is 60%. Does it scale out? And if you change the request to 100m, with the same use?

Show answer

50m: yes (80% > 60%). 100m: no (40% < 60%). The HPA divides use by the request, so changing the request changes the percentage even though the app does the same work. That's also why the HPA can't scale on CPU without a request.

If this one was shaky, reread "The HPA: more traffic, more pods."
