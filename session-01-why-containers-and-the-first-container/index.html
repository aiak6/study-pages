Monolith vs microservices: why this stage exists

MonolithMicroservicesServerless
ShapeOne codebase, one deploySmall services, one job eachJust your code
Changing one featureRedeploy everything, coordinated with every teamThat team deploys only its serviceUpload new code
CostSlow and risky as it growsMore pieces to run and connectYou don't control the servers
Your exampleThe investment appStash: onboarding, bank services, Money Coach, transfersLambda (Scale 18)

Eldiiar's estimate: roughly 90–95% of companies use microservices today, but you'll meet all three styles.

A new company with strong engineers usually starts with microservices. An old one migrates piece by piece, or leaves a stable monolith alone when the payoff isn't worth the cost.

Blue-green deployment: build the replacement next to the old system, move traffic over, then shut the old one down.

Microservices almost always run as containers. That's why this stage starts with the container.

The problem containers solve: "works on my machine"

Before containers, every machine had its own installed Python and libraries. The laptop has 3.12, the test server has 3.9, and the app fails in QA.

An image carries the app together with its Python and libraries. Any machine with Docker and a Linux kernel runs it the same way.

Process, kernel, PID 1

WordPlain meaning
ProcessA running program
KernelThe core of the OS. It runs processes and controls their access to the hardware.
DistributionA kernel plus one set of programs. Amazon Linux uses dnf and Debian uses apt, on the same kind of kernel.
PID 1The first process. On EC2 it's systemd. Inside a container, PID 1 is whatever command you started it with, like bash or sleep 300.
When PID 1 exits, the container stops. Try it in the lab below.

Lab: watch PID 1 decide when a container stops

Pick a command and flags, then run it. Use the buttons to exit bash, let time pass, stop or remove containers, and watch docker ps and docker ps -a change.

docker ps

docker ps -a

What to notice: with --rm, a stopped container vanishes from docker ps -a too. Without it, it stays as Exited until you docker rm it. And docker rm refuses a running container.

Image vs container (and vs AMI)

app code + libraries
↓ Dockerfile + docker build
IMAGE: a packaged filesystem + a start command. No kernel, nothing running.
↓ docker run
CONTAINER: one process, on the kernel the machine already has

One image can start many containers. A repository is where images are stored: Docker Hub is public; ECR is AWS's private one, and this unit uses it.

AMIImage
KernelYes, a full OSNone
StartsBoots a machine, in minutesStarts a process, in about a second
A container is not a small VM. A VM boots its own kernel; a container uses the host's. On a Mac, Docker Desktop runs one Linux VM, and every container uses its kernel.

Redo the demo yourself

Everything stays on your laptop, so this costs nothing. Tick each step as you finish it; your ticks stay in this browser.

Before you start

Docker Desktop installed and running.

0 of 6 steps done

1. Check that Docker is alive

Any answer, even an empty table, means the daemon is running.

docker ps
What you should see

Column headers like CONTAINER ID IMAGE .... If you get Cannot connect to the Docker daemon, start Docker Desktop.

2. Run a public image and go inside it

-it = interactive terminal, --rm = delete on exit, bash replaces the start command and becomes PID 1.

docker run -it --rm python:3.12-slim bash
What you should see

Unable to find image ... locally the first time, then a pull. Your prompt changes to something like root@3f2a9c1d7e4b:/#.

3. Look around inside

Note the kernel version down.

ls /                  # bin boot etc ... a normal Linux file tree
cat /etc/os-release   # Debian
uname -r              # kernel version
top                   # "command not found": the slim image leaves it out
What you should see

A normal Linux file tree, Debian, a kernel version, and top: command not found.

4. Open a second terminal on the laptop

Leave the container running; docker doesn't exist inside it.

docker ps                                  # your container: id, image, "bash", random name
docker top <container-id>                  # its processes: just bash
uname -r                                   # the Mac's kernel (Darwin), which is different
docker run --rm python:3.12-slim uname -r  # same kernel as step 3
What you should see

Both container readings match each other, and the Mac's reading doesn't match them.

5. Exit and check that it's gone

Type exit in the first terminal, then:

docker ps -a
What you should see

Not there: bash exited → container stopped → --rm deleted it.

6. Run a container in the background that stops itself

docker exec gets a shell inside, like SSH.

docker run -d python:3.12-slim sleep 300    # prints the id; your terminal stays free
docker exec -it <container-id> bash         # get a shell inside
exit
docker ps                                   # still running (sleep is PID 1)
What you should see

After 5 minutes, docker ps is empty and docker ps -a shows it as Exited.

If it goes wrong

ErrorMeaning
Cannot connect to the Docker daemonDocker Desktop isn't running
Docker Desktop stuck on "starting" (Apple chip)Install the Rosetta update, restart the Mac, try again
docker rm refusesThe container is still running. Run docker stop first.

Clean up

docker stop <container-id>; docker rm <container-id>   # any leftovers
docker rmi python:3.12-slim                            # optional: delete the ~145 MB image

What the instructor stressed, and what's next
