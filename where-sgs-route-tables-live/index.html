Where the SGs and route tables actually live

Three different layers decide whether a packet reaches your database, and they attach to different things. The route table hangs off the subnet and decides where packets can travel; the security group hangs off the resource and decides who's allowed to connect. Public vs private is a routing fact, not a security-group fact.

Subnet

what slice of the VPC am I in?

A range of the VPC's IPs, pinned to one AZ. It's just an address block — it holds no rules by itself.

attaches to → the VPC + one AZ

Route table

where can these packets travel?

The 0.0.0.0/0 → igw line is the only thing that makes a subnet public. No such line = private.

attaches to → a subnet

Security group

is this specific connection allowed?

Stateful firewall on the resource. db-sg trusts app-sg by name, so only your app can reach 5432.

attaches to → the instance / ENI
Two layers must both say yes. For your app to reach RDS: the routing has to allow the packet to travel (both are inside the VPC, so 10.0.0.0/16 → local covers it) and db-sg has to allow the connection (5432 ← app-sg). This is exactly the request path you traced end-to-end — and the same jump-box setup, where you SSH into the public EC2 first because RDS sits in the private subnet with no way in from outside.
