Inside the ALB: listener → rule → target group

In the big picture these are three small boxes. But they're really a chain: the listener catches the connection, its rules decide where it should go, and the target group is the pool it gets sent to. Here's what actually lives inside each one, following one request all the way down.

a request arrives GET https://investmentapp.example.com/portfolio  ·  TCP 443
▼hits the listener on its port

Rules

IF condition → THEN action

"Checked in priority order. The FIRST rule that matches wins — the rest are skipped."

PriorityIF (conditions)THEN (action)
1path-pattern = /api/*forward → api-tg
2host-header = investmentapp.example.comforward → app-tg
default(anything not matched above)forward → app-tg (or fixed-response 404)

Conditions you can match on:

host-headerpath-patternhttp-headerhttp-request-methodquery-stringsource-ip

Actions a rule can take:

forwardredirectfixed-responseauthenticate-oidc / cognito

Lower priority number = evaluated first. The default rule always exists and catches anything no rule matched — there's no such thing as an unhandled request.

▼matched rule forwards to a target group

Registered targets

the actual EC2s
aws_instance.app["a"]
public subnet · AZ a
● healthy — receiving
aws_instance.app["b"]
public subnet · AZ b
● failed check — draining

A failing target is removed from rotation until it passes again; when one is deliberately deregistered, the ALB waits out the deregistration delay (connection draining) so in-flight requests finish first.

This health-check block is what you measured in Assignment 05. Your ~59 s failure window ≈ unhealthy threshold (2) × interval (30 s) — how long until a dead target gets pulled out. Your ~143 s recovery ≈ healthy threshold (3) × interval (30 s) plus the time to boot and register the replacement. Change the numbers in this block and those windows move with them.
