Concepts

The main ideas, from zero

Why this matters: base64 is not a lock

kubectl get secret investment-app-secret -o jsonpath='{.data.DB_PASSWORD}' | base64 -d
# change-me-class-password
  • A Secret's value is only encoded, not encrypted. Anyone who can read it can decode it.
  • So the question becomes: who is allowed to read Secrets?
  • Tonight answers two of three questions: what may you do (and how to check), and what may Claude Code do. The third, where the password should live instead of Git, is Part 4.
The password is safe only if the cluster lets the right users read Secrets and nobody else.

The two checks: AWS says who you are, Kubernetes says what you may do

  • Kubernetes has no user accounts of its own. Each platform brings its sign-in. On EKS, that is your AWS sign-in (profile 312-cluster).
  • Think of AWS as the house and the cluster as a locked room inside it. Being in the house doesn't open the room.
kubectl get secrets (on your laptop) ↓ kubectl signs a token with your AWS credentials CHECK 1 · AWS: which IAM role signed this? ↓ looked up in the cluster's ACCESS ENTRIES table ↓ role Containers26a → user student:my-namespace ✗ no access entry → "Unauthorized" CHECK 2 · Kubernetes (RBAC): may this user LIST SECRETS in THIS namespace? ✗ no rule allows it → "Forbidden" ✓ a RoleBinding allows it → command runs
  • Access entry: a table in the cluster that maps an IAM role to a Kubernetes user.
  • The whole class shares one IAM role, Containers26a. Your sign-in name fills in the rest: student:<your sign-in name>, which is also your namespace.
  • Your sign-in name is at the end of the Arn that aws sts get-caller-identity prints.
  • No access entry = Unauthorized, even for an AWS administrator.
  • In the IAM console the role shows up as AWSReservedSSO_Containers26a_… because IAM Identity Center created it.
ErrorWhich check failedWhat it means
You must be logged in to the server (Unauthorized)AWSThe cluster doesn't know who you are
Error from server (Forbidden): … cannot list …KubernetesThe cluster knows you; no rule allows this
Unauthorized = "who are you?" failed. Forbidden = "you may not" failed.

whoami: the user the cluster made from your sign-in

kubectl auth whoami
# Username  student:my-namespace
# Groups    [students system:authenticated]
  • students is a group the whole class shares.
  • system:authenticated only means "you signed in."

RBAC: a Role says what, a RoleBinding says who

  • RBAC = role-based access control, the cluster's own permission rules.
  • Role: a list of what's allowed: which verbs (actions) on which resources (kinds of object).
  • RoleBinding: gives a Role to a user, in one namespace.
  • A Role on its own gives nothing to anyone. There is no deny: if no RoleBinding allows it, it's refused.
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: pod-reader
  namespace: my-namespace
rules:
- apiGroups: [""]               # "" = the core group: pods, ConfigMaps, Secrets, Services
  resources: ["pods"]           # ["*"] would mean every kind in the group
  verbs: ["get", "list", "watch"]
VerbMeansNeeded for
getRead one object by namekubectl get pod web-1
listRead all of themkubectl get pods
watchWait for changeskubectl get pods --watch

Trap: a Role with only get lets you read pod/web-1 by name and refuses kubectl get pods.

The one word that means different things in AWS and Kubernetes

AWS IAMKubernetes RBAC
A policy lists what's allowedA Role lists what's allowed
You attach the policy to an IAM roleA RoleBinding gives the Role to a user
Policy can say Allow or DenyRole can only allow
A Kubernetes Role is like an IAM policy, not like an IAM role.

And the IAM role Containers26a and the ClusterRole edit are two different things: the first gets you into the cluster (AWS check); the second lists what you may do there (Kubernetes check).

The four objects: Role, ClusterRole, RoleBinding, ClusterRoleBinding

  • ClusterRole: a list of rules written once for the whole cluster. The binding that uses it decides where it applies.
BindingPoints toApplies in
RoleBindingRoleOne namespace
RoleBindingClusterRoleOnly the RoleBinding's namespace (this is you)
ClusterRoleBindingClusterRoleEvery namespace
ClusterRoleBindingRoleNot allowed
  • In one namespace, a Role and a ClusterRole with the same rules give the same rights.
  • A ClusterRole exists so one rule list can be written once and reused in many namespaces, or all of them.
  • Built-in ClusterRoles in every cluster: view, edit, admin.
  • Your access: a RoleBinding student-edit in your namespace → ClusterRole edit. One edit serves all ~95 students, each only in their own namespace.
  • edit does not include reading Roles or RoleBindings, so you can't print your own binding.
  • Create the Role first. A RoleBinding naming a Role that doesn't exist gives nothing until the Role is created.
kind: RoleBinding
metadata:
  name: student-edit
  namespace: my-namespace   # applies only here
roleRef:                            # WHAT
  kind: ClusterRole
  name: edit
subjects:                           # WHO
- kind: User
  name: student:my-namespace
Role + RoleBinding = per namespace. ClusterRole + ClusterRoleBinding = whole cluster. ClusterRole + RoleBinding = the ClusterRole's rules, in one namespace only.

ServiceAccount: a user for a program

  • A program in a pod has no AWS sign-in. Kubernetes knows it by its ServiceAccount.
  • The pod YAML names it with serviceAccountName:. Kubernetes gives the pod a token, and its requests arrive as system:serviceaccount:<namespace>:<name>.
  • A pod that names none runs as default, which is what your investment-app does.
  • The default ServiceAccount has no rights of its own. Don't bind a Role to it: that would reach every pod in the namespace that names no ServiceAccount.
  • So each program that needs rights gets its own ServiceAccount and its own small Role.
person → arrives through AWS → student:<namespace> program → arrives as its ServiceAccount → system:serviceaccount:<ns>:<name> both → get rights the same way: a RoleBinding

Least privilege: report-bot and Claude Code

  • Least privilege: a user or program gets only the permissions its job needs.
  • report-bot only reads settings → it gets read access to ConfigMaps and nothing else.
  • Claude Code runs kubectl for you. With your sign-in it could read every Secret or delete anything, including by mistake. To debug it only needs to read.
  • So it gets its own sign-in: profile 312-cluster-readonly → IAM role Containers26aReadOnly → user readonly:<namespace> → built-in view in your namespace.
In your namespaceYou (edit)Claude Code (view)
Read pods, logs, events, ConfigMapsyesyes
Read Secretsyesno
Run commands in a pod (exec)yesno
Read Roles and RoleBindingsnono
Create, change, deleteyesno
Claude Code finds the problem. You apply the fix yourself, in your own terminal, with your own profile.

Hands-on

Redo the demo yourself

Before you start:

  • Signed in: aws sso login --profile 312-cluster, and kubectl pointed at your namespace my-namespace.
  • Night 1's objects in your namespace. In 04-config-secrets-identity/:
kubectl apply -f configmap-investment-app.yaml -f secret-investment-app.yaml \
  -f postgres.yaml -f deployment-investment-app.yaml
  • Claude Code installed (for step 7). Nothing here creates AWS resources, so it costs nothing.
  • You can't redo report-bot: students can't create Roles or use --as. Read that part in the Commands section.
1

See the user the cluster made from your sign-in. This is the result of the AWS check.

aws sts get-caller-identity --profile 312-cluster   # your sign-in name is at the end of the Arn
kubectl auth whoami

Username student:my-namespace and Groups [students system:authenticated].

2

Ask the Kubernetes check what you may do. can-i changes nothing; it only answers yes or no.

kubectl auth can-i get secrets            # in your namespace
kubectl auth can-i delete pods
kubectl auth can-i list roles             # edit doesn't include Roles
kubectl auth can-i get secrets -n <classmate-namespace>

yes, yes, no, no.

3

Get a real Forbidden and read it.

kubectl get secrets -n <classmate-namespace>

Error from server (Forbidden): secrets is forbidden: User "student:my-namespace" cannot list resource "secrets" in API group "" in the namespace "<classmate>". Who = your user. What = list secrets ("" = core group). Where = their namespace.

4

Check which ServiceAccount your app runs as.

kubectl describe pod -l app=investment-app | grep 'Service Account'
kubectl get serviceaccounts               # at least "default"

Service Account: default, because the deployment YAML names none.

5

Add the read-only profile for Claude Code. Open ~/.aws/config and add a block at the bottom. Don't remove anything already there. The setup page has the exact block; it looks roughly like this:

[profile 312-cluster-readonly]
sso_session = 312                 # same SSO session your 312-cluster profile uses
sso_account_id = <same account id as 312-cluster>
sso_role_name = Containers26aReadOnly
region = us-east-1                # where the cluster runs (Identity Center itself is in us-east-2)
aws sso login --profile 312-cluster-readonly    # browser opens; confirm the code

a "successfully logged in" message in the terminal.

6

Write a separate kubeconfig so your own ~/.kube/config stays unchanged.

aws eks update-kubeconfig --name containers-26a --region us-east-1 \
  --profile 312-cluster-readonly --kubeconfig ~/.kube/readonly
KUBECONFIG=~/.kube/readonly kubectl config set-context --current --namespace=my-namespace
KUBECONFIG=~/.kube/readonly kubectl auth whoami
KUBECONFIG=~/.kube/readonly kubectl auth can-i get secrets
KUBECONFIG=~/.kube/readonly kubectl get pods

a new file ~/.kube/readonly; whoami prints readonly:my-namespace; can-i prints no; get pods lists your pods.

7

Start Claude Code with the read-only sign-in and test it.

KUBECONFIG=~/.kube/readonly AWS_PROFILE=312-cluster-readonly claude

Then ask it, one at a time:

  • "Create a pod called test in my namespace" → should fail.
  • "List all pods in my namespace" → works.
  • "What's running in my namespace, and is any pod not ready? Why?" (the homework question)
  • "Which Role does the default ServiceAccount use?" → it can list ServiceAccounts but not Roles, and should say so.

pods is forbidden: User "readonly:my-namespace" cannot create resource "pods" for the first ask, and a normal pod list for the second.

If it goes wrong

ErrorMeaning
UnauthorizedAWS check failed. SSO session expired, or the wrong profile. Run aws sso login --profile … again.
Forbidden … User "student:…"Kubernetes check failed. You're asking about another namespace, or something edit doesn't cover (Roles, RoleBindings).
Forbidden … User "readonly:…" on a writeWorking as intended. Run the fix yourself with your normal profile.
Read-only commands show the wrong namespaceThe new kubeconfig has no default namespace. Run the set-context --namespace line, or add -n my-namespace.

Clean up

  • No cloud resources were created, so nothing costs money. Keep the read-only profile and ~/.kube/readonly; you'll reuse them.

report-bot: the instructor's demo (read along)

apiVersion: v1
kind: ServiceAccount
metadata:
  name: report-bot
---
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: configmap-reader
rules:
- apiGroups: [""]
  resources: ["configmaps"]
  verbs: ["get", "list", "watch"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: report-bot-reads-configmaps
roleRef:
  apiGroup: rbac.authorization.k8s.io
  kind: Role
  name: configmap-reader
subjects:
- kind: ServiceAccount
  name: report-bot
BOT=system:serviceaccount:instructor:report-bot
kubectl apply -f serviceaccount-report-bot.yaml -f role-configmap-reader.yaml
kubectl auth can-i get configmaps --as $BOT      # no: a Role alone gives nothing
kubectl apply -f rolebinding-report-bot.yaml
kubectl auth can-i get configmaps --as $BOT      # yes
kubectl auth can-i get secrets --as $BOT         # no
kubectl auth can-i delete configmaps --as $BOT   # no

Mo first applied the RoleBinding without -n instructor and had to re-run it: a RoleBinding is namespaced, so it lands wherever you apply it.

You don't need to memorize the YAML. The Kubernetes docs page "Using RBAC Authorization" has an example of each object.

Emphasis

What the instructor stressed

  • Remember the two checks. "Focus on this, this is important": the cluster lives inside AWS, so you pass AWS first, then Kubernetes.
  • Being in the AWS account doesn't mean you can reach the cluster. Different teams get different clusters.
  • An IAM role and a Kubernetes Role are different things. He spent the most time here.
  • Least privilege, always. Don't give Claude your own rights: AI can misread "delete this pod" as "delete the deployment", and in production that costs real money.
  • Don't use defaults (the default namespace, the default ServiceAccount) for your apps.
  • Re-watch if it's still confusing. "Not hard, but the first time it's a lot."
  • His own view on interviews: say you use Copilot lightly, not that AI does your job. Wait for the school's official advice at the end of the program.

Self-test

Check yourself

1. A new teammate is an AWS administrator in the account, but every kubectl command prints Unauthorized. Giving them the ClusterRole admin doesn't help. Why not, and what's missing?

Show answer

They're failing the AWS check, before RBAC ever runs. Their IAM role has no access entry in the cluster, so the cluster doesn't know who they are. RBAC rules only matter once you get past check 1.

If this one was shaky, reread "The two checks."

2. You create a RoleBinding in namespace team-a that points to a ClusterRole allowing list secrets. Can that user list Secrets in team-b?

Show answer

No. A RoleBinding limits a ClusterRole's rules to the RoleBinding's own namespace. Cluster-wide would need a ClusterRoleBinding. This is exactly why you can't see classmates' Secrets.

If this one was shaky, reread "The four objects."

3. A teammate wants a new log-shipping pod to read ConfigMaps, so they bind a ConfigMap-reader Role to the default ServiceAccount. What's wrong with that?

Show answer

Every pod in the namespace that names no ServiceAccount now gets that right too. Create a dedicated ServiceAccount, bind the small Role to it, and set serviceAccountName: in the pod. That's least privilege.

If this one was shaky, reread "ServiceAccount: a user for a program."
