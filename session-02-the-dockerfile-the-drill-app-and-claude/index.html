The Dockerfile: your boot script, rewritten as instructions

Problem: on EC2, a boot script installed Python, copied the app and started it on every new machine. That's slow, and it runs again every time.

What it is: a plain text file named Dockerfile. Each line is an INSTRUCTION (uppercase) followed by its arguments. docker build reads it top to bottom, and the result is an image.

InstructionWhat it doesRuns when
FROM python:3.12-slimThe base image to start from (Docker Hub by default)build
WORKDIR /appThe folder that later instructions and the app run inbuild
COPY requirements.txt .Copies a file from your folder into the image (. = the WORKDIR)build
RUN pip install -r requirements.txtRuns a command and keeps its result in the imagebuild
CMD ["gunicorn", ...]The start command, which becomes PID 1docker run
ENV KEY=valueSets an environment variable inside every containersetting only
EXPOSE 8080Documentation only. It opens nothing.setting only
USER investment-appRuns the start command as this user instead of rootsetting only

ADD is a more powerful COPY; you can skip it. ENTRYPOINT was skipped on purpose, because Kubernetes replaces it anyway (unit 2, command/args).

Base images and tags: which FROM to pick

Image name : tag. In python:3.12-slim, python is the image and 3.12-slim is the tag. There are many tags so each carries only what one use case needs. Like a Terraform module, someone already built it, so you reuse it.

Base imageSize (deck, arm64)Trade-off
python:3.121.12 GBLots of tools, easy to debug, slow to pull
python:3.12-slim145 MBUsed in this course. No extras, which is why top was missing.
python:3.12-alpine53 MBSmallest, but some Python packages have to compile on it, which is slow and sometimes fails
Smaller image = faster start, fewer tools when it breaks. The app decides.

Containers are immutable: what you change inside doesn't survive

docker exec hello touch /app/created-here → the file exists in THIS container
↓
docker rm -f hello → the container is gone, with its file
↓
docker run ... hello → a fresh container from the same image: no file

On EC2, files went to the disk (EBS) and stayed. A container gets a fresh file system from the image every time. Kept data (databases) needs volumes, which unit 6 covers.

To change what's in a container, change the Dockerfile and build again.

Layers and the cache: why the order of lines matters

IdeaPlain meaning
LayerThe saved result of one instruction that changes files. An image is its layers stacked in order, like an onion.
No layerCMD and ENV add no layer. They change settings, not files.
Never changedIf you copy a secret in and delete it in a later line, it's still in the image (deck slide 22).
CacheA second build reuses saved layers from the top until the first line whose input changed. Every layer after that line is rebuilt.

Logs go to the terminal, and the three places a port shows up

EC2:        gunicorn → trades.log file → CloudWatch agent ships it → CloudWatch
container:  gunicorn → stdout / stderr → Docker keeps them → docker logs <name>

stdout is the program's normal text; stderr is its error text. The CloudWatch agent and log file are dropped, and the app's one logging line loses its filename=. At work, agents in the cluster (Eldiiar's company uses Datadog on EKS) collect container logs.

What it saysWhereWhat it does
--bind 0.0.0.0:8080CMD (gunicorn)The app listens on 8080 inside the container. This is what makes it work.
EXPOSE 8080DockerfileA note for people reading it. Opens nothing.
-p 127.0.0.1:8000:8080docker runLaptop port 8000 reaches container port 8080, from your laptop only

Ports 0–65535 exist. Linux reserves below 1024 for root (22 SSH, 53 DNS, 80, 443), so containers use a high port; the course uses 8080. An app bound to 127.0.0.1 inside the container can't be reached by -p. Bind 0.0.0.0.

Build context and .dockerignore

Build context: the files docker build . lets the builder see (. = this folder). A file reaches the image only if a COPY copies it. COPY . . copies everything, including .git/, .terraform/ and env files with secrets.

.dockerignore works like .gitignore. You create it by hand next to the Dockerfile:

*.env
.terraform/
.git/
A Scale repo root with .terraform/ sends 823 MB to the builder. With these three lines it sends under 1 MB.

The five review items for any Dockerfile Claude writes

#CheckWhy
1Base image with a version (3.12-slim, never latest)latest moves. A rebuild in 5 years should get the same Python.
2Non-root USER, created first with RUN useraddUSER alone doesn't create the user
3Dependencies before sourceThe cache: a code change doesn't repeat pip install
4No secret in the imageA layer keeps it forever, and Dockerfiles get pushed to git
5CMD in exec formThe app is PID 1 and gets the stop signal

Also pick official images with lots of downloads. Anyone can push an image called "python-chatgpt" with malware in it.

The investment app's Dockerfile (worked copy in 01-the-container/example/investment-app/)

FROM python:3.12-slim                # step 1 · base image with a version
ENV PYTHONUNBUFFERED=1               # Python writes output at once
WORKDIR /app                         # step 4 · the directory
RUN useradd --system investment-app  # step 4 · user, created before USER
COPY requirements.txt .              # step 5 · dependencies before source
RUN pip install -r requirements.txt  # step 5
COPY app.py .                        # step 6
USER investment-app                  # non-root for the start command
EXPOSE 8080                          # a note, opens nothing
CMD ["gunicorn", "--workers", "2", "--bind", "0.0.0.0:8080", "app:app"]  # step 8 · exec form

The prompt from the deck, typed into Claude in apps/investment-app/:

Write a Dockerfile for the Flask app in this folder. Gunicorn serves it on port 8080 with two workers. Configuration comes from an environment file when the container starts, not from the image.

--workers 2 means Gunicorn starts two child processes to answer requests. In this course, "worker" will also mean a machine in the cluster.

Where the notes correct what was said live

Left: what was said in class. Right: the correct version from the site notes and deck.

Said in classCorrect version (site notes and deck)
"Binding port 80 of my laptop to 8080" / "gunicorn listens on port 80"Laptop 8000 → container 8080. Gunicorn listens on 8080.
"Shell form takes about 10 seconds to reach the main process"The signal never reaches gunicorn. sh doesn't pass it on, so Docker waits 10 s and then kills the container (exit 137).
"The build only fetches metadata, it doesn't pull the base image"The base image's layers are downloaded. The build keeps them in its own cache, which is why python:3.12-slim didn't show up in docker images.
PYTHONUNBUFFERED=1: "no idea what it is"When Python isn't attached to a terminal, it holds print() output in a buffer. This makes it write right away, so docker logs shows output immediately.

Redo the demo yourself

Everything runs on your laptop and costs nothing. Tick each step as you finish it; your ticks stay in this browser.

Before you start

Docker Desktop running, and your clone of 312school/containers up to date (git pull origin main on your branch).

0 of 10 steps done

1. Check that Docker is up

An empty table means the daemon is running.

docker ps
What you should see

Column headers. If you get Cannot connect to the Docker daemon, open Docker Desktop.

2. Read the six lines

Map each one to a boot script step before you build.

cd ~/DevOps/containers/01-the-container/example/drill
cat Dockerfile requirements.txt
What you should see

FROM, WORKDIR, COPY, RUN, COPY, CMD, then flask and gunicorn.

3. Build the image with a name and a tag

-t name:tag; . = this folder is the build context.

docker build -t hello:v1 .
docker images                 # hello  v1  ...  ~160 MB
What you should see

[1/5] FROM … [5/5] COPY app.py. There's no CMD step, because CMD runs at docker run.

4. Run it in the background and call it

docker run -d -p 127.0.0.1:8000:8080 --name hello hello:v1
curl --retry 5 --retry-all-errors --retry-delay 1 localhost:8000
What you should see

hello from the drill app. It also works in the browser at 127.0.0.1:8000.

5. Stop it and start it again

Notice how fast this is compared with EC2.

docker stop hello
docker ps          # empty
docker ps -a       # hello is there, Exited: stopped, not deleted
docker start hello # back in about a second
What you should see

hello listed as Exited, then running again in about a second.

6. See the file disappear

-f stops it first.

docker exec hello touch /app/created-here
docker exec hello ls /app        # created-here is there
docker rm -f hello
docker run -d -p 127.0.0.1:8000:8080 --name hello hello:v1
docker exec hello ls /app        # gone
What you should see

Only app.py and requirements.txt the second time.

7. Read the logs, and check PID 1

docker logs hello                     # gunicorn's startup lines
docker exec hello cat /proc/1/cmdline # gunicorn = exec form worked
What you should see

Listening at: http://0.0.0.0:8080.

8. Watch the cache

Change the text in app.py (for example "hello v2"), then rebuild.

docker build -t hello:v2 .
What you should see

CACHED on steps 1–4, and only [5/5] COPY app.py rebuilt. Undo your edit afterwards with git checkout app.py.

If it goes wrong

ErrorMeaning
Unable to find image 'hello:latest'You left out the tag, so Docker assumed latest. Use hello:v1.
port is already allocatedAnother container already uses laptop port 8000. Use 8001 or 8002, or remove the old container.
The container name "/hello" is already in useA stopped hello still exists. Run docker rm -f hello first.
rmi: image is being used by stopped containerRemove the containers first, then the image
docker build asks for credentialsOld Docker Hub login in the keychain. Eldiiar hit this and fixed it with AI. Try docker logout.

Clean up

docker rm -f hello app db      # remove the containers
docker network rm app-net
docker rmi hello:v1 hello:v2   # optional: images cost disk, not money

What the instructor stressed, and what's next

Stressed in class

  • Always exec form for CMD. If you see shell form, tell the author to switch.
  • Always pin a version tag. latest moves, and a new Python can break your app.
  • Never put a secret in a Dockerfile or image. He called it a golden rule.
  • Use official images with a large download count. Public registries can carry malware.
  • You won't write Dockerfiles by hand. Claude writes them; you check them against the five items. His Sonnet run left out USER, so review every time.
  • Don't let AI run commands on its own. At his company, he approves each command, because AI agents have connected to accounts and databases on their own.
  • The app decides the tools. Pick the base image and setup from what the app needs.
