Why a pod's IP is not enough

Every pod gets its own IP when it's created. Pods are ephemeral: deleted, replaced, rescheduled at any time. The Deployment brings the count back, but the new pod has a new IP, so a caller holding the old IP gets no answer. With 2+ replicas, the caller would also have to pick which pod to call. Same problem as Foundation: every new EC2 instance meant a new IP.

Scale:        user → ALB (one DNS name)   → target group → EC2s  (ASG swaps them)
Kubernetes:   pod  → Service (one name)   → endpoints    → pods  (Deployment swaps them)
Never hard-code a pod IP. Call the Service by name.

The Service: a fixed name and address in front of changing pods

What it is: an object with a fixed name (drill) and a fixed address (172.20.x.x). A request to it reaches one of the pods its selector picks.

What it is not: a program or a pod. It isn't placed on a node, so kubectl get pods doesn't list it. It's stored in your namespace, like a Deployment.

Selector = a label. The Deployment stamps app: drill on every pod. The Service's selector: app: drill picks them all, including a pod started a second ago. The client pod has app: client, so this Service never picks it.

You wroteWhat happens
selector: app: drillBoth drill pods picked
selector: app: dril (one letter missing)Selects nothing. No error, no warning. The Service just never answers.
apiVersion: v1            # Deployments use apps/v1; Services use v1
kind: Service
metadata:
  name: drill             # the name callers use
spec:
  type: ClusterIP         # the default; can be left out
  selector:
    app: drill            # must equal the pods' label exactly
  ports:
    - port: 80            # what callers dial
      targetPort: 8080    # where gunicorn listens

Lab: break and fix a Service

Start by curling a pod by IP, delete that pod, and curl again. Then apply the Service, try a wrong selector or targetPort, and see exactly which error each mistake gives.

Endpoints: the list of pod addresses, kept for you

Endpoints = the IPs of the pods the selector found, plus the port to send to. Stored as an EndpointSlice (the older Endpoints object still works with a warning). A controller in the control plane updates it on its own every time a matching pod starts or stops. Delete a pod: one IP in the list changes. The Service's name and ClusterIP stay the same.

Service answers nothing? Read the EndpointSlice first. Empty means no pod matches the selector.

ClusterIP: a rule on every node, not a machine

One word, two meanings: the default Service type, and the address every Service gets (the CLUSTER-IP column). No machine has that address, and it isn't an AWS object. kube-proxy, a program on every node, writes a rule there that rewrites 172.20.x.x:80 to one pod, like 10.20.2.7:8080, picked at random. Requests spread across the pods. A pod that isn't ready is marked in the EndpointSlice and gets no requests.

Works only inside the cluster. From your Mac, curl http://drill → Could not resolve host. Like SSHing to an EC2 private IP from outside the VPC.

client pod ── curl drill:80 ──▶ rule on client's node rewrites to ──▶ drill pod 10.20.x.x:8080

The port numbers, and the one that must match

Where it's writtenNumberWhat it does
port in the Service80What callers dial. http://drill = http://drill:80
targetPort in the Service8080Where the rule sends. Must equal where the app listens
--bind 0.0.0.0:8080 in the Dockerfile CMD8080Where gunicorn actually listens
containerPort in the Deployment8080Documentation only. Changing it changes nothing
EXPOSE 8080 in the Dockerfile8080Documentation only

Eldiiar's picture: doors between rooms. App code opens 8080 → Dockerfile → container → pod → Service. Wrong targetPort: accepted with no error, endpoints still listed, and every call fails with Connection refused, because nothing listens on that port.

targetPort = the port the process listens on. Everything else is either the caller's port or a note.

The name: cluster DNS turns drill into the ClusterIP

Every Service gets <service>.<namespace>.svc.cluster.local. Same namespace: drill is enough. Another namespace: drill.<namespace>. A Service deleted and created again gets a new ClusterIP; the name stays, which is why callers use the name.

Inside a pod, /etc/resolv.conf has a search line (adds your namespace to short names) and nameserver 172.20.0.10. That nameserver is CoreDNS, the cluster's DNS. It answers cluster names only; public names are Route 53. ;; Got recursion not available in nslookup output is a notice. Ignore it.

Each type keeps what the one before has: a LoadBalancer Service also has a node port and a ClusterIP. NodePort: Kubernetes picks the port unless you set nodePort: in the range. Not usable here: nodes are in private subnets and your namespace allows 0 node ports.

NodePort (shown, not usable here): same file with these changes

  type: NodePort
  ports:
    - port: 80
      targetPort: 8080
      nodePort: 30080     # optional; must be 30000–32767

LoadBalancer: AWS builds the NLB for you

StepWhat happens
Apply the manifestAWS creates an NLB with a listener on port 80 and a target group
Target groupHolds the pod IPs, kept equal to the endpoints. The NLB sends each connection straight to a pod.
Health checkA pod gets traffic once it passes. The NLB takes a few minutes to become active.
kubectl get svc drill-publicShows the NLB's DNS name under EXTERNAL-IP
AnnotationA setting in metadata that changes how an object is handled. aws-load-balancer-scheme: internet-facing makes it public; without it the NLB is internal only.
http:// onlyHTTPS needs a certificate, which comes with the Ingress
A nice nameA Route 53 CNAME → the NLB's DNS name (same as Scale)
StudentsBilled by the hour, so students can't create one: exceeded quota
apiVersion: v1
kind: Service
metadata:
  name: drill-public
  annotations:            # without it: internal only
    service.beta.kubernetes.io/aws-load-balancer-scheme: internet-facing
spec:
  type: LoadBalancer
  selector:
    app: drill
  ports:
    - port: 80
      targetPort: 8080
user → drillapp.exchangeweb.net (CNAME) → NLB :80 → target group → drill pod :8080
LoadBalancer is the production way in. port-forward is the engineer's way in.

port-forward to the Service, two ways to create objects, and seeing the cluster

kubectl port-forward svc/drill 8000:80: laptop port first, then the Service port. kubectl reads the Service's targetPort, picks one pod, and tunnels to it through the API server; the ClusterIP rule isn't used. Only your laptop can use it (127.0.0.1). When that pod is replaced, port-forward prints lost connection to pod and stops, while curl drill from the client pod keeps working.

4. See the problem

Call a pod by IP, kill it, call again.

kubectl exec client -- curl -s http://<drill-pod-ip>:8080
kubectl delete pod <that-drill-pod>
kubectl exec client -- curl -s --max-time 5 http://<same-ip>:8080
kubectl get pods -o wide
What you should see

hello from the drill app first, then nothing after 5 seconds. The replacement has a new IP.

5. Add the Service and call it by name

kubectl apply -f service-drill.yaml
kubectl get svc drill
kubectl exec client -- curl -s http://drill
What you should see

TYPE ClusterIP, CLUSTER-IP 172.20.x.x, 80/TCP, and hello from the drill app every time.

6. Watch the endpoints update themselves

kubectl get endpointslices -l kubernetes.io/service-name=drill
kubectl delete pod <one-drill-pod>
kubectl get endpointslices -l kubernetes.io/service-name=drill
kubectl get svc drill
kubectl exec client -- curl -s http://drill
What you should see

One IP changed in the slice with no command from you, and the ClusterIP unchanged.

7. Prove ClusterIP is inside-only, and look at DNS

curl http://drill                               # from your Mac
kubectl exec client -- cat /etc/resolv.conf
kubectl exec client -- nslookup drill
What you should see

Could not resolve host on the Mac; a search line and nameserver 172.20.0.10; Name: drill.<ns>.svc.cluster.local with the same address as get svc.

8. Break it on purpose

Wrong targetPort, then wrong selector. The README's scenarios cover these too.

# edit service-drill.yaml: targetPort: 9090, then
kubectl apply -f service-drill.yaml
kubectl get endpointslices -l kubernetes.io/service-name=drill   # still lists pods (port 9090)
kubectl exec client -- curl -s http://drill                      # Connection refused
# put 8080 back; then try selector app: dril and apply again
kubectl get endpointslices -l kubernetes.io/service-name=drill   # no endpoints
# put app: drill back and apply
What you should see

No error from apply in either case. The only clues are the refusal and the empty slice.

9. Tunnel from your laptop

kubectl port-forward svc/drill 8000:80   # terminal 1
curl localhost:8000                      # terminal 2
What you should see

Forwarding from 127.0.0.1:8000 -> 8080, then hello from the drill app.

What the instructor stressed, and what's next

Stressed in class

  • Run the AWS analogy for everything new. Ask "what was this in AWS?" It reviews Scale at the same time.
  • Labels are everything. One missing letter and the Service silently serves nothing. Kubernetes won't guess what you meant.
  • Ports must line up, from the app code all the way to targetPort.
  • LoadBalancer is what's used in real life. Every EKS app is roughly NLB → Service → pods.
  • Don't dig into cluster DNS at work. On EKS it just works. If DNS breaks, restart the CoreDNS pods.
  • Use Freelens to see, kubectl to work. Exams and jobs both expect the CLI.
  • Read the official Kubernetes docs, or point Claude at them, to build vocabulary.
  • Always clean up your namespace after practice (Bakhtiyar).
