1 · Judgment

Making decisions in a real work environment

I can always find a reason for either option (e.g. preferred vs required affinity). How do I actually pick?

Show answer

Go in this order:

  1. Is anything specific needed here? Not "for the company" — for this application in this cluster. Did anyone state a requirement? Does the app have to run on particular nodes?
  2. If nothing specific → it's generally your call. Pick either one, based on best practice or your own reasoning.
More than half of real decisions end up at step 2.

Within one company, 10 applications may split — half one way, half the other.

So how do I defend the choice instead of letting AI pick blindly?

Show answer

The goal isn't a provably perfect answer, it's knowing why you chose it. Any reasonable option is fine.

The question to ask yourself: how would someone have decided this before AI existed?

Isn't "based on my experience" a good enough reason?

Show answer

Mostly no — experience gets old fast. If you decide today using judgment from 3–4 years ago, you're making a 3–4 year old decision.

The example the instructor gave: a few years ago, scaling a cluster meant Cluster Autoscaler. Today the answer is Karpenter. Same question, different answer.

Experience is only a fair basis if it's very recent (you did it a month ago), or if you actively stay current — e.g. you just came back from KubeCon.

Same process, just faster. Think of AI as your personal data scientist — someone who crawls all the data and answers questions. The decision stays yours.

2 · Working with AI

Staying in control of what AI writes

AI keeps making decisions I should have made. How do I catch that?

Show answer

The instructor sees the same pattern even with well-trained agents — no matter how carefully you set up the plan step, it still slips decisions in.

The fix: create your own interface files and force AI to write to them.

FileWhat it holds
plan.mdshort, human-readable plan
decisions.mda decision log — one entry per setup, with the reasoning

Writing it down doesn't stop AI deciding — but it's how you catch it. You read the file and spot the call it made.

What's the core principle?

Show answer
AI can write a lot of files. You decide which ones you read — and read those carefully.

So make those few files comfortable to read: tell it to keep them human-readable and well structured. That instruction is part of the prompt, every time.

3 · Career

Why "years of experience" is a weak signal

How does platform work get narrow?

Show answer

You can easily spend six months on one migration, or two years on Helm chart updates for product teams.

The cost: you lose touch with everything else — monitoring, cluster deployments, infrastructure. Your world shrinks to your routine.

Doesn't two years of Helm make someone good at Helm?

Show answer

Not necessarily. Many companies have standardized setups, so the work becomes changing a few values here and there. Nothing big, nothing challenging.

The instructor's point: someone with two years of daily Helm may still struggle with Helm interview questions.

Years of experience is a poor track record of useful, valuable experience.

People with 5, 10, even 15 years often lack basics outside their routine — because very few sit down and look at what they're doing structurally.

5 · Terraform

State file history & safe destroy

Does the state file keep history?

Show answer

No. The state file is only the current / latest snapshot of what Terraform made in the real infrastructure.

BackendWhat happens on each apply
Localoverwrites terraform.tfstate, saves the old one as terraform.tfstate.backup — only one version back
S3overwrites terraform.tfstate every time — Terraform keeps no backup

Then how do I roll back if I destroyed something by accident?

Show answer

With the S3 backend, the backup is AWS's job, not Terraform's — it's the S3 Versioning feature, and you have to turn it on.

With versioning, overwriting a file never deletes it. S3 saves the old one as a previous version and writes the change as a new file. You get the full history, as far back as you want:

terraform.tfstate   (current)
terraform.tfstate   2026-11-13
terraform.tfstate   2026-11-12
terraform.tfstate   2026-11-11  …

In the console: Show versions on the object. Each version has its date, size and details.

Note: it's not a daily backup — it saves per change, so several changes in a day means several versions.

What do I watch out for before destroy — or before an apply that replaces something?

Show answer

First question: do you even need to run terraform destroy? Consider commenting out the resources instead.

Then watch for two categories:

  1. Anything that holds data — it may be unrecoverable: databases (RDS), S3, EBS, EFS.
  2. Anything that forces other things to be recreated — VPC and subnets. You can't cleanly recreate a VPC; everything inside it has to be recreated too.

Is there any protection built in?

Show answer

Good news — the important things are not that easy to delete:

  • VPC: AWS won't let you delete it until everything inside is destroyed first.
  • S3 buckets: similar protections.
  • RDS: has deletion protection — one line in Terraform.
resource "aws_db_instance" "main" {
  # …
  deletion_protection = true
}

With it on, terraform destroy won't destroy it. You must explicitly set it to false, or turn it off in the console, first.

Watch out

This setting is specific to RDS — not every resource has one. EBS has no such protection.

A student destroyed EKS before Karpenter finished — what happened?

Show answer

Karpenter's deletion hadn't finished, EKS was destroyed anyway, and because there were no workers left, some AWS resources couldn't be removed — they had to be deleted by hand.

The fix they added: a dependency in the code so EKS waits until Karpenter is fully terminated before going.

The instructor's take: that kind of forced ordering is often a good thing — it prevents exactly this sort of accident.

In a real company, would I even be able to fix that by hand?

Show answer
EnvironmentTypical platform-engineer access
Dev / sandbox / non-productionfull admin — break it, fix it, that's what it's for
Productionlimited, specific access — often no permission to destroy

Broader production access is granted temporarily when needed: an initial deployment, a big change window, a day or a week.

And it's a reason not to touch production in your first days at a company.

6 · Scaling

Karpenter

What does Karpenter replace?

Show answer

AWS Auto Scaling of EC2s, for the cluster's worker nodes.

Scales based on
AWS Auto ScalingEC2 metrics — CPU usage goes up, add nodes; goes down, remove them
Karpenterwhat the pods need

Same job, different trigger.

What does Karpenter actually do?

Show answer
  • Pods need more room → launches new EC2 worker nodes.
  • Nodes underutilized → consolidates: moves pods onto fewer workers, then deletes the EC2s that are no longer needed.

How does Karpenter know what a pod needs?

Show answer

Through resource requests — a Kubernetes feature.

When you create an EC2 you pick a size (t3.medium, m5.large…). When you create a pod you pick nothing — so requests is the only way to say how much it needs. It's the minimum resources for that pod.

That's the number Karpenter does its math with: this pod needs 1 CPU — does that other node have 1 free CPU? Yes → move it. No → can't.

7 · Kubernetes

Context, namespaces and kube-proxy

What is a context in kubectl?

Show answer

A saved cluster + namespace combination, stored in ~/.kube/config.

The closest word is "profile" — exactly like AWS profiles.

AWS profiles select which account; contexts select which cluster you're connected to. (The instructor: it would have saved a lot of explaining if they'd just called it profile.)

You can have 10 or 15 of them. Only one is current, because you can only connect to one cluster at a time.

kubectl config get-contexts    # list them all, * marks the current one

If the context is already saved, why do I still have to run update-kubeconfig?

Show answer

Because with a saved context alone, kubectl get nodes fails — the credentials inside it are temporary.

That's an EKS security feature: access depends on your IAM role, and it's re-verified each time. So you re-run it per terminal session, and every day.

even if someone steals your kubeconfig, they still can't connect — they'd need your IAM role too. On a plain, non-cloud cluster, a stolen kubeconfig would get them in.

So what does aws eks update-kubeconfig do exactly?

Show answer

Two things at once:

  1. Authenticates you with EKS, via your IAM role.
  2. Sets the current context to that cluster.

So you don't need kubectl config set-context afterwards — it's already done for you.

What is a namespace — and is it network isolation?

Show answer

No, it's not network isolation. It's a virtual grouping of pods inside one cluster — like folders for files.

It's a core Kubernetes topic you can't skip. What it's actually used for:

  • group resource limits for a set of pods
  • group permissions — e.g. give someone access to one namespace only

What is kube-system?

Show answer

A system-created namespace, made when the cluster is created. Kubernetes puts its own system pods there — CoreDNS, API server and others — so they don't mix with yours.

kubectl get pods                 # your namespace
kubectl get pods -n kube-system  # the system pods

Karpenter was installed into kube-system in our cluster.

And kube-proxy?

Show answer

Another Kubernetes system component, running on every worker node — just like kubelet.

Its main job is to make the Service feature work (ClusterIP and the rest). Without kube-proxy, Services don't work properly.

Don't confuse them

Context, namespace, kube-system and kube-proxy are four unrelated things that only share part of a name. Don't try to connect them.

8 · Storage & networking

Storage types & networking limits

What are the three kinds of cloud storage?

Show answer
TypeAWSWhat it is
ObjectS3files in buckets, reached over HTTP/HTTPS
BlockEBSa disk attached to a server — one disk, one server
File systemEFSremote shared storage mounted as a folder, e.g. /var/shared-files/

What makes EFS different from EBS?

Show answer

EBS is a disk for one server. EFS is centralized, shared storage: one or many servers mount the same folder.

If one server adds a file, the others see it immediately. Use it when your servers — or your pods — need shared storage.

Challenge from the session

Show the challenge

Create an nginx Deployment with 3 replicas that all share the same folder at the nginx root, using EFS as the shared storage.

It's harder with pods than with EC2s — a bit of extra effort, but doable, and worth practising. It's not in the tickets, but you can build it into one of them.

Can I change a VPC's CIDR block later?

Show answer

No. There is no such thing as changing a VPC.

Subnets you can recreate. The VPC you cannot — and everything in a VPC lives with that VPC, so redoing it means recreating everything inside it.

Set it correctly the first time.

The good news: with all the Terraform code, recreating is possible — just big work. There's rarely a reason to change it. One case that forces it: a CIDR conflict in VPC peering — though Transit Gateway and other options can get around that now.

If I have 15 clusters, how do I keep track of which Terraform code is which?

Show answer

More clusters = more Terraform root folders. The child modules stay shared; the root modules multiply.

So before every terraform apply or terraform destroy, know two things:

  1. which folder you're in
  2. which AWS account you're in

That's your job as the platform engineer — you're the one running destroy. Documentation listing what lives where is strongly recommended.

Do I need to know how SSO / Identity Center works?

Show answer

Understand what SSO is — yes. How to configure it — no.

It's a one-time setup; in bigger companies it's often done by dedicated IT administrators, not platform engineers. For most engineers it's like Gmail: already configured for you. Nobody will ask you to set it up in an interview.
