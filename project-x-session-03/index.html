Work

Tickets & boards: why Slack isn't enough

  • Work comes from Slack or from your board. A board is a Kanban-style view: each column is a status (To Do → In Progress → Review → Done), each card is a ticket.
  • Common tools: Jira (Atlassian), Trello, Linear, Asana, monday.com, ClickUp. Views: board (columns, often per sprint) and backlog (a list of everything waiting).
  • A ticket has fields: title, description, assignee, labels/priority, comments, history, and sub-tasks (each can have its own owner).
  • Why not just Slack? You post "can someone look at this Kubernetes node problem?", ten more messages land after it, and it's buried. Nobody owns it, and you can't follow up properly. A ticket stays on the board, assigned to someone, with a history.
  • Same thing, four names: task, story, ticket, issue. In Jira it might officially be a story, but engineers still say "I got a ticket".
  • Finishing a ticket: our PR #1 deploy from Session 02 moved to Review with a comment ("Deployed to dev. Pending Jordan's validation. Close after."). Some teams also reassign it to the person who must validate (Jordan, QA), since they own the next step.
  • The class Slack and Jira pages are static front-end copies, read-only for students. Marcel pushes changes to Git and you refresh to see them.

Concept

Code is the blueprint: IaC & GitOps

  • Over the last 10–15 years, companies moved to creating real environments from code. If you want to know what a house looks like, read its blueprint. You often don't need access to the environment at all.
  • Infrastructure as Code (IaC): Terraform, CloudFormation, Pulumi, AWS CDK. Nadia's ECS is CloudFormation in the infra repo (Session 02).
  • GitOps: everything goes through Git. Every change is a commit, and the cluster follows the repo. More on this later (Argo CD).
  • Manual changes are avoided. Only an old-school company 10–15 years behind still clicks things together by hand.
  • Why this matters with AI: an agent can read the code first, without touching the real environment, and explain what's running.
Tools

Open an agent session, not a chat

  • Use the work AI, never your personal account at work.
  • Technical people use agentic harnesses: Claude Code, Codex, Cursor. Not claude.ai or chatgpt.com in a browser. Chat with connectors is fine for marketing or sales; we need more.
  • Why a harness? It uses everything on your machine: Bash, your AWS credentials, the browser, installing packages, running and testing commands, back and forth. That's heavy-duty work a chat can't do.
  • Cursor lets you pick models from different vendors. Claude Code runs only Claude models; Codex runs only GPT.
  • Which repo? Launch from the one that fits the ticket. Moving the app to EKS is about the house, not the tenant, so: the infra repo.
  • Model and effort: Marcel used Opus at high effort. He rarely sees a difference with extra/max.
Tools

Worktrees: parallel sessions without collisions

  • The problem: two Claude Code sessions launched from the same folder share the same files and branch.
    • Session A: "create a file called chips". Session B: "list 15 EC2 types in a file". Both files show up in git status.
    • B is asked to commit and open a PR. Will it commit only its own file, or both? This time it got it right, but with 10 or 50 changed files you get conflicts. And A was now sitting on B's branch.
  • The fix: a worktree. The session gets its own folder with its own branch copy:
ls -a                           # inside the repo
.claude/worktrees/
    dummy-chips-file/           # session A works here
    ec2-types-list/             # session B works here
cd .claude/worktrees/dummy-chips-file && git status   # its own branch, its own files
  • It's like two people working on two different machines. Turn on the worktree option when starting the session. If it reuses a folder, tell it "create the worktree properly" (it sometimes messes up).
  • Archiving the session removes the worktree, unless it holds commits that aren't saved anywhere else.
  • Q: do worktree sessions share context? No. They don't know about each other unless you tell one to go read the other's folder.
Concept

Context engineering for a real ticket

What to hand the agent (this is context engineering, Session 02):

  1. The ticket: text, link or ID (with a Jira connector it can look it up itself)
  2. The meeting transcript: Teams, Zoom, Google Meet or Granola. The most valuable source. Your team's judgment, preferences and company quirks never appear on the internet
  3. A prompt, if useful. A bare prompt is fine; prompts matter less than context
  4. Slack channels where it was discussed
  5. Read-only access to the live environment: it can check real usage, for example node resource use (self-managed nodes may beat serverless on cost) or high CloudWatch logs/metrics bills
  • People told Marcel: "I gave it the ticket and the meeting call, and it knew the rest."
  • Ask for an HTML artifact for anything complex. A visual page with diagrams is easier to understand than a wall of text. Say your level ("I know Kubernetes basics, not EKS").
  • Ask it to research the latest docs. Otherwise it builds from memory and gives you an old version or misses a newer feature.
  • Q: can I download skills for best practices? Skills capture your process, and we don't have one yet. Outside skills for platform work vary a lot (some overcomplicated, some too simple), so we'll build our own later.
Judgment

Arguing with AI: the shortcut bias

  • The agent's first answer: stay on ECS. One service, one task, no load. EKS adds a control plane fee and ongoing work (version upgrades, add-ons, the load balancer controller) and a second management tool. For today's workload, that's fair.
  • Then add the real future: launch in ~30 days, $3M marketing spend, organic growth after. It still leaned on the simple answer.
  • Why: models are trained for token efficiency. It's like telling a person "decide fast, as fast as possible, but make the best decision". Those conflict, so you get the easiest, fastest answer, almost never the best. It even skips checking: "probably not needed anymore, but I haven't checked."
  • AI is very knowledgeable but not that smart yet. The human stays the navigator. If you just follow it, it can lead you into wrong solutions.
  • Push back: "You're dismissing every reason for Kubernetes. What do I tell my coworkers? You may be biased." After pushback it came back with:
    • Kubernetes gets more valuable with every service and team you add; ECS doesn't (each new service = another CloudFormation block)
    • Shared tooling: a paved road on standard pieces (Argo CD, Argo Rollouts, External Secrets) instead of custom CloudFormation per app
    • Hiring: engineers you hire will expect Kubernetes
    • Cost at scale: Karpenter + spot + denser packing beats Fargate pricing once load is steady
    • The longer you wait, the more you move: every ECS-native service adds to the migration later
    • The honest case against: two people, one deadline, new ways to fail at launch
  • Q: won't it just agree to please me? Launch a fresh sub-agent without your pushback and ask for an independent review.
  • AI doesn't count its own progress. Ask: "Does agentic AI make Kubernetes easier to run? Does that change the choice?"
  • It's weak at new ideas and timelines too (it estimated two weeks for what an agent can build in hours).
  • Most teams end up on Kubernetes: runs on any cloud, rich ecosystem. Complexity is less of a problem for people who know it.
Have your own opinion. Don't hand coworkers "A or B, you choose". Say "I think we should do this" and argue for it.
Plan

The migration plan: build alongside, shift traffic

Today (CloudFormation): users → ALB → ECS Fargate task → RDS Postgres + ECR (image) · Secrets Manager (DB creds) · CloudWatch (logs & metrics) Next to it (Terraform): users → ALB ─┬─ 90% → ECS Fargate task ─┐ └─ 10% → EKS pods ─────────┴→ same RDS Postgres
  • Why Terraform for the new part: CloudFormation is AWS-only and turns into one 1,000–5,000-line YAML file. Terraform splits into files and modules (Scale Session 15), works on any cloud, and most enterprises use it. Others: Pulumi, AWS CDK. Don't get locked into one cloud.
  1. Build a new EKS cluster (control plane + worker nodes) with Terraform, next to ECS. Both keep running.
  2. Deploy the same image to EKS. Test it (yourself or with QA).
  3. Point it at the same RDS. Only the compute layer moves; the database stays.
  4. Shift traffic gradually: 1% → 10% → 50% → 100%. You can run 70/30 for a while.
  5. Decommission ECS once everything works.
  • Why users don't notice: same DNS name, same container image, same database. Only the load balancer and the place the container runs change. Done right, there's no downtime.
  • How to split traffic: Marcel showed Route 53 weighted routing (90% to the ECS load balancer, 10% to the EKS one). The infra repo's write-up chose a weighted second target group on the existing ALB for dev. Same idea, done at the load balancer instead of DNS.
  • Plan phases: decide & record (put it in AGENTS.md) → build EKS foundation → cut over. Prod is a separate project.
  • The VPC question (a real interview story): the VPC and RDS were made by CloudFormation. Options: (1) new VPC + new RDS from a snapshot, (2) new VPC only, (3) reuse the existing VPC and later move the VPC and RDS under Terraform (transfer ownership, don't recreate). Marcel picked 3: that's how you'd handle prod, where you can't just recreate the database.
  • Decision for dev: EKS goes into the existing CloudFormation VPC (10.40.0.0/16) and uses the existing RDS. Moving them under Terraform is a later ticket.
EKS

EKS in one picture (from the AI guide)

Kubernetes has two halves (Containers Session 04):

HalfWhat it isWho runs it on EKS
Control planeAPI server, scheduler, etcd (the brain)AWS. $0.10/hour ≈ $73/month
Data plane (worker nodes)Where the pods runYou, on EC2 (m5.large, m5.xlarge, …)
  • Fargate for EKS hands the nodes to AWS too. It costs more and isn't really simpler.
  • How to run the nodes (decision #2, from the latest docs): EKS Auto Mode, managed node groups, or Karpenter (a node autoscaler; Office Hours Oct 24). Study what Karpenter is before choosing.
  • Other open decisions in the guide: secrets, Argo CD, traffic API, observability, who can reach the API endpoint, Kubernetes version.
  • Upgrades are the most annoying part of running Kubernetes yourself, along with extra controllers.
  • Practice cheaply: if you want your own cluster, GKE (Google) has a free tier that covers the control plane fee; you pay only for VMs. If you use EKS, build it with Terraform and terraform destroy as soon as you're done. It's billed by the hour.
Correction

Marcel said upgrades come "every six months or something". Kubernetes ships ~3 minor versions a year, and EKS standard support lasts ~14 months per version, so plan on upgrading at least once a year.

Big picture

What AI speeds up, and what it doesn't

plan → design → BUILD → test → deploy → maintain ↑ agents nearly zero this learn ← mixed into every step for you
  • Before AI, build took the biggest chunk. A cluster AI says takes "two weeks" now gets built in 30 minutes to an hour once you know what you want.
  • What still takes time, and stays with humans: planning, designing, testing, verifying. That's why the "one engineer = 10 engineers" hype didn't come true.
  • For you, add a step: learn. It's no longer "learn, then plan". It's mixed in everywhere: plan & learn, build & learn, test & learn. You don't need to learn to write the plan; you need to learn to make the decisions.
  • This class was ~70–80% of how work gets done now: start a session, give context, have it explain and plan, question it, decide, then let it build, test and deploy.

Self-test

Quiz: score yourself out of 10

Answer each question out loud first, then open the answer.

1. You asked a teammate in Slack to look at a failing node. Two days later nothing has happened. What went wrong, and what should you have done?

Show answer

A Slack message has no owner and no status. A ticket has both. Your message got buried under newer ones, nobody was assigned, and there's no easy way to follow up. Create a ticket (or ask them to), assign it, and post the link in Slack. Now it sits on the board with a history until someone moves it to Done.

2. You get the ticket "Assess moving the app from ECS to EKS." What is your very first step, and why not start with the AWS console?

Show answer

Understand the current situation by opening an agent session in the infra repo. The code is the blueprint: CloudFormation/Terraform show what's running without you clicking through an account you may not even have access to yet. The console is one source, but the code, docs and people come first. You can't plan a future state without knowing the current one.

3. Two Claude Code sessions run from the same repo folder. One is asked to commit and open a PR. What can go wrong, and what fixes it?

Show answer

They share one working folder and one branch, so one session can commit the other's files or end up on its branch. With a couple of tiny files it may work out. With 10–50 changed files you get conflicts and messy PRs. Fix: run each session in a worktree (.claude/worktrees/<name>), its own folder with its own branch copy. Like two people on two machines.

4. Interview question: "What's the most useful context you can give an AI agent for a team decision, and why?"

Show answer

The meeting transcript where the team discussed it. AI already has general knowledge. What it lacks is your company: teammates' preferences, constraints, the reasons behind past choices. That only exists in human conversation. Add the ticket, relevant Slack threads, docs, and read-only access to the live environment, and it often knows the rest.

5. Your agent recommends "stay on ECS" in 20 seconds. Why should you be suspicious, and what do you do?

Show answer

Models are trained to be token-efficient, so the first answer is the fastest one, not the best one. It judged today's tiny workload and ignored the future (launch, $3M marketing, more services). Push back with the missing context, ask it to check the latest docs, and ask whether agentic AI changes the trade-off. It almost never thinks of its own progress.

6. You pushed back and the AI now agrees with you. How do you know it didn't just cave to please you?

Show answer

Launch a fresh sub-agent that never saw your pushback, give it the same facts, and ask for an independent review. If it reaches the same conclusion on its own, the reasoning holds. If not, compare the two arguments. Same idea as a second reviewer on a PR.

7. Give three strong reasons to move a growing startup from ECS Fargate to EKS, and one honest reason to wait.

Show answer

For: (1) Kubernetes gets more valuable with every new service and team; ECS just adds another CloudFormation block each time. (2) A shared paved road built on standard tools like Argo CD, Argo Rollouts and External Secrets. (3) Cost at scale: Karpenter with spot instances and denser packing beats Fargate pricing once load is steady. Bonus: hiring, portability across clouds, and "the longer you wait, the more you have to move".

Against right now: a two-person team with a launch deadline adds new ways to fail. Ongoing work like version upgrades and add-ons is real.

8. You move the app from ECS to EKS and switch traffic. Why don't users notice?

Show answer

Nothing they touch changes: same DNS name, same container image, same database. Behind the name, traffic now goes to a different load balancer and a container running in a different place. Because RDS stays put and only the compute layer moves, there's no data to copy and no downtime. Shift it gradually (1% → 10% → 100%) with weighted routing in Route 53 or a weighted second target group on the ALB, so you can roll back by changing the weights.

9. Interview question: "The VPC and RDS were built with CloudFormation, and you're building EKS with Terraform. What do you do with the VPC and database?"

Show answer

Reuse them: launch EKS into the existing VPC and point it at the existing RDS, then later transfer ownership of the VPC and RDS to Terraform (import) instead of recreating them. A new VPC plus a new RDS from a snapshot works for a throwaway dev account, but in prod you can't casually recreate a database or move its network. Changing who manages a resource, not the resource itself, is the safe pattern. It's also a good "challenge I faced" story.

10. Your manager says: "With AI, this migration should take a day, right?" How do you answer?

Show answer

The build part, maybe. The work around it, no. Agents nearly zero the build step: once decisions are made, Terraform for the cluster can be written in hours. But planning, design decisions (node setup, secrets, GitOps, traffic split), testing, verifying with QA, a gradual cutover, and the learning you need to make those calls still take human time. That's why AI didn't turn one engineer into ten. The cutover also waits on other people.
