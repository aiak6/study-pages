🔌 The ClusterIP Service: one stable address for changing Pods

The class opened with a question: can one Pod reach another Pod directly, with no Service?

  • Technically yes. Every Pod has its own IP, and a Pod could call the API server (kubectl get pods) to look them up.
  • But that is a bad deal: the app has to build that lookup into its own code; the Pod needs permission to list other Pods (a Role, a RoleBinding and a ServiceAccount — Containers Session 10); and Pod IPs change every time a Pod is replaced.

🔑 The selector is the only thing that decides where traffic goes. selector: app: investment-app must match the Pods' labels. Nothing else links them.

What the Service does for you, for free:

  • Keeps one virtual IP that doesn't change when Pods are replaced (it only changes if you delete and recreate the Service).
  • Keeps the endpoint list up to date as Pod IPs change.
  • Stops sending traffic to a Pod whose readiness probe fails.
  • Spreads requests across all matching, Ready Pods.

💡 A Service is virtual. A classmate asked where it "sits" — it doesn't sit anywhere. It is not a Pod, it uses no CPU or memory. It's a networking rule, and kube-proxy is what actually rewrites the traffic from the Service IP to a Pod IP.

apiVersion: v1
kind: Service
metadata:
  name: investment-app
spec:
  selector:
    app: investment-app      # must match the Pod labels
  ports:
    - port: 80               # what callers use
      targetPort: 8080       # the real port in the container
  type: ClusterIP            # internal only — this is NOT public access

Who actually needs this? Real examples from class: front-end Pods calling auth Pods to check who you are; the front end sending "buy 10 shares of Apple" to a separate trading service; add-on Pods reaching regular app Pods.

💡 Most applications in a real company are never public. They only ever talk to each other through ClusterIP Services — which is exactly why this is an interview must-know.

🧭 Cluster DNS, kube-proxy and why there are two port numbers

You could hard-code the Service's IP, but you use its DNS name instead.

FormExample
Fullinvestment-app.main-product-line.svc.cluster.local
Shortinvestment-app.main-product-line
Same namespacejust investment-app

The name is built as service name → namespace → the standard cluster domain. CoreDNS answers it; without it nothing resolves, which is why CoreDNS is a required EKS add-on (Session 07).

FieldWho it's forRule
portCallers of the ServicePick anything. 80 is just a nice habit
targetPortThe containerMust be the port the app really listens on (8080)
  • So curl http://investment-app:80/ hits the Service on 80, and the Service forwards to 8080 on a Pod. If you chose port: 1990, every caller must use 1990. Get targetPort wrong and nothing works.
  • Nodes don't matter here. A classmate asked — the Pods can be on the same node or on different nodes; the networking rule reaches them either way.
kubectl -n main-product-line apply -f service.yaml
kubectl -n main-product-line describe endpointslice   # should list the Ready Pod IPs

# run a throwaway client Pod with curl in it
kubectl -n main-product-line run testpod --rm -it --image=curlimages/curl -- sh
# inside the Pod:
curl http://investment-app/        # no port needed, because the Service is on 80

💡 port-forward is not the same thing. It's a tunnel from your laptop through the API server to one named Pod. It skips the Service entirely and only exists while the command runs.

⛵ Helm: what it's actually for

Helm has already been used in this course — it's how Karpenter got installed (Session 07). There are two completely different ways you'll meet it:

Use caseWho wrote the chartWhat you do
Tools — Karpenter, Grafana, logging, CI/CDThe software vendor ships a ready chartYou're a user: helm install, adjust values
Your company's appsYouYou're the author: write templates, maintain them, change values

🔑 The second row is where platform engineers spend most of their time. Nobody else is going to write your company's chart.

What problem does it solve? You want the same app in dev, staging and production, with different settings in each.

  • Without Helm you'd keep deployment-dev.yaml, deployment-staging.yaml, deployment-prod.yaml — and the same again for the Service, the ConfigMap, and everything else. It works. It just multiplies forever, and every change has to be made in three places without forgetting one.
  • With Helm you keep one template and three small values files: dev replicaCount: 2, staging 3, production 60.
  • Anything that's the same everywhere (resource requests and limits, for example) goes in the shared values.yaml instead of being repeated in all three.

💡 The comparison from class: it's Terraform modules all over again. One reusable child module, different variable values per environment. Helm just has no "root module" concept — whatever you run helm against is the root.

💡 This is how almost every company does it, from dating apps to the New York Times. Real values files can run 1,500 lines; the structure is identical, there's just more in it. Ours is about 15 lines.

🗂️ Chart structure: templates, values and the environment files

charts/investment-app/
  Chart.yaml          # name + version. That's it — the chart's metadata
  templates/          # MUST be exactly "templates" — no typo, no space
    deployment.yaml
    service.yaml
    configmap.yaml
  values.yaml         # defaults + shared values. ALWAYS loaded automatically

values-dev.yaml        # outside the chart: this environment's choices
values-staging.yaml
values-production.yaml

🔑 Two filename rules that silently break things:

  • The folder must be templates. People type template, or add a space, and then wonder why nothing renders.
  • The shared file must be values.yaml. Call it shared-values.yaml and Helm will never pick it up.

Why are the environment files outside the chart? Because the chart is the reusable part and the values are not. The chart can even live in its own repository; a single chart might serve 10 different apps, each with its own dev and production values.

How values combine: values.yaml is always applied, then your chosen file is layered on top. Dev gets the shared resource limits plus 2 replicas. Production gets the same limits plus 60 replicas.

# before
replicas: 2
name: investment-app

# after
replicas: {{ .Values.replicaCount }}
name: "{{ .Values.appName }}"      # quotes needed when it sits inside other text

💡 A classmate asked the obvious question: if the values files live outside the chart, how does Helm know which one to use? It doesn't guess — you name it explicitly with --values.

helm upgrade --install investment-app charts/investment-app \
  --values charts/investment-app/values-dev.yaml \
  --namespace main-product-line --create-namespace

Read the command left to right: investment-app is the release name · charts/investment-app is where the chart is · --values picks the environment file · --namespace picks the namespace.

🔑 The filename does not pick the cluster. values-dev.yaml only supplies values. The cluster comes from your kubectl context. To deploy to staging you log into the staging account, switch context, and change one word in the command. Check kubectl config current-context before you install.

What is a "release"? Another classmate asked. It's Helm's own name for one installation. Whatever you type after --install becomes .Release.Name, and the templates use it to name the real resources. Call the release demo and your Service is called demo.

💡 Preview without touching the cluster: helm template investment-app charts/investment-app -n main-product-line -f values-dev.yaml renders the final YAML so you can read it first.

⚠️ Helm does not adopt your existing plain Deployment, Service and ConfigMap. Copy their settings into the values file first, check the rendered output matches, then replace them. The Secret stays put — secrets don't belong in a chart.

🔁 Advanced Helm: range, if and what's worth learning

FeatureWhat it isUse it for
rangeA loop — Helm's for_eachSix repeated ConfigMap env entries collapse into one block
ifA conditionalMake a whole resource optional from a values flag
 
{{- if .Values.clusterIP.create }}
apiVersion: v1
kind: Service
# ...the whole Service lives inside the if
{{- end }}

# values.yaml
clusterIP:
  create: true       # false → the Service is simply never rendered

🔑 The one principle to remember: the chart holds the templates, and you change behaviour only by editing values files. Somebody has to maintain the chart, but the person using it never opens templates/.

  • Helm also tracks release history, so you can roll back to a previous revision.
  • Is Helm syntax still a skill? The instructor's blunt answer: not really, not any more. It used to be a genuine specialty because the syntax is awkward. Today AI writes it well, and the people he knows who work with charts daily all let AI make the changes.
  • 💡 So don't memorise syntax. Learn the structure and the logic: what's shared, what's an input, which file wins. Nobody will ask you to hand-write a chart in an interview.
  • A classmate asked how to understand a chart you've never seen at work: ask AI to read it back to you, or read the README and walk the templates yourself the hard way.

📈 HPA vs Karpenter: two autoscalers, two levels

A classmate asked: do we even need HPA if we have Karpenter? Yes — they scale different things.

HPA (HorizontalPodAutoscaler)Karpenter
ScalesPodsWorker nodes (EC2)
Triggered byLoad on the current Pods (e.g. CPU > 70%)Pods that can't be scheduled for lack of room
Without itNo new Pods, no matter how busyNew Pods stay Pending forever

🔑 You need both. HPA asks for more Pods; Karpenter provides somewhere to put them.

autoscaling:
  enabled: false          # true → HPA is created, and replicaCount is ignored
  minReplicas: 2
  maxReplicas: 10
  targetCPUUtilizationPercentage: 70

The template reads if not .Values.autoscaling.enabled → use replicaCount. When HPA is enabled the Deployment leaves replicas unset, because the HPA owns that number.

💡 autoscaling is just a name someone chose. Call it hpa if you like — it only has to match between the values file and the template. Karpenter and the HPA are both from Containers Session 12.

🌍 Going public: NodePort, LoadBalancer and the Classic LB surprise

Where we stood: the app ran on EKS, reachable only by port-forward. Meanwhile the ECS copy still served the real public hostname through its ALB. You cannot ask users to run a kubectl command.

NodePort is ruled out immediately. It opens the same port on every worker node — but on AWS those workers are autoscaling EC2 instances whose IPs change all day. There's no stable address to point anything at.

service:
  type: LoadBalancer      # was ClusterIP

# then just re-run the same command — that's the point of "upgrade --install"
helm upgrade --install investment-app charts/investment-app \
  --values charts/investment-app/values-dev.yaml -n main-product-line
kubectl -n main-product-line get service     # now shows an external address

💡 A LoadBalancer Service is two things in one — it still has a ClusterIP underneath, plus the external load balancer. You don't create a separate ClusterIP Service alongside it.

And then the surprise. AWS created a Classic Load Balancer — the oldest of the three types (Classic, Network, Application) and the one nobody should be using.

Why? The AWS Load Balancer Controller was never installed on this recreated cluster. It is in the platform repo's setup script, right next to Karpenter — the agent that rebuilt the cluster just never ran it. Without it, an old legacy in-tree controller handles the Service and produces a Classic LB.

Load balancerNeeds the AWS LB Controller?
ClassicNo — the legacy path still makes one (this is what happened)
Network (NLB)The instructor wasn't certain and said so out loud
Application (ALB)Yes, definitely

What the controller actually does: it watches your Kubernetes objects and calls AWS. When a Pod is replaced and its IP changes from 10.0.3.17 to 10.0.4.28, the controller updates the load balancer's targets. Browser traffic never passes through the controller — it only configures the load balancer.

💡 Note how not-knowing was handled: he said he couldn't find a definitive answer and that AI had given him a wrong one. Admitting the gap beats inventing an answer. The Classic LB did answer curl from his terminal but not his browser — left unresolved, because it was the wrong tool anyway.

🚪 Gateway API: the modern way in

🔑 ingress-nginx was retired in March 2026. Gateway API is now the official Kubernetes standard for routing traffic in. (Istio and others do a similar job.) It is three objects, and the split matters:

ObjectAnswersHow often
GatewayClassWhich program builds the load balancer? (e.g. the AWS controller → an ALB)Once per cluster
GatewayWhich ports does it listen on? (e.g. 443)Once per cluster, one per port
HTTPRouteWhich hostname goes to which app?Once per application
 
kind: GatewayClass
metadata:
  name: projectx-alb
spec:
  controllerName: gateway.k8s.aws/alb      # the AWS Load Balancer Controller

Where each file lives — a classmate asked directly: GatewayClass and Gateway are once-per-cluster, so they belong outside the app chart (in the platform repo). HTTPRoute is per application, so it goes inside the app's Helm chart.

The HTTPRoute points at a ClusterIP Service — not a LoadBalancer Service. You don't want a second load balancer.

⚠️ Prerequisites, in order: install the AWS Load Balancer Controller, then the Gateway API object type definitions, and only then apply these YAMLs. None of that happened in Class 9 — it's all Class 10.

💡 The instructor was candid that Gateway API is more complicated than ingress-nginx was. That's the trade for flexibility, and you set it up once.

💰 Why share one load balancer: 10 apps, 1 ALB

Picture the startup growing: investing, portfolio, research, market data, learning, accounts, reports, notifications, admin, billing. Ten applications, each needing to be reachable.

ApproachWhat you end up with
A LoadBalancer Service per app10 load balancers — ten bills, ten things to configure and monitor
One Gateway + an HTTPRoute per app1 load balancer, 10 HTTPRoutes, 10 ClusterIP Services
  • 🔑 Two reasons, and they're the interview answer: cost and simplicity at scale.
  • One ALB handles roughly 100 HTTP routes under default configuration, so one shared gateway covers a lot of growth.
  • Adding app number eleven is then just: a ClusterIP Service, plus an HTTPRoute where you change two lines — the hostname and the backend service. The GatewayClass and Gateway never change.
  • 💡 Separate load balancers still make sense when an app genuinely needs its own access rules, capacity or isolation. Sharing is the default, not a law.

🚦 One-way vs two-way door decisions

A classmate asked how much to build "just in case" — private subnets you might not need, a ServiceAccount nobody uses. The answer: prefer simple and minimal. Over-building adds complexity, and complexity hurts too.

DoorMeaningExamples
Two-wayYou can change it back later. Most decisions.Replica counts, resource limits, Service type, chart layout
One-wayVery hard to undo — you'd redo the whole thingVPC CIDR, a production database change
  • 🔑 Spend your thinking time on the one-way doors. Everything else: pick something reasonable and move.
  • 💡 Practical trick: ask your AI which decisions here are one-way. It'll usually flag the few that are final.
  • Related: the roles of a platform engineer now read infrastructure (Terraform/IaC) + application deployment + writing and maintaining Helm charts. That third one is new on your résumé as of this class.

Check yourself

Answer each question out loud first, then open the answer. Score yourself out of 10.

1. A teammate wants the front-end Pods to find the trading Pods by calling the Kubernetes API for their IPs. Why is a ClusterIP Service the better answer, and what two extra things would their approach force you to build?

Show answer

Because the Service does it outside the application, and their version drags the lookup into the app and into RBAC.

  • Their approach needs application code to call the API server and pick an IP — networking logic welded into a business app.
  • It also needs permissions: a ServiceAccount, a Role and a RoleBinding allowing that Pod to list Pods (Containers Session 10).
  • And it's fragile: Pod IPs change every replacement, so the app has to re-query constantly and handle Pods that are alive but not Ready.
  • A ClusterIP Service gives a stable virtual IP and DNS name, keeps the endpoint list current, drops not-Ready Pods, and spreads load — for free, with zero app changes.

💡 There is a legitimate case for the hard way: distributed systems where you must reach one specific Pod, e.g. because that Pod holds particular data. That's what StatefulSets and headless Services are for.

2. Your Service is port: 80, targetPort: 8080. A teammate "simplifies" it to port: 8080, targetPort: 8080 and ships it. What breaks, and what doesn't?

Show answer

Nothing inside Kubernetes breaks — but every existing caller does, because they're all still asking for port 80.

  • targetPort was correct before and is correct after: the container really listens on 8080. That half is fine.
  • port is the front door number other Pods dial. Anything doing curl http://investment-app/ (which implies port 80) now gets connection refused and must become http://investment-app:8080/.
  • 🔑 The rule: targetPort must match reality; port can be anything you like, but it's a contract with your callers. Changing it is a breaking API change.
  • The reverse mistake is worse and quieter: get targetPort wrong and the Service looks perfectly healthy while every request times out.

3. A Pod is Running, the Service exists, and kubectl get pods looks fine — but requests to the Service never reach that Pod. Give two different causes and how you'd tell them apart in one command.

Show answer

Either the labels don't match the selector, or the Pod isn't Ready — and describe endpointslice distinguishes them instantly.

  • Label mismatch: the Pod says app: investment-app-v2, the selector says app: investment-app. The Service has no idea the Pod exists — it never appears in the endpoints at all.
  • Readiness failure: labels match fine, but the readiness probe is failing, so Kubernetes deliberately removes it from the endpoint list. kubectl get pods shows 1/1 Running but 0/1 READY.
  • The command: kubectl -n <ns> describe endpointslice. Pod absent entirely → labels. Pod listed as not-ready → the probe.

💡 "Running" and "Ready" are different claims. Running = the container process started. Ready = the app says it can actually serve. Only Ready Pods get Service traffic (Session 08, Containers Session 08).

4. You run helm upgrade --install app charts/app --values values-dev.yaml. Your kubectl context happens to point at the production cluster. What happens?

Show answer

You deploy dev's settings straight into production — Helm never looks at the filename.

  • --values supplies numbers and names. That's all it does. The word "dev" in the filename carries no meaning to Helm.
  • The cluster comes entirely from your kubectl context. The namespace comes from -n.
  • Result: production gets dev's replica count (maybe 2 instead of 60), dev's image tag, and dev's database settings written into its ConfigMap. The app may come up pointing at the wrong database.
  • 🔑 The habit that prevents it: run kubectl config current-context before every install. That's the whole reason the demo checked the context first.

💡 Real teams harden this further — separate AWS accounts per environment (so the wrong credentials simply can't reach prod), plus CI doing the deploy instead of laptops.

5. Why must the folder be called exactly templates and the shared file exactly values.yaml? What happens if you name the shared file shared-values.yaml, and why doesn't that same rule apply to values-dev.yaml?

Show answer

Because those two names are how Helm finds things automatically — and values-dev.yaml isn't found automatically, it's named by you.

  • templates/ is the only folder Helm renders. Typo it as template or add a space and Helm renders nothing — no error about your typo, just an install that creates no resources.
  • values.yaml is loaded implicitly, every time. Rename it and it's simply ignored: your shared resource limits and defaults silently vanish.
  • values-dev.yaml is different because you pass it explicitly with --values. It could be called bananas.yaml and work identically — which is also why it can live outside the chart folder.
  • 🔑 Layering: values.yaml always applies, then your explicit file is merged on top and wins on conflicts.

💡 This class of failure is nasty precisely because it's silent. helm template before installing shows you the rendered truth.

6. Traffic spikes. Your HPA scales from 2 Pods to 10. Eight of them sit in Pending and your dashboards stay red. What's wrong, and what would have happened with no HPA at all?

Show answer

You have a Pod autoscaler but no node autoscaler — the HPA asked for Pods and nothing provided room for them.

  • HPA scales Pods based on load. Karpenter scales worker nodes when Pods can't be scheduled. They operate at different levels.
  • Pending is the signature: the Pods were created fine, but the scheduler can't place them because the existing nodes have no spare CPU or memory.
  • Here Karpenter is missing or broken — exactly what happened in class, where Karpenter hadn't been reinstalled after the cluster was recreated.
  • With no HPA at all you'd stay at 2 Pods, each getting hammered: slow responses, maybe readiness failures and restarts. The cluster would look calm while users suffer.
  • 🔑 You need both. HPA alone gives you Pending Pods; Karpenter alone gives you an idle cluster that never adds capacity because nothing ever asks.

💡 Check order: kubectl describe pod for the scheduling reason, then whether Karpenter's controller is running and whether its NodePool limits are capping you.

7. You set type: LoadBalancer and AWS hands you a Classic Load Balancer. Explain why, and say what you'd do to get an ALB instead.

Show answer

Because the AWS Load Balancer Controller wasn't installed, so an old in-tree legacy controller handled the Service — and legacy only knows how to make Classic.

  • EKS still carries a legacy load-balancer integration. When the modern controller is absent, that path quietly takes over, which is why it "worked" but produced the wrong thing.
  • Classic is the oldest of AWS's three types (Classic, Network, Application) and shouldn't be used for new work.
  • To get an ALB: install the AWS Load Balancer Controller (an IAM role in AWS plus a Helm chart in kube-system) — an ALB is not possible without it. Then expose the app through Gateway API (GatewayClass → Gateway → HTTPRoute) rather than a LoadBalancer Service.
  • 💡 A LoadBalancer Service handled by the modern controller gives you an NLB, not an ALB. ALBs come from Ingress or Gateway API — the layer that understands hostnames and paths.

🔑 Interview-worthy framing: a Kubernetes object is only a request. A controller has to be running to turn it into real AWS infrastructure, and which controller answers decides what you get.

8. For ten applications on one cluster, how many GatewayClasses, Gateways and HTTPRoutes do you have? Which of those files live in the platform repo and which in each app's Helm chart, and why does that split exist?

Show answer

One GatewayClass, one Gateway, ten HTTPRoutes — and the split follows ownership: cluster-wide things belong to the platform, per-app things ship with the app.

  • GatewayClass × 1 — "use the AWS controller, build me an ALB". Cluster-wide. Platform repo.
  • Gateway × 1 (per listening port) — "listen on 443". Cluster-wide. Platform repo.
  • HTTPRoute × 10 — "this hostname goes to that app's Service". Each app's Helm chart.
  • Why it matters: an app team can ship a new route without touching shared cluster infrastructure, and the platform team can change the shared entrance without editing ten charts. Blast radius and ownership both line up.
  • Each app also needs its own ClusterIP Service — not LoadBalancer. A LoadBalancer Service here would create a second, redundant load balancer.

💡 Adding app eleven is then two lines of real change: the hostname and the backend service name.

9. An interviewer asks: "We run ten microservices on EKS. Why wouldn't you just give each one a LoadBalancer Service?" Give the numbers, and then say when separate load balancers are the right call.

Show answer

Ten LoadBalancer Services means ten load balancers to pay for and operate; one Gateway means one. Cost and operational simplicity.

  • Per-app LoadBalancer: 10 Services → 10 load balancers. Ten line items on the bill, ten sets of listeners, certificates, security groups and health checks to keep straight.
  • Shared Gateway: 1 ALB, 10 HTTPRoutes, 10 ClusterIP Services. Hostnames or URL paths pick the app.
  • Capacity isn't the constraint: roughly 100 HTTP routes per ALB under default configuration.
  • The class page cites a financial services company that moved to shared gateways and ended up with 96% fewer load balancers.
  • When separate is still right: an app needs its own access rules (different source IP restrictions), its own capacity or isolation, a different protocol, or regulatory separation.

💡 Honest extra credit: Ingress could also share an ALB. Sharing isn't unique to Gateway API — Gateway API is just the supported, modern way to do it now that ingress-nginx is retired.

10. Of these, which deserve the most thinking time and why: replica count · VPC CIDR · Service type · resource limits · the production database engine? How should the answer change how you work day to day?

Show answer

VPC CIDR and the production database engine — they're one-way doors. The rest are two-way and can be changed next week.

  • One-way: VPC CIDR can't be resized meaningfully once things are in it; you'd rebuild the network. The production database engine means a real migration with downtime and data risk.
  • Two-way: replica count, resource limits and Service type are all a values edit and a redeploy away.
  • How it changes your work: deliberate slowly on the one-way doors — write it down, ask for review, sleep on it. On two-way doors, pick something reasonable and move; deliberating costs more than being wrong.
  • It also answers "should I build this for the future?": mostly no. Over-building adds complexity now against a future that may not arrive.

💡 Practical move: ask your AI which decisions in this design are one-way. It'll usually surface the two or three that are genuinely final.
