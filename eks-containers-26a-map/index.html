📌 Who brings things back?

Container restart = the kubelet. When PID 1 exits, the kubelet restarts the container in the same Pod, on the same node – same name, same IP (the IP belongs to the Pod). RESTARTS goes up.

New Pod = a controller. The ReplicaSet (created by a Deployment) counts its Pods; one missing → it creates a new one with a new name and new IP, on a node with room (~7 s in class).

Liveness probe fails (Session 08) → the kubelet restarts the container too. Readiness never restarts – it only stops traffic.

Kubelet → containers. ReplicaSet → Pods.

A bare Pod made from pod.yaml has no owner. Delete it and nothing recreates it.

With plain docker run, nobody restarts anything: the container stays Exited.

🔁 Desired state vs actual state

Your YAML is the desired state, stored in etcd. What really runs is the actual state.

Controllers keep comparing the two and fixing the difference: a missing Pod is created, an extra one removed – and they repeat even when everything matches. That loop is reconciliation.

Terraform applies once; Kubernetes applies forever.

Thermostat: you set 21°; it keeps measuring and switches the heating on and off.

💻 Your Mac

Two jobs happen here: building the image (Docker) and telling the cluster what should exist (kubectl). Your app never runs on the cluster from here – the Mac only sends files and requests.

🐳 Docker side – build & test

Docker Desktop runs one Linux VM; every container uses that VM's kernel. The daemon does the work – "Cannot connect to the Docker daemon" = Docker Desktop isn't running.

📄 Dockerfile

The recipe, run once at build. FROM python:3.12-slim → WORKDIR → COPY requirements.txt → RUN pip install → COPY app.py → CMD [...].

RUN happens at build. CMD happens at run and becomes PID 1. Exec form CMD ["gunicorn", ...], never shell form.

1docker build

docker build --platform linux/amd64 -t investment-app:v1 .

Your Mac is arm64; the cluster's nodes are amd64. Without the flag → exec format error on the cluster. Check: docker image inspect … --format '{{.Architecture}}' → amd64.

📦 The image

Layers stacked like an onion. No kernel, nothing running – a sleeping template. Images are immutable: change the Dockerfile and build again. Dependencies before source so the cache is reused.

2Local test: docker run on app-net

One process on the VM's kernel. Lives exactly as long as PID 1. The app finds the db container by name on the user-defined network.

21🚪 The shared ALB – one load balancer for the whole class

Every Ingress of class alb joins group containers-26a = one ALB. Each student's Ingress adds one rule to its 443 listener: host → a target group of ready Pod IPs. Default limit 100 rules.

18⚖️ NLB – a type: LoadBalancer Service (Session 07)

Add the annotation service.beta.kubernetes.io/aws-load-balancer-scheme: internet-facing (without it: internal only) and AWS creates a real NLB: a listener on :80 and a target group holding the Pod IPs, kept equal to the Service's endpoints.

Each connection goes straight to a Pod :8080. Billed by the hour, so student namespaces allow none: exceeded quota … services.loadbalancers=0. Shown live in Eldiiar's namespace. Downside: one NLB per Service, each billed – that's why the Ingress exists.

☸️ EKS cluster containers-26a

A cluster = a control plane + nodes. EKS is AWS's managed Kubernetes: AWS runs the control plane, the nodes are EC2 instances. This cluster runs in EKS Auto Mode: AWS adds a node when no node has room for a new Pod.

🧠 Control plane – run by AWS – master nodes

Receives your commands and decides what runs where. You never log in, you never see it in the console, your app never runs here.

7API server

The front door. Receives every kubectl request, checks who you are and whether you're allowed in that namespace, checks the object is valid, stores it in etcd.

The only way into the cluster: your Mac, the scheduler, controllers and kubelets all talk only to it. Refuses bad files (e.g. selector ≠ template labels).

🗃️ etcd

The cluster's database: every object, the record of what should exist. Turn your laptop off overnight and kubectl get pods still knows – because of etcd.

Not your app's database, holds no logs.

9Scheduler

Picks a node for each new Pod that has no node yet, looking at free CPU and memory, and spreads Pods across nodes. It starts nothing itself.

No node has room → Pod stays Pending until Auto Mode adds one (a minute or more).

Session 11: it adds up the requests. A Pod's request must fit on one node: 400m free + 400m free ≠ room for 600m.

8Controllers

Loops that never stop: desired vs running → fix the difference → repeat. The Deployment controller makes a ReplicaSet; the ReplicaSet controller makes Pods until the count matches.

Says who and where: user student:my-namespace gets ClusterRole edit – in your namespace only, because a RoleBinding is namespaced. That's why a classmate's Secrets are Forbidden.

A user for a program: system:serviceaccount:<ns>:default. Pods that name none (your investment-app) run as it. It has no rights. Never bind a Role to it – every such Pod would get it. A program that needs rights gets its own ServiceAccount + small Role.

Session 12 – the namespace's own rules (set by the admins) and the autoscaler. All checked or read by the control plane; none of them is set on a node.

31LimitRange – per container

Fills in what a container didn't declare: request 50m / 64Mi, limit 250m / 256Mi. Rejects a container over the max (1 CPU / 1Gi) with 403. A value you write is kept. The max is not a default. Checked only when a Pod is created. kubectl get limitrange -o yaml

31ResourceQuota – the namespace total

Adds up what Pods declare: 500m CPU requests, 1Gi memory requests, 2 CPU / 2Gi limits, 8 Pods. Over it → no Pod is created; the error is on the ReplicaSet: FailedCreate: exceeded quota. A new node can't help. kubectl describe resourcequota

32HorizontalPodAutoscaler

A controller that changes a Deployment's replicas toward a target, between min and max. Utilization = CPU use ÷ CPU request × 100 – no request, no CPU scaling. Class demo unit5-cpu: 60%, 1–2 replicas. kubectl get hpa --watch

Stable names postgres-0, postgres-1; one claim per Pod from volumeClaimTemplates (data-postgres-0…); scales one at a time; a replaced Pod gets the same name and claim. Doesn't do replication or backups.

📄 The manifests, piece by piece – pod.yaml vs deployment-drill.yaml

Same four top-level keys in every manifest. The green part is the same Pod in both files: a Deployment's template is the Pod you already typed, minus apiVersion, kind and the name (Pod names are generated).

Deployment
metadata→ about the Deployment: its name (drill)
spec→ what the Deployment should do: replicas, selector, and…
template = the Pod blueprint
metadata→ about each Pod: its labels (app: drill)
spec→ what each Pod runs: containers, image, port

Notice: there are TWO metadata and TWO spec

This is the confusing part. The trick: look at how far a key is indented to know who it belongs to.

The top metadata / spec (no indent) are for the Deployment. The ones inside template (indented 4 spaces) are for the Pod.

A Deployment has a Pod inside it, like a box with a smaller box inside. The inner box is exactly the metadata + spec from pod.yaml – that's why the green parts below look the same.

So the Deployment's name lives in the outer metadata, but the label its selector searches for lives in the inner metadata – on the Pods.

🩺 Probes, piece by piece (Session 08) – Running doesn't mean the app can answer

A probe is a check the kubelet runs against one container, every few seconds, for its whole life. It goes under the container in the Deployment. Scale twins: readiness = the target group health check, liveness = the ASG health check that replaces an instance.

deployment-drill-readiness.yaml (the container part) 
containers:
  - name: drill
    image: …/drill:v1
    ports:
      - containerPort: 8080
    readinessProbe:1
      httpGet:2
        path: /3
        port: 8080
      periodSeconds: 54
      failureThreshold: 35

A livenessProbe has the same shape – only the action on failure differs. Class demo: liveness on /health (404) → RESTARTS climbs → CrashLoopBackOff.

  1. 1

    readinessProbe – sits under the container, beside image and ports. Same level as livenessProbe / startupProbe.

  2. 2

    httpGet – the check type (most common). Others: tcpSocket (port accepts a connection), exec (command exits 0), grpc.

  3. 3

    path – a URL the app answers, like in a browser – not a folder. Passes on 200–399. The drill image has only /, so /health = 404 = fails. A route exists only if it's in the image.

  4. 4

    periodSeconds – how often (default 10). Also initialDelaySeconds (0), timeoutSeconds (1).

  5. 5

    failureThreshold – fails in a row before it counts as failed (default 3). successThreshold (1) is the way back. Each controls one direction – no conflict.

ProbeQuestionOn failure
ReadinessReady for requests right now?Stop traffic. No restart. The Deployment does nothing – the count is still right
LivenessStill working?Restart the container – same Pod, name, IP; RESTARTS +1. Waits 10 s → 20 s → 40 s … 5 min
StartupFinished booting?The other two wait; never passes → restart. Rarely needed

The stuck rollout = a good thing. Apply a file whose new Pods never get ready (wrong path, bad image): the rollout stops at the first new Pod, and the old Pods keep serving. No auto-rollback – after 10 min exceeded its progress deadline. Apply the fixed file; the bad ReplicaSet goes to 0.

Not-ready Pod in the EndpointSlice: get still lists its address; describe shows Ready: false. "The devil is in the details" – describe when get looks wrong.

Rules of thumb: liveness checks the app itself, never its database (a slow DB would restart every Pod at once). Use only the probes the app needs.

📏 Requests & limits, piece by piece (Session 11) – what a Pod may use on a shared node

A node is an EC2 instance with a fixed amount of CPU and memory, shared by Pods from any namespace. Without limits, one busy Pod can eat the node and starve its neighbours. So every container says up front how much it needs (request) and how far it may go (limit).

    resources – per container, beside image and the probes. Every replacement Pod from the template gets it.

  3. 3

  4. 4

  5. 5

💾 Storage, piece by piece (Session 13) – the Pod is temporary, the claim keeps the data

Files a container writes without a volume sit on the node's disk and are gone when the Pod is replaced (ephemeral). Fine for the stateless web app – its data is in the DB. Fatal for Postgres. Class demo: create trades, delete the Pod → relation "trades" does not exist. With a claim → buy | 150.00 survives.

✅ Jobs & CronJobs, piece by piece (Session 13) – work that finishes

A Deployment keeps something running forever. A Job runs a task until it succeeds (exit code 0) and stops. A CronJob creates a new Job on a schedule.

  1. 1

    batch/v1 – the API group for Jobs and CronJobs.

  2. 2

    backoffLimit: 2 – two retries after failures, then the Job is failed: BackoffLimitExceeded.

  3. 3

  4. 4

  7. 7

✏️ Fixing a common wrong idea

Wrong: "A container dies instantly without a Pod; inside a Pod it lives longer."

A container lives exactly as long as its PID 1 runs, with or without Kubernetes. With plain docker run it then stays Exited until someone starts it.

What the Pod adds: Kubernetes never runs a bare container – every container runs inside a Pod, and the Pod is the unit Kubernetes schedules and manages. When PID 1 exits, the kubelet restarts the container in the same Pod.

Extra context – not from class: that's the Pod's restartPolicy, Always by default.

🔎 Check: where does my Pod run?

kubectl get pods -o wide

Proves: the Pod's IP and its NODE (the EC2 instance).

Does not prove: that your Mac can reach that IP. curl --max-time 5 <pod-ip>:8080 times out – the Pod IP is on the cluster's network (a private address in the school's VPC). Same idea as RDS in a private subnet.

🏷️ Namespace

A set of object names inside one cluster: your room in the shared house. Your Pods, your quota (8 Pods at once) and your permissions live in it. One typo in kubectl delete pod can't remove someone else's app.

Not a machine and not a network. Pods from many namespaces share nodes, and yours can be on several nodes – so it's drawn as a tag, not a box.

default exists on every cluster; you have no permissions there → Forbidden until set-context. Then No resources found = working and empty.

🔎 Check: which nodes exist?

kubectl get nodes

Proves: the worker machines exist and are Ready – NAME (instance id), STATUS, ROLES, AGE, VERSION. The control plane never shows up.

Does not prove: anything about your Pods.

🌍 Region, AZs & EKS vs ECS

An EKS cluster lives in one Region (us-east-1), with nodes across several AZs – one AZ failing doesn't stop it. Another Region = a second cluster. Multi-AZ alone doesn't keep your app up: replicas, placement, capacity and an owning controller matter.

EKS = managed Kubernetes (per-cluster hourly fee + nodes billed as EC2; same skills on GKE/AKS). ECS = AWS-only, says task / service where Kubernetes says Pod / Deployment.
