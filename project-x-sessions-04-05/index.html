🖱️ ClickOps first: why build it by hand once

  • New rhythm: explain → demo → task → solo work. The morning after class the instructor posts a recording of his own AI-assisted solution to compare with yours.
  • ClickOps = operations by clicking through the console. Do it once before automating, so you have a mental picture of every piece and dependency.
  • Without it you either patch errors one by one or write a pile of untested code. Like building a whole car before you ever turn the key.
  • Same at a real job: test account → create by hand → understand → delete → write the code.
Context is not fixable later. Understand it now.

🧠 Control plane vs worker nodes

  • Creating an EKS cluster creates only the control plane (API server, etcd, scheduler, controller manager). AWS runs it.
  • Worker nodes are a separate step. Without them pods stay Pending.
  • One account can hold several clusters, so always switch explicitly:
aws sso login
aws sts get-caller-identity
aws eks list-clusters --region us-east-1
aws eks update-kubeconfig --name CLUSTER_NAME --region REGION
kubectl get nodes

⚙️ Three ways to run workers

OptionWho does whatTrade-off
EKS managed node groupAWS bootstraps and joins the EC2s, replaces them during a managed updateSimpler, less control
Self-managed nodesYour Auto Scaling Group; EC2s join through user dataMore control, easier to fix yourself
EKS Auto Mode (late 2024)EKS makes nodes when a pod needs roomLeast work; AWS owns more of the node lifecycle
  • Big enterprises often go self-managed: with a 400-node fleet you want direct control, not a support ticket.
  • Karpenter is another way: it watches pending pods and launches EC2s for them.
  • The reference build uses a managed node group in the existing private subnets. For the homework, the choice is yours. Make it a reasoned one.

🚨 Troubleshooting: why the workers didn't join

  • Root cause 1: the cluster used four subnets, including the database subnets. Those have no route to the internet, so a worker there can't reach the AWS APIs it needs to register (EKS endpoint, IAM/STS, ECR).
  • Fix: recreate the node group in the app subnets only, the ones that route through NAT gateway → internet gateway.
  • Root cause 2: the node role was missing AmazonEKSWorkerNodePolicy (calls like ec2:DescribeInstances).
  • To reach AWS services without the internet you need VPC endpoints, which cost extra.
  • Good AI job: a specific problem, a clear "done" condition, lots of config to read.

🔐 Two IAM roles (they can't share one)

RoleTrustsAttach
Cluster (control plane)the EKS serviceAmazonEKSClusterPolicy
Node (worker)EC2AmazonEKSWorkerNodePolicy, AmazonEC2ContainerRegistryReadOnly, more as needed (Secrets Manager, SSM)
  • Create both roles first, then the cluster. In real environments use your own custom roles, not console-generated defaults.

🧩 Add-ons: how a pod finds a Service

  • VPC CNI gives each pod an IP from the VPC.
  • kube-proxy programs the rules on each worker that send Service traffic to backend pods.
  • CoreDNS answers "what's the address of Service db?" so pods use names, not IPs.
client pod → CoreDNS: "db?" → ClusterIP → kube-proxy rules → backend pod (VPC IP from the CNI)

📐 Terraform: modules, layout and your first piece

  • A module is a reusable block of Terraform. A company might have 20–40 (EKS, S3, load balancer, networking, Lambda, RDS…).
  • Public modules are on the Terraform Registry, but many companies write their own: public ones are over-engineered, harder to maintain, and need a security audit.
  • Flat layout: main.tf, variables.tf, provider.tf, outputs.tf, project-x-dev.tfvars. With modules: modules/eks/ plus a root that calls source = "../../modules/eks".
  • State, variable values and tfvars live in the root, never in a child module.
  • The piece you write yourself: find the VPC in the console (CloudFormation stack → Resources → Vpc), then look it up:
variable "vpc_id" {
  type = string
}

data "aws_vpc" "existing" {    # data = look up, don't create
  id = var.vpc_id
}

output "vpc_cidr" {
  value = data.aws_vpc.existing.cidr_block   # compare with the console
}

When you review the bigger plan, sort it into what Terraform reads (VPC, subnets) and what it creates (EKS pieces).

🏛️ Architecture decisions in the reference build

  • Managed node group for system workloads only: 1 node in dev, 2 in prod.
  • Karpenter runs on that node, watches for pending pods, and launches EC2 workers for the app. More to manage than Fargate, more control than Cluster Autoscaler, and it looks at pending pods directly.
  • Database: the existing RDS Postgres, shared with ECS for now.
  • Subnets: two new private /19 subnets (~8,000 IPs each) in the existing VPC. NAT gateway reused.
  • State: S3 with versioning and encryption.
  • In class the cluster and system node came up, but Karpenter wasn't installed live: its Helm install is a separate step. PR #17 tried Auto Mode for comparison.

🌳 Three roots, three state files

OrderRootCreatesState
1bootstrapS3 state bucketlocal (no backend yet)
2network2 EKS subnets in the existing VPCnetwork.tfstate
3ekscluster, node group, add-ons (~43 resources)eks.tfstate
  • A root is the folder where you run terraform. Each has its own state. Child modules: eks-cluster, eks-network, state-backend.
  • Why separate? Different lifecycles: change the cluster without touching the network.
  • EKS reads subnet IDs with terraform_remote_state. It doesn't update by itself when network changes, and it needs read access to the whole network state. HashiCorp prefers explicit sharing, e.g. SSM Parameter Store. Inside one root, plain module outputs are simpler.
  • To copy it: change the account ID in bootstrap (bucket names are global), backend bucket names, cluster admin role, and the VPC lookup. Don't overlap existing subnets.

💾 State: memory, recovery and locking

  • State = Terraform's memory: resource address ↔ real resource.
  • Lose it and the resources still exist, but Terraform plans to create them again. Don't apply that plan.
  • Recovery: with S3 versioning, download the previous version and put it back at the exact original key. This fixes Terraform's memory only. It doesn't roll back infrastructure or data. Protect the local bootstrap state too.
  • Locking: use_lockfile = true writes a temporary .tflock while a run is going. A second run gets "Error acquiring state lock". It locks that state only: not AWS, not another root.
terraform {
  backend "s3" {
    bucket       = "my-tfstate-ACCOUNTID"
    key          = "eks.tfstate"
    region       = "us-east-1"
    encrypt      = true
    use_lockfile = true   # S3-native lock, no DynamoDB table
  }
}

Quiz: Session 04

1. You create an EKS cluster, it shows Active, and a pod stays Pending forever. What's missing?

Show answer

Worker nodes. Creating a cluster only gives the control plane. The scheduler has nowhere to put the pod. "Active" means the brain is up, not that there's a body to run anything.

2. Node group created, EC2s running, but kubectl get nodes is empty. The subnets include the DB subnets. Why does that break it?

Show answer

The workers can't reach the AWS APIs they need to join. DB subnets have no route out. Workers must talk to the EKS endpoint, STS and ECR. Fix: app subnets with a NAT route, or pay for VPC endpoints.

3. Subnets fixed, still no nodes. What do you check next, and which policy was missing in class?

Show answer

The node IAM role. It must trust EC2 and have AmazonEKSWorkerNodePolicy plus AmazonEC2ContainerRegistryReadOnly. The worker policy was missing. Network first, then identity.

4. Why can't the control plane and workers share one IAM role?

Show answer

Different principals, different trust. The cluster role trusts the EKS service; the node role trusts EC2 (worn through an instance profile). Their permissions differ too. Least privilege keeps them apart.

5. Interviewer: "Managed node groups, self-managed or Auto Mode for a 400-node production fleet? Defend it."

Show answer

Weigh control against effort. Managed: AWS joins and rolls nodes, less control. Self-managed: full control over AMI, bootstrap and upgrades, fix it yourself, which is popular at scale. Auto Mode: least work, extra fee. EC2 cost is the same for managed vs self-managed. Pick one and say why.

6. Isn't ClickOps the opposite of Infrastructure as Code?

Show answer

ClickOps is for learning, IaC is for running. Click it once in a test account to see every piece, delete it, then write code. Production still goes through code.

7. A pod calls http://db:5432. Which add-ons make that work?

Show answer

CoreDNS resolves the name, kube-proxy routes the ClusterIP, VPC CNI gave the pod its IP. Without CoreDNS names fail; without kube-proxy the Service IP goes nowhere.

8. You wrote data "aws_vpc" "existing". Then you run terraform destroy. What happens to the VPC?

Show answer

Nothing. A data source only reads. CloudFormation owns the VPC, so it isn't a managed resource in your state. That's why the homework starts with a lookup.

9. Where do terraform.tfvars and state go with modules: root or modules/eks/?

Show answer

The root. You run Terraform there; tfvars are only auto-loaded from the working directory. A child module just receives inputs.

10. One classmate approved your PR. Why can't you merge into main?

Show answer

GitHub branch protection requires a PR and the set number of approvals. Your write access only lets you push your own branch.

Quiz: Session 05

1. Someone deletes eks.tfstate. Next morning terraform plan says "43 to add". What happened to the cluster, and what do you do?

Show answer

The cluster still runs; Terraform lost its memory. Don't apply. Restore the previous version from S3 versioning at the exact same key, then plan should show no changes.

2. You restored yesterday's state, but last night someone added a node group by hand. What does restoring do and not do?

Show answer

It fixes Terraform's memory, not AWS. The hand-made node group still exists and isn't in state. Import it or remove it on purpose.

3. Two people run apply on the eks root at once. One gets "Error acquiring state lock". What's locked?

Show answer

Only that root's state. Not AWS (console clicks still work) and not the network root. Released when the run ends.

4. "Don't commit the lock file, it's temporary." Which lock file, and is that right?

Show answer

Two files. .tflock (state lock, S3, temporary) never goes in Git. .terraform.lock.hcl (provider versions) does.

5. Why split network and EKS into two roots? A pro and a con.

Show answer

Pro: separate lifecycles, smaller blast radius. Con: IDs must cross the gap through remote state (full read access, no auto-update) or SSM Parameter Store.

6. Why does bootstrap keep its state locally?

Show answer

It creates the bucket. The backend must exist before init can use it. So protect that local file, and keep the bucket until everything it tracks is gone.

7. The AI picks EKS Auto Mode right away. What should you do?

Show answer

Push back. Ask about fees and downsides, ask what teams actually use, ask what the answer is based on. Make it interview you so you decide.

8. In the reference build, 6 new app pods don't fit on the system node. What happens?

Show answer

Pending → Karpenter sees them → launches fitting EC2s → pods scheduled. Unless you skipped the Helm install: then nothing launches and they stay Pending.

9. PX-108: EKS pods crash with "connection timed out" to RDS. First place to look?

Show answer

The RDS security group. A timeout = dropped packets. It probably only allows the ECS tasks' SG. Allow 5432 from the EKS nodes/pods SG or the new subnet CIDRs. Then check host and credentials.

10. Your PR is 900 lines of AI code plus a long evidence.md. How do you make it reviewable?

Show answer

A ~20-line one-pager on top (what changed, decisions, testing, unfinished, cleanup), linking a details file and a decisions log. Commit non-secret tfvars or an example.
