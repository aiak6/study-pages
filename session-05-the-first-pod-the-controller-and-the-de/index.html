The kubelet: the agent on every node

Problem: a node is just an EC2 instance. How does the cluster know it belongs, and that its containers are healthy?

What it is: a program EKS installs on every node. It starts containers and reports their health back to the control plane. If a container exits, the kubelet restarts the container in the same pod, on the same node, and RESTARTS goes up by one. Like restarting a frozen laptop: same machine, fresh start.

The kubelet restarts a container. It never creates a new pod. New pods come from a controller.

The bare Pod: nobody is counting

kubectl apply -f pod.yaml stores the object and returns. Then the scheduler picks a node, and the node pulls the image and starts the container. The pod's IP is on the cluster's network: your laptop can't reach it, only the API server through kubectl.

Delete it and it's gone. Nothing in pod.yaml says how many there should be, so nothing watches the count.

STATUS / columnMeans
PendingNo node yet. On this cluster AWS may be adding a node (a minute or more)
ContainerCreatingHas a node; the node is pulling the image
RunningContainer started
READY 1/2Containers ready out of containers in the pod. Here one image couldn't be pulled
RESTARTSHow many times the kubelet restarted the container in this pod

The controller: Kubernetes' Auto Scaling group

Problem: companies run tens of images with several copies of each. Someone has to notice when a copy dies and start another.

What it is: a program in the control plane that compares desired state with what is running, fixes the difference, and repeats. It never stops. You already used one: the Scale ASG with desired capacity 2.

kubectl apply → API server stores "replicas: 2" in etcd → apply returns
↓
controller loop: desired 2 vs running ? → 1? create one → check again …
Terraform applies once; Kubernetes applies forever.

The Deployment: a count plus the Pod you already typed

apiVersion: apps/v1        # Pod is v1; Deployment is apps/v1
kind: Deployment
metadata:
  name: drill
spec:
  replicas: 2              # the count = ASG desired capacity
  selector:                # which pods are mine
    matchLabels:
      app: drill
  template:                # the Pod to create = the launch template
    metadata:
      labels:
        app: drill         # stamped on every pod; must match the selector
    spec:
      containers:
        - name: drill
          image: IMAGE_URI
          ports:
            - containerPort: 8080
FieldJobScale equivalent
replicasHow many pods should existDesired capacity
templateThe full pod spec, written out. It can't point to pod.yamlLaunch template
selectorWhich label marks this Deployment's podsThe ASG's membership

Pods are found by label, not by name, because their names are generated: <deployment>-<ReplicaSet hash>-<random id>, e.g. drill-7ff7775db6-fjb2v.

deployment-drill.yaml is a file on your laptop. kubectl get deployments shows the object in the cluster. apply copies the file in; nothing copies back.

The label written twice, and the refusal

Under selector: which pods this Deployment counts. Under template: the label stamped on new pods. If they differ, the Deployment would create pods it never counts, and keep creating them. So the API server refuses the file:

The Deployment "drill" is invalid: spec.template.metadata.labels: Invalid value: ...: `selector` does not match template `labels`

Nothing is created or changed. Fix it, apply again, and you get unchanged: the cluster already matches the file.

Deployment → ReplicaSet → pods

Deployment  drill                 (you write this)
 └─ ReplicaSet  drill-7ff7775db6  (the Deployment creates it: holds the count)
      ├─ pod  drill-7ff7775db6-fjb2v
      └─ pod  drill-7ff7775db6-x9k2p

ReplicaSet: the object the Deployment creates to hold the count and own the pods. Its controller creates the replacements. You never write one. kubectl get rs shows DESIRED / CURRENT / READY: desired 3, current 2 → the controller creates one. After scale, it's the same ReplicaSet (same hash, same age) with a new DESIRED number.

One owner per level: Deployment owns the ReplicaSet, the ReplicaSet owns the pods.

Where the notes correct what was said live

Left: what was said in class. Right: the correct version from the site notes and deck.

Said in classCorrect version (site notes and deck)
"Link traffic to the deployment and it splits it across the three pods"A Deployment doesn't receive traffic. It only keeps a count. A Service gives the pods one address and spreads requests (unit 3).
"If there's a conflict between the file and the cluster, it always throws an error"No error. After scale --replicas=5, applying a file that says 3 quietly sets it back to 3. The last write wins, so in real work you edit replicas in the file and apply it.
"This cluster is in one zone"An EKS cluster is in one region, across several availability zones, so one zone failing doesn't stop it. Another region needs a second cluster.
"The kubelet replaces the pod"Maher corrected this himself: the kubelet restarts the container in the same pod. Replacing a deleted pod is the ReplicaSet controller's job.

Redo the demo yourself

This uses the repo's drill image on port 8080, as in the notes and after-class. Maher's live demo used nginx on port 80; the steps are the same. Tick each step as you finish it; your ticks stay in this browser.

Before you start

The setup page is done (AWS CLI, kubectl, the 312-cluster profile, update-kubeconfig run once). Open two terminals in ~/DevOps/containers/02-the-cluster-and-the-loop. Your pod.yaml already has the drill image in it.

0 of 9 steps done

1. Sign in and point at your namespace

The SSO token lasts one day, so this is the first thing every class day.

aws sso login --profile 312-cluster
aws sts get-caller-identity --profile 312-cluster   # check 1
kubectl config use-context containers-26a
kubectl config set-context --current --namespace=<your-namespace>
kubectl config get-contexts                         # check 2
kubectl get pods
What you should see

No resources found in <your-namespace> namespace. That means it works and the namespace is empty.

2. Apply the bare Pod

apply stores the object; the cluster does the rest.

kubectl apply -f pod.yaml   # pod/drill created
kubectl get pods            # run it twice, a few seconds apart
What you should see

0/1 ContainerCreating, then 1/1 Running.

3. Read where it runs and what it did

kubectl get pods -o wide
curl --max-time 5 <pod-ip>:8080          # from the laptop: times out on purpose
kubectl logs drill
kubectl describe pod drill
What you should see

Connection timed out from curl. Listening at: http://0.0.0.0:8080 in the logs. Events read Scheduled, Pulled, Created, Started.

4. Delete it and watch nothing happen

kubectl delete pod drill
kubectl get pods           # and again ten seconds later
What you should see

No resources found both times. Nothing was counting.

5. Put the image into the Deployment and apply it

deployment-drill.yaml still says IMAGE_URI.

sed -i '' 's|IMAGE_URI|SCHOOL_ACCOUNT_ID.dkr.ecr.us-east-1.amazonaws.com/drill:v1|' deployment-drill.yaml   # macOS sed
kubectl apply -f deployment-drill.yaml
kubectl get deployments                  # READY 2/2
kubectl get pods
What you should see

Two pods named drill-<hash>-<id>, both 1/1 Running. You never typed those names.

6. See all three levels

-l selects by label, like the Deployment does.

kubectl get deploy,rs,pods -l app=drill
What you should see

One deployment, one replicaset drill-<hash> with desired 2, and two pods carrying the same hash.

7. Delete one pod while watching

Terminal 2 watches; terminal 1 deletes one pod by its full name.

kubectl get pods -w                          # terminal 2
kubectl delete pod drill-<hash>-<id>         # terminal 1
What you should see

The old pod goes Terminating, and a new name goes Pending → ContainerCreating → Running within seconds.

8. Trigger the label refusal

Under template: metadata: labels:, change app: drill to app: drilx.

kubectl apply -f deployment-drill.yaml   # refused
# change drilx back to drill, then:
kubectl apply -f deployment-drill.yaml   # deployment.apps/drill unchanged
What you should see

`selector` does not match template `labels`, then unchanged.

9. Scale, then let the file win

kubectl scale deploy/drill --replicas=3   # a third pod appears
kubectl get rs                            # same ReplicaSet, DESIRED 3
kubectl apply -f deployment-drill.yaml    # the file still says 2
kubectl get pods
What you should see

Three pods, then back to two, with no warning. The last write wins.

If it goes wrong

ErrorMeaning
Error from server (Forbidden) ... in the namespace "default"The context has no namespace. Run the set-context line from step 1 again.
An SSO or expired-token error on any commandThe one-day sign-in ran out. Run aws sso login --profile 312-cluster.
Pod stuck in Pending for a minuteNormal when the cluster has no room: AWS is adding a node. Wait.
ErrImagePull / ImagePullBackOffThe image can't be pulled. Most likely you skipped step 5 and IMAGE_URI is still in the file.
A new pod refused with a quota messageYour namespace allows 8 pods. Clean up old ones first.

Clean up

kubectl delete -f deployment-drill.yaml -f pod.yaml --ignore-not-found
kubectl get pods                                                         # No resources found

The cluster is shared and your namespace allows 8 pods, so clear it before Thursday. Deleting the Deployment also deletes its ReplicaSet and every pod.

What the instructor stressed, and what's next

Stressed in class

  • Pod = car body, container = engine. No container, no pod. Docker and Kubernetes work together; one doesn't replace the other.
  • The manifest says what should exist, not steps. That's the difference from a Dockerfile.
  • Selector and template labels must match. Shown twice, with and without an existing Deployment.
  • The YAML file is a starting point. The cluster can drift from it, and kubectl never edits your file. His analogy: house plans on paper vs telling the builder "change that window" in person.
  • Check your context before you change anything. The dev script that ran against production and took hours to undo.
  • Use the docs. Copy the example manifest and change what you need.
  • Class beats the knowledge interview. If one is scheduled during class, message Aziz on Slack to reschedule.
