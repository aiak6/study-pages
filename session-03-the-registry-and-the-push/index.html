A second container: Postgres on its own network

app-net is a private network on the laptop. Only containers you put on it can use it, and they find each other by name, so DB_HOST=db finds the container called db. Same idea as RDS in a private subnet only the app servers can reach (Scale Session 06), or an SSH tunnel.

-e POSTGRES_* are environment variables the official image reads on its first start (its Docker Hub page lists them). They must match what the app uses in investment-app.env. You install nothing, just as you installed nothing on RDS. postgres:16 is about 400 MB, so the first pull is slow. Secrets Manager is out of scope for now: everything is local and hard-coded on purpose.

Order: network, then the DB container, then the app container. Check docker ps shows db as Up before starting the app.

Why the app stopped twice

What happenedLog saidFix
Failure 1The app started on Docker's default bridge network, where the name db doesn't existName or service not knownAdd --network app-net to the app's docker run
Failure 2app.py creates its table on import. With --workers 2, both workers ran CREATE TABLE at the same moment on a new database, and one failedWorker failed to boot--preload: import the app once in the master, then start the workers
CMD ["gunicorn", "--workers", "2", "--preload", "--bind", "0.0.0.0:8080", "app:app"]

A Dockerfile change needs a new build: build, docker rm -f app, run again. The course repo's Dockerfile has --preload now. Both causes were found by pasting the log into Claude, which is how Eldiiar works day to day.

Read what Claude changes before you accept it. Its first answer also changed the port mapping, which wasn't the problem, and the page stopped loading. The real fix was the original command plus --network app-net.
Rule: docker ps -a shows Exited → docker logs app → read the error → fix → rebuild if the Dockerfile changed.

The payoff: a second copy in seconds

docker run -d --name app2 --network app-net -p 127.0.0.1:8002:8080 \
  --env-file investment-app.env investment-app:v1

The same image answers on port 8002 a few seconds later. Compare the nine-step boot script from Scale Session 09. The image runs the same way on any Linux machine with the same processor type.

Docker Desktop shows the same images and containers as docker images and docker ps -a, with stop and delete buttons, and scans each image for packages with known vulnerabilities. At work you'll mostly use the CLI.

The processor: arm64, amd64 and --platform

uname -m   # arm64 on Apple Silicon; x86_64 (= amd64) on Intel, EC2 and the cluster
docker build --platform linux/amd64 -t investment-app:v1 .
docker image inspect investment-app:v1 --format '{{.Os}}/{{.Architecture}}'   # linux/amd64

A program is built for one kind of processor, called its architecture. An image built on Apple Silicon holds arm64 programs. The cluster's amd64 machines can't run them, and the container stops with exec format error.

The difference is the processor, not macOS vs Linux: these are Linux images on both machines. The --platform build is slower because the Mac emulates the other processor.

Rule: check with docker image inspect before every push.

Registry, repository and tags

Registry: a service that stores images. Docker Hub is one; Amazon Elastic Container Registry (ECR) is this course's.

Repository: inside a registry, it holds the versions of one app's image. Make one per app, investment-app, in your own AWS account. It's not a git repo and not an S3 bucket. Think of a GitHub repo for images.

Image tagRepository tag
Examplev1owner = devops, a cost code
NamesOne image in the repoThe repo as an AWS resource, like EC2 tags
Used byDockerPeople and finance. Docker never sees it

If the ECR bill jumps from $100 to $1,000 in a month, finance reads the resource tags to see which team to ask. A lifecycle policy deletes images by a rule, for example everything older than a year.

Price: $0.10 per GB per month stored. Push is free, a pull from the same region is free, and a cross-region pull is about $0.09/GB. The cluster is in us-east-1.

The full image address

Change any part and watch the address update. docker push, docker pull and the cluster all use this whole address.

ECR is regional, so a repository made in us-east-1 is not listed in any other region.

Tag vs digest

TagDigest
Looks likev1, latestsha256:…
Can it move?Yes. A person can point it at another image.No. Computed from the bytes, like a git commit SHA.
Build with no tagDocker uses latest; building again moves latest and leaves the old image untaggedSame content, same digest. Change anything and it changes.

latest doesn't mean newest. It means no tag was given. A digest isn't encryption, and nothing can be read back from it. A build that reuses every cached layer gives the same image and ID.

Rule: use version tags like v1 and v2, never latest.

Your ECR repository from Terraform, then the push

Run aws sts get-caller-identity first: the next commands act in your account. Then two files in a folder of their own (in class, 01-the-container/ecr-terraform/):

# providers.tf
terraform {
  required_providers {
    aws = { source = "hashicorp/aws", version = "~> 6.0" }
  }
}
provider "aws" { region = "us-east-1" }

# ecr.tf
resource "aws_ecr_repository" "investment_app" {
  name                 = "investment-app"
  image_tag_mutability = "IMMUTABLE"   # a pushed tag can never be overwritten
}
terraform init && terraform plan && terraform apply
REGISTRY=<your account>.dkr.ecr.us-east-1.amazonaws.com
aws ecr get-login-password --region us-east-1 \
  | docker login --username AWS --password-stdin $REGISTRY   # valid 12 hours
docker tag investment-app:v1 $REGISTRY/investment-app:v1
docker push $REGISTRY/investment-app:v1
GotchaWhat to do
Claude's ecr.tf also has a provider "aws" blockDelete it. Terraform refuses two provider blocks for the same provider; this stopped terraform init in class.
docker push investment-app fails with deniedA bare name is a Docker Hub name. Use the full ECR address.
Pushing v1 twice fails with tag invalid … already existsThat's IMMUTABLE working. Push v2.
A push stops part way with a network errorRun it again. Layers already sent aren't sent twice.
Watch out: the console's View push commands button builds with no --platform and tags latest. On Apple Silicon that pushes an arm64 image the cluster can't run. If inspect says linux/arm64, rebuild with --platform linux/amd64 and push as v1.

Cross-account: the repository policy

Your repository is in your account. The school's EKS cluster is in the school's account, SCHOOL_ACCOUNT_ID. A cluster is a group of Linux machines (EC2 underneath) that run containers together, and those machines share an IAM role that must be allowed to pull your image. Like IAM roles in Scale Session 04, it needs two sides:

SideWhatStatus
School's sideA role policy on the node role allows the pull actionsAlready done
Your sideA resource policy on your repository naming that roleYou write this one. Without it the pull is refused.
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Principal": { "AWS": "arn:aws:iam::SCHOOL_ACCOUNT_ID:role/containers-26a-node" },
    "Action": [
      "ecr:BatchGetImage",
      "ecr:GetDownloadUrlForLayer",
      "ecr:BatchCheckLayerAvailability"
    ]
  }]
}
aws ecr set-repository-policy --repository-name investment-app \
  --policy-text file://repository-policy.json

Or in the console: your repository → Permissions → Edit policy JSON → paste → Save. View JSON shows what was saved.

The three actions are what a pull does: check which layers exist, get their download addresses, get the image. ecr:GetAuthorizationToken isn't here; it can only go in a role policy, on the school's side.

Rule: don't change the account ID. SCHOOL_ACCOUNT_ID is the school's account, and the policy names the school's role.

Next: why Kubernetes

One or two containers are easy to start by hand. A stopped container stays stopped until someone starts it, and nobody can watch a hundred of them.

Kubernetes is container orchestration, like a conductor for an orchestra. It places containers on a group of machines, starts a new one when one stops, and adds copies when load grows. The school's EKS cluster is AWS-managed, has one node right now, and scales up as more people use it.

The golden rule of this class: an image is only useful where it can run and be found. Build it for the cluster's processor, push it to your registry under a version tag, and grant the cluster's role the pull from your side of the account line.

Redo the demo yourself

Steps 1–4 run on your laptop. Steps 5–8 act in your own AWS account. Tick each step as you finish it; your ticks stay in this browser.

Before you start

Docker Desktop running, the containers repo pulled, and apps/investment-app/investment-app.env in place. Use the DB_PASSWORD from that file for Postgres.

0 of 8 steps done

1. Build, then make the network and the database

Order matters: network, then DB, then app.

cd apps/investment-app
docker build -t investment-app:v1 .
docker network create app-net
docker run -d --name db --network app-net \
  -e POSTGRES_USER=investment_app \
  -e POSTGRES_PASSWORD=<DB_PASSWORD from investment-app.env> \
  -e POSTGRES_DB=investment_app \
  postgres:16
docker logs db      # wait for: database system is ready to accept connections
What you should see

db Up in docker ps, and the "ready to accept connections" line in its log.

2. Start the app on the same network

Both containers need --network app-net.

docker run -d --name app --network app-net -p 127.0.0.1:8001:8080 \
  --env-file investment-app.env investment-app:v1
curl localhost:8001/health
What you should see

{"server":"…","status":"ok"}. If it Exited, run docker logs app and check the two failures above.

3. Start a second copy

The payoff: one command.

docker run -d --name app2 --network app-net -p 127.0.0.1:8002:8080 \
  --env-file investment-app.env investment-app:v1
curl localhost:8002/health
What you should see

The same answer on port 8002 a few seconds later.

4. Build for the cluster's processor

Check before every push.

uname -m
docker build --platform linux/amd64 -t investment-app:v1 .
docker image inspect investment-app:v1 --format '{{.Os}}/{{.Architecture}}'
What you should see

arm64 from uname on Apple Silicon, then linux/amd64 from inspect.

5. Create your ECR repository with Terraform

Check the account first. Two files: providers.tf and ecr.tf (above). Only one provider block.

aws sts get-caller-identity
terraform init && terraform plan && terraform apply
What you should see

Your account in the identity output, then Apply complete! Resources: 1 added.

6. Log in and push v1

The login lasts 12 hours.

REGISTRY=<your account>.dkr.ecr.us-east-1.amazonaws.com
aws ecr get-login-password --region us-east-1 \
  | docker login --username AWS --password-stdin $REGISTRY
docker tag investment-app:v1 $REGISTRY/investment-app:v1
docker push $REGISTRY/investment-app:v1
What you should see

Login Succeeded, then layers pushing and a line ending in a sha256: digest.

7. See IMMUTABLE refuse a second v1

Optional, but good to recognize.

docker push $REGISTRY/investment-app:v1
What you should see

tag invalid … already exists. That's the protection working.

8. Set the repository policy

Save the JSON above as repository-policy.json. Keep SCHOOL_ACCOUNT_ID.

aws ecr set-repository-policy --repository-name investment-app \
  --policy-text file://repository-policy.json
What you should see

The policy printed back in the output. In the console, Permissions → View JSON shows it.
