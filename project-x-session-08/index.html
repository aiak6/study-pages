📦 Workload types: how do I run it?

The first question for anything on Kubernetes: what kind of object runs it?

KindFitsExample
DeploymentThe default. The app keeps its data somewhere else (a database)The investment app
StatefulSetEach Pod needs its own persistent storage and a stable nameA database running inside the cluster
JobRuns once and finishesA data import, a conversion, a cleanup
CronJobA Job on a scheduleWeekly cleanup, nightly import
DaemonSetOne Pod on every worker nodeMonitoring and log agents
  • Why never a bare Pod: if it dies, nothing brings it back, and you can't scale it from 1 to 2.
  • A Deployment is a manager: Deployment → ReplicaSet → Pods (Containers Session 05).
  • Our app stores its trades in RDS, so a Deployment is right.
  • Do we need a StatefulSet for the database? No. RDS is a managed database: we pay AWS for backups and maintenance. Running Postgres ourselves as a StatefulSet would be cheaper, but then backups and restores are on us (Containers Session 13).
  • Not sure which kind? Read the code and README, or just ask the developer: a short Slack message or a comment on the ticket. A simple question doesn't need a meeting.
  • A classmate asked: could S3 replace the database? No.

🔌 Service types: how do I reach it?

A Service gives changing Pods one stable address. It picks its Pods with a selector (Containers Session 07).

TypeWhat it doesWhen
ClusterIPAn internal address. Only Pods in the same cluster can reach itApp-to-app inside the cluster
NodePortOpens the same port on every worker node (30000–32767 by default). The node passes the request to a PodRare. Our workers are in private subnets behind a NAT gateway, so this can't give public access
LoadBalancerAsks AWS for a load balancer that forwards to the PodsAccess from outside the cluster
  • In class no Service was created. The types were only discussed.
  • Workload types and Service types must be instant answers in an interview. Not being able to define ClusterIP is "a bit embarrassing".

🧩 The whole picture: system design in one breath

Dockerfile → image → ECR → Deployment (2 replicas) → Pods on Karpenter workers ↑ settings: ConfigMap + Secret (as env variables) Pods → RDS same VPC + DB address + credentials + security group rule You → Pod kubectl port-forward (a Service comes later)

For the app to reach RDS it needs four things:

  1. To be in the same VPC (or a connected one). Already true.
  2. The database address: in a ConfigMap or a Secret.
  3. The credentials: in a Secret.
  4. Network permission: the database's security group must allow it in.
  • Whoever lets traffic in opens their firewall. Traffic goes to RDS, so the rule is inbound on the RDS security group. Outbound is normally already allowed (Scale Session 06).
  • If an interviewer asks "how would you deploy an app to Kubernetes?", walk the same path: package it (Dockerfile → image → ECR) → choose the runtime (Deployment, StatefulSet, Job…) → database? → settings (ConfigMap, Secret) → expose it? (which Service type).

🐳 Reading the Dockerfile and requirements.txt

  • First question on any deploy task: where is the code? Here it's small: candidate/ in the app repo, with app.py, requirements.txt and a Dockerfile.
  • ECS → EKS is the lucky case: ECS runs containers too, so the Dockerfile and the image already exist. Moving from EC2 (Ansible, custom AMIs) would mean someone has to write the Dockerfile: you or the developer.
  • requirements.txt = the list of Python packages (and versions) the app needs: Flask, gunicorn, psycopg, requests. They get installed with pip install -r requirements.txt.
# Python app on a small base image
FROM python:3.12-slim
ENV PYTHONUNBUFFERED=1
# the files live in /app
WORKDIR /app
RUN useradd --system investment-app
# standard in every Python image: copy the list, install the packages
COPY requirements.txt .
RUN pip install -r requirements.txt
COPY app.py .
# don't run as root
USER investment-app
# the port to remember
EXPOSE 8080
ENV name=investment-app
CMD ["gunicorn", "--workers", "2", "--preload", "--bind", "0.0.0.0:8080", "app:app"]
  • --workers 2 = two gunicorn worker processes inside the container. Nothing to do with Kubernetes worker nodes.
  • --bind 0.0.0.0:8080 = listen on port 8080 on every address.
  • app:app = the file app.py, and the Flask object called app inside it.
  • --preload = load the app once, before the workers start (Containers Session 03).
  • What would be a red flag: real settings hard-coded with ENV. Those should move to a ConfigMap or a Secret. Nothing like that here.
  • Know these cold: FROM, WORKDIR, COPY, RUN, ENV, EXPOSE, USER, CMD, ENTRYPOINT, plus docker build -t and keeping the image small (Containers Session 02).
  • Decision: don't touch the Dockerfile. Reuse the image that's already in ECR.

📂 Where the YAML lives: app repo vs infra repo

  • We have three repos: infra (Terraform), platform (cluster tools such as monitoring; a Karpenter chart could live there) and app.
  • Kubernetes manifests and Helm charts belong with the app repo (some companies give them their own repo). They're tied to one application: you build it here, you deploy it from here. Infra stands on its own: you can create an EKS cluster without thinking about any app.
  • Then why is the ECS setup in the infra repo? Because it was written in CloudFormation, next to the ECS cluster itself. Not ideal.
  • You can create Kubernetes objects with Terraform (the kubernetes provider), and some teams do everything that way. The instructor wouldn't.
  • Many questions in this job have no single right answer. It comes down to taste and team rules. The safe, widely respected answer: Helm charts.

🚀 The live build: manifests, values from ECS and apply

  • A new folder for Kubernetes manifests in the app repo. The Deployment was started by hand from the Kubernetes docs (copy the example, change the name, image, port, probes, node selector, env), then the AI finished it and created the ConfigMap and Secret.
  • Where things go in the YAML (count the levels, like in a game): nodeSelector goes in the Pod spec (spec.template.spec), not the Deployment's top spec. env, resources and the probes go inside the container, at the same level as image.
  • Where the real values came from: the app is already running on ECS, so copy from there. ECS console → cluster → task → Environment variables. The database user and password were in a Secrets Manager secret (Retrieve secret value).
  • The AI didn't know the variable names until it was given Alex's doc.
  • The Secret is in its own file, which normally goes in .gitignore. The class repo only has secret.example.yaml with placeholders.
  • Letting the AI read real database details is OK in dev. In production, be careful what you let it read.
apiVersion: apps/v1
kind: Deployment
metadata:
  name: investment-app-deployment
  labels:
    app: investment-app
spec:
  replicas: 2
  selector:
    matchLabels:
      app: investment-app
  template:
    metadata:
      labels:
        app: investment-app
    spec:
      nodeSelector:
        karpenter.sh/nodepool: general      # run on Karpenter's workers
      containers:
      - name: investment-app
        image: ACCOUNT_ID.dkr.ecr.REGION.amazonaws.com/REPOSITORY:TAG   # same image as ECS
        ports:
        - containerPort: 8080
        env:
        - name: DB_HOST
          valueFrom:
            configMapKeyRef:                # plain setting
              name: investment-app-config
              key: DB_HOST
        - name: DB_PASSWORD
          valueFrom:
            secretKeyRef:                   # sensitive value
              name: investment-app-secret
              key: DB_PASSWORD
        # ...same pattern for TICKER, DB_PORT, DB_NAME, DB_USER, FINNHUB_KEY
        resources:
          requests: { cpu: "0.5", memory: "50Mi" }
          limits:   { cpu: "0.5", memory: "100Mi" }
        livenessProbe:
          httpGet: { path: /health, port: 8080 }
          initialDelaySeconds: 3
          periodSeconds: 3
        readinessProbe:
          httpGet: { path: /, port: 8080 }
          initialDelaySeconds: 3
          periodSeconds: 3

🔒 Running but not Ready: the RDS security group

The RDS security group only allowed the ECS security group. Nobody had let EKS in yet. The fix, in the console:

  1. RDS → the database → Connectivity & security → open its security group.
  2. Inbound rules → Edit → Add rule: type PostgreSQL (5432), source = the security group the Karpenter workers use.
  3. Save, then restart the Pods, because the app only tries the database when it starts.
  • Check you picked the security group of the Karpenter-launched workers. Not the system node group's, not the control plane's.
  • After that, both Pods became Ready.
  • Why "Running" but not "Ready"? The two probes ask different questions (Containers Session 08):
ProbePathWhat it provesIf it fails
LivenessGET /healthThe process answers. Doesn't touch the databaseThe container is restarted
ReadinessGET /The app can read trades, so the database worksThe Pod gets no traffic, but keeps running
  • A readiness path made by the developer for this purpose would be better than /.
  • Same lesson as Scale Session 06: a timeout to the database almost always means a security group.

🔦 Testing with kubectl port-forward

A way to open the app without exposing it to the internet: a tunnel from your laptop, through the API server, straight to one Pod (Containers Session 06). No Service, no load balancer.

kubectl -n main-product-line get pods                                   # copy a real Pod name
kubectl -n main-product-line port-forward pod/<app-pod-name> 8080:8080  # LOCAL:CONTAINER
# now open http://localhost:8080

kubectl -n main-product-line port-forward pod/<app-pod-name> 10000:8080 # local 10000 → container 8080
  • The right number is the container's port and must be 8080. The left number is your laptop's port: any free one.
  • The tunnel lives only while the command runs. Ctrl+C closes it.
  • Result: the page opened and a buy worked. A buy writes to Postgres, so that's real proof the Pod can use the database. A passing /health alone wouldn't show that.
  • It's a partial success / proof of concept: the app runs on EKS, but there's no Service, nothing is public, and ECS still serves the traffic.
Golden rule: answer the questions before you write the YAML: how does it run, what does it need, who has to let it in, and how will I check it. And "Running" isn't "working": believe it when the page opens and a buy lands in the database.

Check yourself

Answer each question out loud first, then open the answer. Score yourself out of 10.

1. An interviewer says: "We have a Python app in a Git repo. How would you get it running on Kubernetes?" Walk through your answer in order.

Show answer

Package it, choose how it runs, give it its data, its settings and a door, then check it.

  • Package: Dockerfile → image → push to ECR.
  • Runtime: pick the workload type. Usually a Deployment.
  • Database: same VPC, the address, the credentials, and a security group rule.
  • Settings: plain ones in a ConfigMap, sensitive ones in a Secret, both read as env variables.
  • Door: a Service. ClusterIP for inside the cluster, a load balancer or Ingress for outside.
  • Check: Pods Ready, then a real action through port-forward.

It's like moving a shop to a new building: pack the goods, pick the room, connect water and power, hang the sign, then make one real sale.

2. Pick the workload type for each and say why: (a) the investment app, (b) Postgres running inside the cluster, (c) a log-collecting agent, (d) a one-time data import, (e) a weekly cleanup. Why is a bare Pod never the answer at work?

Show answer

(a) Deployment, (b) StatefulSet, (c) DaemonSet, (d) Job, (e) CronJob.

  • Deployment: the app keeps its data in RDS, so any Pod can be replaced at any time.
  • StatefulSet: each Pod needs its own persistent storage and a stable name.
  • DaemonSet: one Pod on every worker node, which is what an agent needs.
  • Job: runs once and finishes. CronJob: the same thing on a schedule.
  • Bare Pod: if it dies, nothing brings it back, and you can't scale it. A Deployment is the manager that keeps the number of Pods you asked for.

3. Your workers are in private subnets behind a NAT gateway. A teammate says: "Just use a NodePort Service to make the app public." What's wrong with that, and what are the real options? Which Kubernetes object gets you an ALB on AWS?

Show answer

A NodePort only opens a port on the nodes, and nobody on the internet can reach a private node.

  • NodePort: the same port (30000–32767) on every worker. Useful only for something else inside the VPC.
  • ClusterIP: inside the cluster only.
  • LoadBalancer Service: AWS creates a load balancer in front of the Pods. For a Service that's a Network Load Balancer.
  • An ALB comes from an Ingress, not from a Service (the shared ALB from Containers Session 08).

Think of NodePort as a side door on each warehouse building. It doesn't help if the whole yard is fenced off.

4. You apply a Deployment with nodeSelector: karpenter.sh/nodepool: general. The Pods stay Pending for a few minutes, then start. Is something broken? Which two things must already exist for a worker to appear at all?

Show answer

Probably nothing is broken: Karpenter is launching a node, and Spot capacity can be slow.

  • Karpenter has two halves, and both must exist. AWS side: IAM roles and friends, created by Terraform. Kubernetes side: the Karpenter controller (installed with Helm) and a NodePool.
  • If the controller was never installed, the Pods stay Pending forever.
  • Check with kubectl describe pod (events) and kubectl get nodes.
  • Our NodePool is Spot only. Fine for dev. Production uses on-demand or a mix so it doesn't wait for capacity.

5. Two app Pods show Running but 0/1 Ready for ten minutes. Liveness is GET /health, readiness is GET /. The developer's notes say /health doesn't check the database and / reads trades. What's your first guess, and how do you confirm it?

Show answer

The Pod can't reach the database.

  • kubectl describe pod: the events show the readiness probe failing.
  • kubectl logs: look at the error text. Timed out → network: check the RDS security group's inbound rules. Password authentication failed → the Secret has the wrong credentials. Host name not found → wrong DB_HOST in the ConfigMap.
  • "Running" only means the container process started. "Ready" means it passed the check that it can do real work.

6. The app on EKS must reach RDS on port 5432. Which security group do you edit, inbound or outbound, and what's the source? Why use a security group as the source and not the nodes' IP addresses?

Show answer

The database's security group: an inbound rule for 5432, with the Karpenter workers' security group as the source.

  • Whoever lets traffic in opens their firewall. The traffic goes to RDS.
  • Outbound from the workers is already allowed, and security groups are stateful, so the reply comes back on its own.
  • Why a security group as the source: Karpenter adds and removes nodes all the time, so their IPs change. A rule that points at the group follows whatever nodes are in it.
  • Make sure it's the group of the Karpenter-launched workers, not the system node group's or the control plane's.

7. You add the missing rule to the RDS security group. Two minutes later the Pods still aren't Ready. Give two likely reasons and what you do about each.

Show answer

The app only tries the database when it starts, and you may have allowed the wrong security group.

  • Restart the Pods so the app connects again, for example kubectl -n main-product-line rollout restart deployment/investment-app-deployment.
  • Check the source group: open one Karpenter-launched instance in EC2 and see which security group it really uses.
  • If it's still failing after that, read kubectl logs: it may be the credentials or the database name, not the network.

A firewall change fixes the road. It doesn't make a driver who already gave up try again.

8. A teammate wants both probes on GET / "so we know the database is fine". Then the database has a 5-minute failover. What happens to the Pods, and why is the class setup better?

Show answer

Every Pod gets restarted again and again for a problem a restart can't fix.

  • A failed liveness probe makes the kubelet kill and restart the container. With the database down, the new container fails too, and you land in CrashLoopBackOff.
  • When the database comes back, the Pods may still be waiting out the back-off, so recovery is slower.
  • With the class setup (liveness /health, readiness /), the Pods just become not Ready: they get no traffic, keep running, and are back the moment the database answers.
  • Rule: liveness asks "is this process stuck?" and should not depend on other systems. Readiness asks "can I serve right now?" and may.

9. You run kubectl port-forward pod/<pod> 10000:8080, open localhost:10000, buy one share, and it works. QA asks: "So the app is live on EKS?" What has your test proven, and what hasn't it?

Show answer

It proves one Pod works end to end. It doesn't prove anyone else can reach it.

  • Proven: the image starts, the env values are right, and that Pod can read and write the RDS database (a buy is a write).
  • Not proven: the second Pod; a Service and its selector (none exists yet); a load balancer, DNS or HTTPS; real users, whose traffic still goes to ECS.
  • The tunnel exists only while the command runs. 10000 is your laptop's port, 8080 is the container's.

It's a test drive in the factory yard, not the car on the road.

10. The app needs seven env variables. Which go in a ConfigMap, which in a Secret, and where did the real values come from in this migration? What happens if you apply the Deployment before the Secret exists?

Show answer

Plain settings go in the ConfigMap, the password and the API key go in the Secret, and the values were copied from the running ECS task.

  • ConfigMap: TICKER, DB_HOST, DB_PORT, DB_NAME, DB_USER.
  • Secret: DB_PASSWORD, FINNHUB_KEY. Putting the host and user in the Secret too is also fine.
  • Source of the values: the ECS task's environment variables in the console, and the Secrets Manager secret it points to.
  • Secret missing: the Pod is created, but the container can't start: CreateContainerConfigError (Containers Session 09). Create the Secret and it starts by itself.
  • Keep the Secret file out of Git. A Kubernetes Secret is only base64, not encryption. The grown-up version is External Secrets (Containers Session 11).

Scoring: 9–10, you can take an app from image to a working Pod 🏆 · 7–8, solid 💪 · below 7, reread Session 08 and retry 🔁
