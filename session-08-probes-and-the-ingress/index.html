Services recap: the three types

Pick a type to see how traffic reaches the pods.

Inside the cluster only. The Service gets a stable address like 172.20.x.x and the name drill. Other pods (like client) call http://drill.

client pod: curl http://drill
↓ CoreDNS: "drill" = 172.20.x.x
ClusterIP 172.20.x.x:80
↓ kube-proxy rule on the node
a ready pod 10.20.x.x:8080

Node IP + a port above 30000. Rarely used. Breaks when nodes are replaced, and unusable on this cluster because EKS Auto Mode gives you no node IPs. Fine for quick dev access or bare-metal clusters.

AWS creates a load balancer (an NLB) for each Service. Easy, but every one is billed by the hour. 5 apps = 5 load balancers. This is exactly the problem the Ingress solves.

Last class's question 2. kube-proxy writes a rule on each node that changes 172.20.x.x:80 into a ready pod's 10.20.x.x:8080.

CoreDNS does something smaller: it only answers "what is the address of the name drill?" with the ClusterIP. In class it was said "CoreDNS does that mapping"; that's the part to correct.

The instructor's advice: don't over-study NodePort or cluster DNS internals. On EKS Auto Mode you rarely touch them.

Readiness lab: the stuck rollout

You start where the demo did: deployment-drill-readiness.yaml applied, 2 pods, probe checks /. Now apply the wrong-path file (probe checks /health, which this image doesn't have) and watch the rollout gate hold.

Rollout: complete
What to notice: the new pod is Running but 0/1. Running means the container started; 0/1 means readiness is failing, so it gets no traffic. Kubernetes won't remove an old pod until a new one is ready, so users never see the broken version. It also won't roll back for you. You fix it by applying the right file.

↓
old ReplicaSet keeps its 2 pods (1/1) → users still served
↓
apply right file → wrong ReplicaSet scaled to 0 → its pod is removed

Liveness lab: the restart loop

A standalone pod drill-liveness. Its liveness probe runs every 5 s and gives up after 2 fails in a row. Time here runs 10× faster than real life.

The wait between restarts doubles each time, up to 5 minutes. While it waits, STATUS shows CrashLoopBackOff.

Same name, same IP, RESTARTS goes up: liveness restarts the container, not the pod. And try changing the path while it runs: in class this gave Forbidden, because you can't change probes on a running bare pod. You have to delete and apply again. A Deployment would swap pods for you.
Liveness factIn plain words
Same check as readiness, different actionAfter failureThreshold fails in a row, restart the container
Checks one containerNot "the whole pod's health"
Best fitAn app still running but stopped answering (hung)
Not for memory leaksA container eating memory is stopped by a memory limit (unit 5)
Check the app itself, never its databaseA slow database would restart every pod at once

The three probes side by side

The kubelet (the agent on every node) runs them against one container, every few seconds, for as long as the container runs.

ProbeQuestion it asksWhen it failsYour Scale twin
ReadinessReady for requests right now?No traffic. Container keeps running and is checked again.Target group health check
LivenessStill working, or stuck?Container restarted in the same pod.ASG replacing an instance
StartupFinished booting?Others wait for it. Never passes → restart.Waiting for an instance to warm up

Settings and their defaults

SettingMeaningDefault
initialDelaySecondsWait after start before the first check0
periodSecondsTime between checks10
timeoutSecondsHow long one check waits for an answer1
failureThresholdFails in a row before it counts as failed3
successThresholdPasses in a row to become ready again1

httpGet passes on status 200–399. Other check types: tcpSocket (port accepts a connection), exec (command exits 0), grpc.

# under the container, in spec.template.spec.containers[]
readinessProbe:
  httpGet:
    path: /              # a URL the app answers, like in a browser (not a folder!)
    port: 8080           # the container's port
  periodSeconds: 5
  failureThreshold: 3

Startup probe: waiting for a slow boot

For an app that takes a long time to start, for example one that loads data or runs database migrations for about 2 minutes. While the startup probe hasn't passed, liveness and readiness don't run at all. If it never passes, the kubelet restarts the container.

Eldiiar has never used one. Most apps start in seconds, and a start that takes minutes usually means a problem in the image. He called startup probes often over-engineering.

All three on one container

Click a probe to highlight its block. Structure only: pick what your app actually needs.

containers:- name: drill  image: SCHOOL_ACCOUNT_ID.dkr.ecr.us-east-1.amazonaws.com/drill:v1  ports:    - containerPort: 8080  startupProbe:              # runs first; the others wait    httpGet: { path: /, port: 8080 }  readinessProbe:            # traffic on/off    httpGet: { path: /, port: 8080 }    periodSeconds: 5    failureThreshold: 3  livenessProbe:             # restart if stuck    httpGet: { path: /, port: 8080 }    periodSeconds: 5    failureThreshold: 2

Startup runs first. Once it passes, readiness and liveness start their checks every 5 seconds.

Two habits from class: keep liveness checking the app itself, never its database (a slow database would restart every pod at once). And don't add all three probes just because the docs say so. Use the ones your app actually needs.

The Ingress: one load balancer, many apps

Five LoadBalancer Services means five AWS load balancers on the bill. An Ingress is just a rule, "this hostname → this Service", added to one shared ALB. Same idea as the listener rules in your Scale alb.tf.

LoadBalancer Service each

One ALB + Ingress rules

The real path of a request

1

Browser asks DNS

A wildcard record already points every *.k8s.312school.com name at the shared ALB. You create no DNS record.

2

HTTPS to the ALB's 443 listener encrypted

The certificate lives here (ACM, made with Terraform). HTTPS ends at the ALB. Port 80 just redirects to 443.

3

Listener rules checked in order

Your host's rule matches. No match at all → the ALB answers its own 404.

4

Rule → target group

Holds the IPs of your ready drill pods. The controller copied them from the Service's EndpointSlice ahead of time.

5

ALB → pod directly plain HTTP, inside the VPC

The Service's ClusterIP is not on the path, and no controller pod is either.

Bonus link to part one: a not-ready pod isn't in the target group, so readiness protects internet traffic too.

More about the controller, and old tutorials

Without Auto Mode, a team installs a controller first, for example the AWS Load Balancer Controller.

Old tutorials use ingress-nginx. Its maintenance ended in March 2026, and this cluster doesn't use it. The Ingress object itself is still current. The Gateway API is a newer API for the same job.

The shared ALB and the certificate

The whole class shares one ALB (group containers-26a). Each student's Ingress adds one rule to its HTTPS listener. An ALB allows 100 rules by default, a soft limit AWS can raise.

The certificate *.k8s.312school.com is in ACM, made with Terraform (aws_acm_certificate, same as Scale's dns.tf). It's free and auto-renews. It's attached through the IngressClass settings, so your Ingress never mentions a certificate.

Everything after the ALB is inside the VPC, so plain HTTP there is safe and faster. Port 80 redirects to 443 with 301 Moved Permanently.

Deleting your Ingress removes only your rule. The shared ALB stays, because the instructor keeps one Ingress there so it never gets deleted.

Your Ingress (only 3 lines really matter)

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: drill
spec:
  ingressClassName: alb                              # 1. the shared ALB
  rules:
    - host: my-namespace.k8s.312school.com   # 2. only your own host is accepted
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: drill                          # 3. your Service...
                port:
                  number: 80                         # ...and its port. Never change it.
Keep number: 80 (the Service's port, not the pod's 8080). A wrong port makes the controller stop updating the shared ALB for every student, and nothing in the cluster catches it.

The hostname rule (admission policy)

The cluster checks every Ingress you apply and refuses anything that breaks these rules. Kubernetes has no such rule by default; it's this cluster's own policy, student-ingress-rules.

RuleWhy
host = <your namespace>.k8s.312school.comNobody can take a classmate's name on the shared ALB
class = albThere's only the one shared ALB
One rule, one path, one ServiceKeeps the ALB under its rule limit

The instructor namespace is exempt, which is how he showed two hosts in class.

On a cluster without this policy

One Ingress can route several paths (or hosts) to different Services. In class it was said "just add more hosts and paths"; that's true in general, but refused here.

rules:
- host: shop.example.com
  http:
    paths:
      - path: /api                 # shop.example.com/api... → api Service
        pathType: Prefix
        backend: { service: { name: api, port: { number: 80 } } }
      - path: /                    # everything else → web Service
        pathType: Prefix
        backend: { service: { name: web, port: { number: 80 } } }

What the instructor stressed, and what's next

Stressed in class

  • Readiness = traffic, liveness = restart. Repeated in every form.
  • get endpointslices is misleading. Use describe to see Ready: false.
  • A failing readiness probe is a safety gate: the rollout stops at the first new pod and the old version keeps serving.
  • Use a Deployment, not a bare pod. A bare pod can't take probe changes without delete-and-recreate downtime.
  • Don't add all three probes just because the docs say so (the SOC 2 story).
  • Memorize the Ingress picture: one ALB, rules per host, straight to the pods. Most companies run production traffic this way, and it saves money.
  • Only three Ingress lines really matter: ingressClassName, host, and the Service name/port.
  • Use AI as a co-teacher: ask it for pitfalls and settings for your own app's probes.
